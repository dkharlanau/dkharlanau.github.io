# Your PR Says Tests Passed. Show the Evidence.

**Source:** Stephen Chin and Cassandra Chin, *“Your PR Says the Tests Passed. Prove It.”*, AI Engineer, 10 November 2026 (23 min). [Talk notes and chapter timestamps](https://qabash.com/bash-tv/74557) · [AI Engineer channel](https://www.youtube.com/@aiDotEngineer).

A coding agent opens a pull request. The description says *“All tests passed.”* That sentence sounds reassuring until you discover the tests ran **before** the final commit—or the agent never captured their output.

The lesson is simple and uncomfortable: **an AI-written summary is a claim, not a test record**.

## The difference between explanation and evidence

The talk describes Tracetoon, which reconstructs a pull request's background from agent session traces, and a Relate-backed graph that connects code, decisions and recorded verification before prose is written. The tooling is interesting, but the underlying problem matters more: your reviewer needs the source of each meaningful claim.

| PR statement | What could support it | What would not prove it |
| --- | --- | --- |
| “The new validation works.” | Test code plus a passing run on the submitted revision | A confident model explanation |
| “Nothing else changed.” | Exact base/head diff and file scope | A list the agent remembers |
| “We ran checks.” | Command, run ID, status, tested commit SHA and timestamp | A check from a previous branch |
| “The issue is fixed.” | Reproduction before; passing regression after | Successful compilation only |
| “Deployment is safe.” | Required approvals, checks and rollout controls | A green unit-test badge alone |

When a check was not captured, say **not captured**. When it failed, say **failed**. When the head commit changed after verification, rerun the relevant checks or mark that evidence stale.

## A compact evidence ledger

~~~yaml
pull_request:
  title: "Add synthetic BP data validation"
  head_sha: "<actual commit from GitHub>"
  change_scope:
    - "validator rule"
    - "regression fixtures"
  claims:
    - id: C1
      text: "Rejects missing mandatory field"
      proof: "test-case-validation-03"
    - id: C2
      text: "Site build passes"
      proof: "workflow-run-id"
  checks:
    - command: "run the project's documented tests"
      status: "not_captured"
      tested_sha: null
  remaining_risks:
    - "target integration behavior not tested"
~~~

This is an editorial training contract, **not** a production schema generated by Tracetoon or GitHub. Replace placeholders with actual evidence. A human owner must still decide whether the proof covers the business requirement.

## Why an evidence graph helps

Consider the chain:

~~~text
Business requirement
  -> changed rule / implementation
     -> test case
        -> test run + log
           -> tested commit
              -> reviewer decision
~~~

A graph is helpful when you need to traverse those relationships repeatedly. It also helps detect orphan claims (“this fixes production”) that have no linked test or business observation. But you do **not** need a graph database for five PRs. A small JSON manifest and normal GitHub checks may be enough.

The architecture choice is between **better evidence retrieval** and **more infrastructure**. Use the simpler one until retrieval and review costs justify the graph.

## A SAP-flavored case

A migration helper changes the file used to mass-update customer attributes. The PR description says *“The output matches the upload template.”* That claim needs more than one happy-path screenshot.

Useful proof includes: column count, order and names; type and date formatting; exactly which cells changed; insert/update/delete classification; stable file generation; and negative cases with missing mappings. These are deterministic properties—test them with code, not another LLM.

The model may summarize the test evidence and identify a gap. It should not invent a passing status or treat an unrecorded manual check as successful.

## 30-minute review exercise

Take one completed PR in a sample repository. Write down five claims from its description. For each claim locate the exact proof: changed file, test name, run ID, commit SHA, timestamp and result.

Classify each claim **supported**, **contradicted**, **not tested**, or **unknown**. Rewrite the PR in plain English using only supported statements.

**Architect challenge:** A code-generation agent tested commit A, then changed one line and pushed commit B. Can the PR say “CI passed”? What tests are now stale, and who is authorized to merge?
