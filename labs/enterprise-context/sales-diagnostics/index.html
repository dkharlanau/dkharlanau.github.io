Assessment recall

A Lead does not start with a fix. A Lead narrows the state and the owner.

For an assessment answer, show how you move from a vague symptom to evidence, ownership, and proof of recovery.

record_voice_over

60-second answer: I first define the expected process state and reproduce the symptom with one bad document. Then I compare it with a good case and find the first field, status, quantity, date, message, or document step that differs. That first divergence tells me which process boundary to inspect. I collect evidence for that owner before changing configuration. After the correction, I repeat the same business path and prove both the technical state and the business result.

First-wrong-state method

Expected → actual → divergence → owner → proof.

This five-step loop is the default way to read a Sales incident. It works across pricing, ATP, delivery, billing, master data, and integration failures.

1. Expected

State what should have happened at this process step. Use the business document and its intended state, not a transaction code.

2. Actual

Capture the wrong document, status, value, message, date, quantity, or follow-on result as evidence.

3. Divergence

Compare a good and bad case and find the earliest point where they stop matching.

4. Owner

Map that divergence to the owning layer: master data, Sales control, pricing, supply, logistics, billing, finance, or integration.

5. Proof

After the change, repeat the same path and prove that the corrected state produces the expected downstream result.

Rule: the first visible symptom and the root cause can live in different modules. Move backward only until you find the first wrong state; do not keep expanding the search after ownership is proven.

Diagnostic contract

Use the casebook to narrow the owner, not to guess a fix.

The cases are symptom-first, but the investigation is state-first. Start with the document, message, or business result that is wrong. Then move backward through the process until you find the first wrong state. A billing symptom can originate in the sales order, shipping, or billing. A price difference belongs first to the pricing model. A JIT quantity problem can belong to the Automotive JIT flow or to integration operations.

Collect evidence before changing configuration. Compare one good document with one bad document. Capture only the data that can separate the cases: document flow, status, partners, organizational data, message identity, quantities, dates, and copied values. The first meaningful difference is usually a better diagnostic starting point than a long list of Customizing possibilities.

Product behavior is checked separately from the authored diagnostic path. For example, SAP documents how billing split analysis compares differing header and business-partner fields, while the casebook adds a practical ownership sequence for investigation. See SAP Help for Split Analysis and Billing Document Split and Convergence. The casebook does not turn these product facts into a universal root-cause list. It keeps the evidence, the hypothesis and the recommended change as separate steps.

FAQ / fast repetition

Five habits that prevent weak incident analysis.

01symptom

Should I start from the transaction where the user sees the error?

Start from the business state that is wrong. The screen tells you where the symptom is visible, not necessarily where the wrong state was created.

02compare

Why compare a good and bad document?

Because the comparison removes many irrelevant possibilities. The first meaningful difference gives you a concrete hypothesis and a smaller ownership boundary.

03owner

When do I involve another module or team?

When the first wrong state belongs to that layer. Send the evidence package with the exact divergence instead of forwarding only the final symptom.

04change

Why not change Customizing and test quickly?

Because a change without a proven owner can hide the symptom while leaving the real defect in place. First prove which rule, data object, or interface state is wrong.

05proof

What counts as proof of fix?

Repeat the same business path and show that the corrected state produces the expected downstream result. A changed configuration value alone is not proof.

Human + machine

One reasoning model, two consumers.

Consultants read the case. Agents retrieve the same case by symptom, process ID or mechanism ID and keep the evidence boundary intact.
