Decision Card / Clean Core

Where should SAP
extension logic live?

RAP, CAP, BAdI, key-user tools, and BTP are not the first decision. Start with business ownership, coupling, transactional consistency, data location, lifecycle, and failure behavior.

My default

STDStandard firstConfigure before extending
NEAROn-stackWhen transaction coupling is real
OUTSide-by-sideWhen lifecycle should be decoupled
Choose the boundary before the technology.
rule

Decision in one sentence: use standard behavior when it represents the requirement, use released on-stack extensibility for rules that must live close to the SAP transaction, and use side-by-side extensibility when the capability should be loosely coupled or own a separate lifecycle.

Placement test

Ask what the extension must own.

NeedDefault direction
Small UI, field, form, or simple business adaptationKey-user extensibility where supported.
Complex logic tightly coupled to the SAP business object or transactionDeveloper/on-stack extensibility through released objects and extension points.
Cross-system process, separate product lifecycle, external data, or independent scalingSide-by-side on BTP using released APIs or events.
Requirement already represented by standard configuration or master dataNo extension. Fix the design at the standard owner.
Direct modification of SAP internalsException only, with explicit technical debt and upgrade consequence.

Decision drivers

Coupling is more useful than fashion.

Transaction boundary

If the rule must be part of the same business transaction and consistency boundary, moving it outside can create new failure modes.

Data ownership

Keep logic close to the system that owns the authoritative state unless the extension intentionally owns a separate business capability.

Latency and availability

A synchronous external dependency can turn an S/4 transaction into a network-availability problem. Make that trade-off explicit.

Lifecycle

Side-by-side is stronger when teams need independent deployment, scaling, runtime, or technology choices.

Release stability

Prefer released APIs, events, BAdIs, CDS views, and ABAP Cloud contracts over direct use of internal objects.

warning

Anti-pattern: move logic to BTP only to call it clean core, while every sales or procurement save now depends synchronously on that remote service. The code moved; the coupling did not.

I change the default when: legal isolation, independent scale, external data ownership, product-team lifecycle, or a required cross-system process outweighs local transaction coupling.

Lead check: name the business owner, consistency boundary, failure mode, released contract, and upgrade path before choosing the implementation technology.
