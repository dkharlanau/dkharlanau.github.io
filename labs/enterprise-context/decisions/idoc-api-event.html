Decision Card / Integration

IDoc, API,
or event?

The wrong starting question is “which technology is newer?”. The useful question is what kind of dependency the business process actually needs.

My default

SYNCAPIImmediate business response
ASYNCIDocDurable SAP document exchange
FACTEventNotify interested consumers
Choose the interaction before the platform.
rule

Decision in one sentence: use a synchronous API when the caller needs an immediate business response, use an asynchronous document message when reliable business transfer and recovery matter more than immediacy, and use an event when the producer should publish a fact without knowing every consumer.

Decision drivers

Five questions change the design.

1. Does the sender need an answer now?

If the next business step cannot continue without a result, a request-response API is usually the cleanest contract.

2. Can the receiver be temporarily unavailable?

If yes, prefer a pattern with durable delivery, retry, queueing, or controlled reprocessing instead of making availability a shared runtime problem.

3. Is this a command, document, or fact?

“Create this object” is different from “this object changed”. Events should not be disguised remote procedure calls.

4. Who owns replay and duplicates?

Reliable delivery is useful only when the receiver can recognise duplicates where needed and the support team knows how replay is controlled.

5. How many consumers exist?

A point-to-point interface can be simpler for one receiver. Events become more attractive when independent consumers need the same business fact.

Default choice

Start simple, then add decoupling where it buys something.

PatternI prefer it whenI avoid it when
APIThe caller needs validation, calculation, availability, confirmation, or another immediate business result.The receiver may be unavailable for long periods, the process tolerates delay, or retry would couple two support teams too tightly.
IDoc / asynchronous documentA durable SAP business document must cross a system boundary with explicit monitoring and reprocessing.The interaction is genuinely conversational or the consumer only needs a lightweight notification.
EventA business fact should be published to one or many independent consumers without the producer controlling their process.The sender actually expects the receiver to execute a command and return a business outcome.
warning

I change the default when: ordering is strict, payloads are very large, legal acknowledgement is required, the interface is external B2B, the landscape has a mandated platform, or the receiving application has only one supported contract.

Failure ownership: transport success is not business success. The design needs a clear owner for retries, duplicate handling, reconciliation, and proof that the receiver reached the expected business state.
