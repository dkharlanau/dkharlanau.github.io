Decision Card / Integration

When does integration
need message ordering?

Ordering is needed when a later business event becomes invalid if it overtakes its predecessor. Global serialization is usually too expensive.

My default

RULEPredecessorWhat must finish first?
COSTTrade-offBlocking and throughput
Ordering is a business invariant, not a queue preference.
rule

Decision in one sentence: require ordered processing only where predecessor completion changes business meaning, keep the sequence scope narrow, and design retries and reconciliation inside the same ordering model.

Decision test

Ask whether overtaking changes the result.

SituationDefault
Create before change or cancel for the same objectOrder that object stream.
Independent orders or customersKeep parallel processing.
Receiver is idempotent but messages arrive out of sequenceIdempotency is not enough.
One failed predecessor blocks successorsAccept and operate the blocking if strict order is required.
Version checks can reject stale updatesPrefer version-aware processing when it removes the need for broad serialization.

Lead checks

Define the sequence before choosing the queue.

Business key

Order one sales order, purchase order, material stream, or other real business unit. Do not serialize unrelated work.

Predecessor rule

State which event must complete before the next event is valid.

Failure behavior

Strict ordering creates head-of-line blocking. Define correction, parking, replay, and escalation ownership.

Throughput

Exclusive sequential processing reduces parallelism. Use it only where correctness needs it.

End-to-end proof

Queue order is not enough if sender, protocol, receiver, or downstream logic can reorder the same business events.

warning

Anti-pattern: put every message in one exclusive queue because “order matters”. One unrelated failure can stop everything.

Lead proof: name the sequence key, predecessor rule, duplicate model, blocked-message behavior, throughput cost, and reconciliation method.
