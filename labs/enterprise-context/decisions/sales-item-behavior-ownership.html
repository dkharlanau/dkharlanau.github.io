Decision Card / Sales Architecture

Where should sales
item behavior live?

When a sales item behaves differently, my first question is which standard control layer owns that behavior. Custom code is the last layer, not the first reflex.

Control stack

HDRDocument typeCommercial frame
ITMItem categoryItem business behavior
SCHSchedule lineQuantity and supply behavior
Use the narrowest standard owner that matches the business meaning.
rule

Decision in one sentence: place the rule at the lowest standard control level that directly represents its business meaning, and use an extension only when document type, item category, schedule line, determination, or governed master data cannot express the requirement clearly.

Control ownership

Do not make one enhancement own the whole order.

Control layerGood fitWarning sign
Sales document typeOverall transaction class, document-wide checks, number/control frame, common business behavior.The rule applies only to one kind of item but changes every order of the document type.
Item categoryPricing relevance, delivery/billing relevance, item-level business role, special process behavior.The logic is really about supply quantity/date or movement behavior.
Schedule line categoryRequirements transfer, availability, delivery relevance, movement and quantity/date execution behavior.The rule is purely commercial and has nothing to do with supply or schedule lines.
Master data / determinationReusable attributes that should vary by material, customer, plant, business context, or valid configuration key.Business users cannot explain why a value is selected without reading code.
ExtensionA real gap with explicit input contract, owner, tests, fallback, and clean-core boundary.The enhancement re-implements standard determination or contains unrelated policy branches.

Decision test

Ask what should change downstream.

Should the item be priced?

Start with item behavior and pricing relevance before inventing code that suppresses conditions later.

Should it be delivered or billed?

Item category is a natural control candidate when the business role changes delivery or billing relevance.

Should supply be planned or checked?

Schedule-line behavior is the stronger owner when requirements transfer, ATP, delivery relevance, or movement semantics change.

Should the same product behave differently by context?

Use standard determination inputs or governed rules when possible so the variation is visible and testable.

Does no standard layer represent the requirement?

Then define an extension contract. Name exactly which standard result it changes and what happens if the extension is unavailable.

warning

Anti-pattern: a central user exit with dozens of customer, material, country, and process branches that silently rewrites item or schedule-line behavior after standard determination.

Lead check: explain the upstream inputs, the selected control object, the downstream consequence, and one test that proves the chosen layer is correct.

Evidence path

Trace control before extension.
