Our code system

One stable mnemonic. Vendor IDs stay references.

SD.<code> means a process or process variant. SD+<code> means an overlay or cross-cutting capability. That keeps the learning key stable even when scope items, apps, or release labels move around.

SD.Process / variant

Examples: SD.TPO, SD.CON, SD.AIC.

SD+Overlay / capability

Examples: promotions, payment overlays, or related-object navigation.

Lead branch answer

Start from standard sell-from-stock, then name the changed rule.

Special-process questions become much easier when the answer is a controlled delta from the baseline instead of a separate memorized document chain.

Baseline

State the ordinary customer order → delivery → goods issue → billing path and the normal ownership of stock, supply, and billing.

Changed business rule

Name the one or two rules that create the branch: supplier ownership, legal entity, customer-specific supply, consignment ownership, return disposition, transfer of control, or billing trigger.

Document consequence

Explain which document or stock object appears, disappears, or changes role because of that business rule.

Cross-process owner

Show where Procurement, Production, Inventory, Shipping, Billing, FI/CO, EWM, or TM becomes part of the process.

Failure proof

Pick one likely failure and trace the first wrong rule or object. Do not repair the final sales document before proving the branch was correct.

Trade-off

Explain why this variant is useful and which commercial, operational, accounting, or integration cost it adds compared with the baseline.

Long-term sales agreements / Contract logic

We separate the commercial commitment from the execution signal.

When we design a long-term customer agreement, we first ask where the real delivery quantity and date live. That question separates quantity contracts, value contracts, and sales scheduling agreements much faster than memorizing document types.

SD.QCON

Quantity contract

We agree a target quantity for a validity period. We do not normally keep the detailed delivery schedule in the contract. When the customer wants goods, we create a release order and consume the open contract quantity.

SD.VCON

Value contract

We agree a target monetary value. Release orders consume the open value, and we can allow a defined material scope, product hierarchy, or other agreed selection. We monitor value in the contract currency.

SD.SA

Sales scheduling agreement

We keep recurring delivery requirements in delivery schedules and schedule lines. We therefore do not need a separate call-off sales order for the normal execution path: the schedule lines themselves become delivery relevant.

route

Our memory rule: if we only know the total quantity or value, we usually need a release order to create executable demand. If we already receive exact quantities and dates over time, we are closer to a sales scheduling agreement.

Quantity contract flow

We use Contract → Release Order → ATP / Schedule Lines → Delivery → PGI → Billing. The contract holds the commercial quantity ceiling; the release order introduces the operational quantity and requested date.

Value contract flow

We use the same release-order pattern when fulfillment happens through sales orders, but we consume value instead of quantity. SAP can also bill the value contract directly when we use a billing plan.

Scheduling agreement flow

We use Scheduling Agreement → Delivery Schedule → Schedule Lines → Delivery → PGI → Billing. We focus on forecast, JIT, planning, cumulative quantities, and delivery-due processing.

Release order / What we actually configure

We treat the call-off as a referenced sales order, not as a special warehouse document.

When we create a release order, SAP checks the contract context and updates its consumption. We therefore design the reference chain as carefully as the order itself.

1. We prove the source and target

We define which order type may follow the contract. In copy control, we verify the source contract type, target order type, and the relevant header and item relationships.

2. We check eligibility

We expect the release to respect validity, allowed products, authorized partners, and remaining quantity or value. We do not bypass these controls just because the customer order can technically be entered.

3. We decide what is copied

We use copying requirements and data-transfer logic to control whether the reference is allowed and which data moves into the order. We also decide where pricing is copied and where we want redetermination.

4. We protect document flow

We keep the reference visible so the contract can show its release orders and update released quantity or value correctly. When consumption is wrong, we inspect the reference chain before changing the final order.

difference

We keep two controls separate: Outline Agrmt Mess. helps us find an open contract while we create an order. Copy control defines whether the contract can become that order and how the reference behaves. Automatic contract search does not replace copy control.

Automatic contract search / Outline Agrmt Mess.

We can let SAP look for an open agreement instead of forcing users to know the contract number.

We configure this behavior in the sales document type. The header-level options focus on the customer context; the item-level options also use the material context. We choose the behavior according to how much automation we want.

Blank

We do not search

We create the order without an automatic open-outline-agreement check.

A / B

We check and let the user decide

We search at header or item level. When SAP finds open agreements, we let the user review the available references and decide whether to use one.

C / D

We copy automatically when the result is unique

We search at header or item level. If exactly one suitable open agreement exists, we let SAP use it automatically; otherwise we keep the selection problem visible.

E / F

We go straight to the selection list

We search at header or item level and move directly to the list of suitable agreements instead of showing an intermediate dialog.

Value contract / Billing decision

We decide whether the contract is only a commercial ceiling or also a billing object.

A value contract gives us two different billing designs. We should state the chosen design explicitly because they produce different document chains and different operational expectations.

Path 1

We bill the release order

We create the call-off order, fulfill it, and bill the resulting order or delivery according to the normal sales process. The value contract remains the long-term commercial control and tracks released value.

Path 2

We bill the value contract directly

We use a billing plan in the value contract and bill planned dates or partial values from the contract itself. We then treat billing-plan design, corrections, and target-value changes as part of the contract design.

Currency

We keep one consumption currency

We can create a release order in another currency, but SAP converts the released value into the contract currency. We therefore distinguish order currency from the currency that controls the contract ceiling.

receipt_long

Billing detail we should remember: when we bill the release order, the release is still an ordinary sales-order flow and can be billed according to its billing relevance, for example order-related or delivery-related. In classic standard examples, OR is commonly used for the release order. When we bill the value contract directly, the billing plan makes the contract itself billing relevant; classic documentation also uses WA as a standard example. We treat those document-type codes as implementation anchors, not as universal design rules.

We adjust open billing dates

If we change the target value of a value-contract item, SAP can recalculate the still-open billing-plan dates so that the remaining contract value is distributed across the open dates.

We do not assume unreleased value will bill itself

A value contract that has not been completely released is not automatically billed. We therefore separate “billing plan exists” from “the contract is ready for automatic billing.”

We control target reductions after billing

If billed billing-plan dates already exist and we later reduce the target value, SAP does not automatically check whether the contract is now overbilled. We review the difference and, where required, create a credit memo.

Value contract / Release authorization

We control who may call off the agreement and who may receive the goods.

Partner authorization is not the same as normal partner determination. We use it to decide whether another sold-to party may release against the contract and which additional ship-to parties are valid for the resulting release order.

AA

We authorize additional releasing sold-to parties

Partner function AA represents an additional sold-to party authorized to place release orders against the sales contract. We can maintain several AA partners.

AW

We authorize additional receiving ship-to parties

Partner function AW represents an additional ship-to party for the release order. If several valid ship-to parties exist, SAP can present the choices when we create the release.

KAB

We keep the release-partner procedure explicit

In the standard release-order partner setup, procedure KAB contains the AA and AW functions. We still verify the assigned partner procedure in the target system instead of assuming the standard template was kept unchanged.

Rule blank — we do not check

Any releasing partner can be accepted. We use this only when the business deliberately does not want partner authorization control.

Rule A — we check contract partners

We accept the contract sold-to party and the additional authorized releasing partners stored with partner function AA in the sales contract.

Rule B — we check the hierarchy

We can authorize partners below the contract sold-to party in the customer hierarchy. This is useful when a central agreement is consumed by subordinate customers.

Rule C — we combine both models

We accept a partner when it passes the contract-partner rule or the customer-hierarchy rule. We use this when a commercial agreement needs both explicit authorized partners and hierarchy-based releases.

group

Our distinction: AA answers “who else may order against this contract?” AW answers “where else may we ship the released goods?” We treat this as a header-level authorization model, not as an item-level material permission.

Contract lifecycle / Dates and defaults

We design the validity period as a rule, not just two manually entered dates.

For contracts that use the relevant contract-profile functionality, we can default lifecycle behavior instead of asking users to calculate every start date, end date, cancellation rule, or follow-up manually.

We determine the start date

We can base contract dates on a rule such as the current date or another business event. The exact baseline dates depend on the contract model and deployment.

We derive the end date

We can combine a baseline date with a duration or date rule. This is useful when the commercial term is “one year from start” rather than a manually maintained calendar date.

We control cancellation and follow-up

A contract profile can provide default date-determination rules, cancellation behavior, and follow-up actions for the relevant contract type. We verify the exact profile fields for the S/4HANA edition we implement.

We keep validity operational

The validity period is not descriptive master data. It is part of release-order eligibility, so a wrong start or end date changes whether we can consume the agreement.

Quantity contract / Down payment

We can collect money before we allow the release order to move into delivery.

For sales quantity contracts, we can use a milestone billing plan for down-payment processing. We create the down-payment request from the contract and create the release order with reference to the same contract. With the relevant configuration, we keep the release-order schedule lines blocked for delivery until the required down payment is received.

Quantity Contract→ Milestone Billing Plan→ Down-Payment Request→ Release Order with Delivery Block→ Incoming Down Payment→ Delivery→ Final Invoice with Down-Payment Clearing

We request

We generate the down-payment request from the contract billing plan.

We protect fulfillment

We can block the release-order schedule lines from delivery while the required down payment is still open.

We release

After the customer payment is posted and the configured requirement is satisfied, SAP can remove the delivery block and we continue fulfillment.

We settle

In final billing, we clear the down payment against the amount due instead of charging the customer twice.

record_voice_over

Our 60-second assessment answer: We use a quantity or value contract when we want a long-term commercial ceiling but do not yet know every delivery date. We consume that agreement through a release order, which is a sales order created with reference to the contract. We use copy control for the contract-to-order relationship and Outline Agrmt Mess. when we want SAP to search for open agreements during order entry. With a quantity contract we control released quantity; with a value contract we control released value and can also bill the contract directly through a billing plan. If the customer sends recurring concrete quantities and dates, we move to a sales scheduling agreement, where the schedule lines themselves drive delivery.

Fast comparisons

Most assessment questions hide inside a contrast.

The useful answer is rarely a definition. It is the boundary between two processes that look similar until one document, stock segment, ownership rule, billing trigger, or execution object changes.

SD.TPO ↔ SD.PTO

Direct ship vs order-specific supply

TPO: the external vendor can ship directly to the customer. PTO: procurement is pegged to the sales item so the acquired supply cannot quietly satisfy another demand.

SD.ICO ↔ SD.AIC

Classic relationship vs orchestrated value chain

ICO: selling and delivering company roles are connected through delivery and intercompany billing. AIC: additional intercompany purchase/sales documents and transfer-of-control logistics make the internal leg explicit.

SD.SFS ↔ SD.VST

Physical goods issue vs transfer of control

SFS: ordinary stock leaves the plant. VST: goods may have physically left while value still remains in a controlled transit stock segment until transfer of control.

SD.CSH ↔ SD.RSH

Immediate payment vs immediate delivery

Cash sales: payment and order-related cash billing are immediate. Rush order: delivery is immediate, but normal delivery-related invoicing follows later.

SD.BOM.ERLA ↔ SD.BOM.LUMF

Main item vs component ownership

ERLA: commercial and logistics behavior sits mainly on the higher-level item. LUMF: subitems become operationally relevant, including delivery-group behavior.

SD.CON.FILL ↔ SD.CON.ISSUE

Move stock vs transfer ownership

Fill-up: stock moves to the customer site but stays yours. Issue: customer withdrawal consumes consignment stock and becomes billing relevant.

SD.RET.LEAN ↔ SD.RET.ARM

Simple receipt vs controlled disposition

Lean: receive, return to valuated stock, then credit. ARM: inspection, follow-up activity, refund logic, and replacement create a real reverse-logistics decision tree.

SD.TPO.SN ↔ SD.TPO.NSN

Supplier event visibility

With notification: supplier shipment becomes an explicit logistics signal. Without notification: customer visibility depends more heavily on confirmations and invoice events.

SD.BILL.CANCEL ↔ SD.CLM.CMR

Reverse an invoice vs grant a credit

Cancellation: the billing document itself was wrong and should be nullified. Credit memo: the invoice may remain valid while the commercial receivable is reduced.
