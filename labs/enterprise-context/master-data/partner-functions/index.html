Customer Sales Partner Functions

Sales documents rarely contain only one customer role. Sold-to, ship-to, bill-to and payer can be different Business Partners. Customer sales partner functions store the maintained relationships that allow SAP to propose those roles consistently for a sales area.

Customer, sales area, partner function and partner counter.

Mental model

Configuration asks for a role; master data supplies the partner.

database

Scope: Customer, sales area, partner function and partner counter.

Important data

Partner function, assigned partner, sales area, partner counter for multiple relationships and relevant validity or relationship data.

Configuration boundary

The partner procedure is configuration; the partner assignment is master data. A required role can therefore fail either because configuration expects it or because no suitable master relationship exists.

Partner function map

Know the four core customer roles first. Then read the extended roles by partner type and scenario.

There is no single universal list that is identical in every SAP system. SAP delivers standard functions, but the active set depends on deployment, language conversion, installed scope and Customizing. The table below is the high-value Sales set to know for design, support and assessment work.

translate

Internal code and UI abbreviation are not always the same. For the four standard customer roles, SAP APIs use the language-independent database values AG, WE, RE and RG. In an English UI they are commonly shown as SP, SH, BP and PY. For integrations, CDS filters and API payloads, verify which representation the interface expects instead of copying the visible UI abbreviation.

Assessment shortcut: do not answer “the customer.” Name the exact role. One legal customer can order, another location can receive, a shared-service center can receive the invoice, and a parent company can pay.

Extended standard set

Sales partner processing is not limited to four customer roles.

SAP Sales can also work with contact people, employees, suppliers and scenario-specific customer partners. These functions are useful in contracts, logistics execution, output, integrations and project-related Sales scenarios.

warning

Do not confuse partner type with partner function. Sales processing uses four main partner types: KU Customer, LI Supplier, PE Personnel and AP Contact Person. A partner function is the specific business role inside that type, for example WE Ship-to under KU or ZM Employee Responsible under PE.

Custom Z* partner functions are normal in customer systems. The design question is not “does SAP have a code for this name?” but “what partner type, determination source, cardinality, change rule and downstream consumer does this function need?”

Released CDS

I_PartnerFunction and I_PartnerFunctionText provide the available partner functions and their partner types. Use them when you need a clean, released view of the configured catalogue.

Customer master relationship

I_CustSalesPartnerFunc exposes customer, sales organization, distribution channel, division, partner counter and partner function. The Business Partner API exposes the same master-data concept through A_CustSalesPartnerFunc.

Sales document runtime

I_SalesOrderPartner lets you inspect the partner function actually stored at sales-order header level and whether the partner is a customer, supplier, personnel number or contact person.

Classic diagnostics

In private-cloud/on-premise investigations, TPAR is a useful partner-function definition reference, KNVP is the classic customer sales partner-assignment table, and VBPA stores document partners. Prefer released CDS/API objects for new integrations.

api

Integration rule: many Sales APIs expect the database/internal partner-function format. For example, send WE for ship-to when the API requires the internal value, even if the English UI displays SH. Never hard-code translated UI labels into an integration contract.

Control model

A partner function is useful only when the full determination chain is coherent.

01

Define the function

Know the business meaning and the partner type that supplies the number: customer, supplier, personnel or contact person.

02

Place it in a procedure

Decide whether the role is required, optional, repeatable, changeable and where SAP should search for it.

03

Assign the procedure

Connect the procedure to the relevant master-data or document context such as a customer account group, sales document header/item design or delivery design.

04

Maintain the relationship

For customer partner functions, maintain the actual assigned partner in the correct sales area and use the partner counter when several assignments are allowed.

05

Prove the document result

The document partner set is the runtime truth. Reference documents, interfaces, manual changes and item-level deviations can produce a result different from the master-data default.

Runtime use

The document resolves roles first, then downstream processes consume those roles.

At document creation the partner-determination procedure defines which partner functions are relevant and how they are resolved. Customer or Business Partner master data supplies maintained relationships. The document stores the resulting sold-to, ship-to, bill-to, payer, and any other relevant partners, and later processes consume the role that matters to them.

01

Name the wrong role

Do not say “the customer is wrong.” State whether the wrong value is sold-to, ship-to, bill-to, payer, or another partner function.

02

Read the procedure

Check whether that role is required, optional, repeatable, or otherwise controlled by the active partner-determination design.

03

Read the relationship

Verify the maintained partner assignment for the relevant customer and sales area, including multiple relationships where they are allowed.

04

Prove the document partner

Compare the master relationship with the partner actually stored in the sales document and check whether a user, reference document, or interface changed it.

05

Follow the consequence

Trace only the downstream behavior owned by that role: destination, invoice recipient, payer context, output recipient, or another role-specific result.

Troubleshooting

“Wrong customer” is too vague; name the partner function.

troubleshoot

Start with the actual partner set in the document and identify the wrong role. Then compare the active partner procedure with the sales-area relationship that should supply that role. If master data is correct but the document differs, inspect reference-document transfer, explicit interface input, or a permitted manual change before editing the shared relationship.

Assessment recall

Separate role control from partner master data.

record_voice_over

60-second answer: I separate the rule from the relationship. Partner determination defines which roles the Sales document needs and how they are resolved; customer or Business Partner master data provides the maintained partners for those roles. When a partner is wrong, I name the function first, compare the procedure and master relationship, then prove what the document actually stored and whether reference data, an interface, or a manual change replaced it. That is safer than changing the sold-to record because a ship-to or payer is wrong.
