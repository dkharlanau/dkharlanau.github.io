Sales BOM / Product Structure

A Sales BOM allows a sellable header product to explode into components in the sales document. The commercial behavior depends heavily on whether pricing and logistics are controlled at header or component level.

Follow the runtime path arrow_downward

Object profile

01MD.SD.BOMCatalogue ID
02logistics adjacent masterData class
Header product, BOM usage, plant/validity, components and quantities.

Mental model

The BOM owns the structure; item categories own the Sales behavior of that structure.

database

Scope: Header product, BOM usage, plant/validity, components and quantities.

Important data

BOM usage, header material, components, component quantities, alternative BOM, validity and plant context where relevant.

Configuration boundary

The BOM defines product structure. Item-category determination and pricing relevance are configuration, so the same structure can produce different sales behavior under different item-category settings.

Runtime use

Explosion answers “which components?”; Sales control answers “which level matters?”

When the sellable header is entered, the valid Sales BOM can explode into component subitems. The BOM explains the product structure and quantities. Item-category and process configuration then decide whether commercial value, delivery relevance, and other Sales behavior live mainly on the header, the components, or both.

01

Prove the BOM context

Start with header product, plant or usage context, validity, and the BOM alternative that should apply to the Sales item.

02

Check the explosion

Compare the expected component structure and quantities with the subitems actually created in the document.

03

Read item categories

Identify the header and component item categories created by the explosion. This is where the product structure becomes Sales behavior.

04

Locate commercial and logistics control

Prove which level is pricing-relevant, delivery-relevant, or otherwise active before changing the BOM structure.

05

Continue downstream

If the structure and item categories are correct, diagnose pricing, ATP, delivery, or billing at the level that actually owns that process.

Troubleshooting

Wrong components and wrong component behavior are different failures.

troubleshoot

If components are missing or wrong, start with BOM usage, validity, plant context, alternative, and component quantities. If the structure is correct but pricing or delivery relevance is wrong, inspect the resulting item categories and their controls. Editing the BOM cannot repair a Sales-control problem when the explosion itself is correct.

Assessment recall

Structure first; Sales control second.

record_voice_over

60-second answer: A Sales BOM defines the product structure behind a sellable header. When the header is entered, the valid BOM can explode into components. I separate that structure from Sales control: item-category determination decides how the header and subitems behave and where pricing or delivery relevance lives. If components are wrong, I diagnose BOM validity and structure; if the components are correct but their commercial behavior is wrong, I move to item categories.
