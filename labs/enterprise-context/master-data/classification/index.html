SAP Cross-Application / Logistics Master Data

Classification: reusable attributes across logistics objects.

Classification lets SAP describe materials, batches, equipment, documents and other supported objects with structured characteristics. It gives many applications one reusable attribute model instead of adding a dedicated field for every business property.

Start with the mental model arrow_downward
rule

Boundary: Classification describes an object. It does not decide business behavior on its own. A search, batch strategy, release strategy, variant model, report, interface, or other consumer must explicitly read the class or characteristic values.

Mental model

Separate definition, structure, assignment, and valuation.

Most Classification problems become easier when these layers are checked separately.

Characteristic

Defines one attribute: data type, length, units, allowed values, value ranges and other controls. Example: COLOR, VOLTAGE or VISCOSITY.

Class

Groups related characteristics into a reusable model. A class always belongs to a class type.

Object assignment

Connects a material, batch, equipment object or another supported object to the class.

Valuation

Stores the actual characteristic values for the classified object, for example COLOR = BLACK or POTENCY = 98.7%.

Core objects

The class type is the first design decision.

The class type defines the classification context and which object types can participate. Do not reuse a class only because its characteristics look similar.

Class typeTypical object or purposeWhy it matters

023Batch / material contextWidely used for batch classification when batch identity is material- or client-level. Supports the material-to-batch object hierarchy.
017DocumentCan classify document information records with structured attributes.

account_tree

Lead rule: class type is not a cosmetic category. It controls object behavior, allowed object types and special functions. Changing class-type design later can affect interfaces, searches, configuration models and historical valuations.

Configuration and maintenance

Build the model from the characteristic upward.

A clean setup separates reusable attribute definitions from classes and object-specific values.

01

Define the characteristic

Use CT04. Choose the data type, length, decimal places, unit of measure, single or multiple values, allowed values, intervals and descriptions.

02

Create the class

Use CL01/CL02 and select the correct class type. Add the characteristics that describe the object family.

03

Assign the object

Classify the object through its application UI or with classification transactions such as CL20N/CL24N, depending on object and scenario.

04

Maintain values

Enter the actual characteristic values for the object. Validate that required values, ranges and units match the business definition.

05

Search and consume

Use CL30N or the consuming process to prove that the object can be found and that the expected runtime mechanism reads the classification.

Characteristic design choices

SettingDesign questionCommon risk
Data typeIs the value numeric, character, date, time, currency, or another supported type?Using free text for a value that should be validated makes search and integration unreliable.
Allowed valuesShould users select from a controlled catalogue?Variants such as Black, BLACK and Blk create semantic duplicates.
IntervalIs a range valid, for example viscosity 5000–12000?Ranges can become inconsistent with downstream batch or configuration logic when changed without impact analysis.
Multiple valuesCan one object legitimately have several values?Enabling multiple values where the process expects one can create ambiguous selection results.
UnitDoes the number require a unit such as V, mm, kg or %?A numeric value without controlled unit semantics is easy to misinterpret in interfaces and search.

Search behavior

Classification is also a search model.

A major benefit is finding an object by business attributes when the exact material or object number is unknown.

Same characteristic

When several permitted values are selected for one characteristic, the search normally treats them as alternatives: value A OR value B.

Different characteristics

Criteria across different characteristics narrow the result together: characteristic X AND characteristic Y.

Result layout

CL30N can be adjusted for practical object search. Class-specific and user-specific layouts help expose the characteristics that matter to the user.

search

Example: an engineer needs an existing component with MATERIAL = STAINLESS STEEL, DIAMETER = 20 mm and VOLTAGE = 24 V. Classification can find suitable materials without knowing the material number first, helping reduce duplicate master-data creation.

Class hierarchies

Use hierarchy for reusable structure, not for arbitrary folders.

Classes can be arranged in hierarchical structures. Characteristics assigned higher in the hierarchy can be inherited by subordinate classes, which helps avoid repeating the same definitions in every class.

Good use

A parent class defines attributes common to all industrial motors, while child classes add attributes for AC and DC motor families.

Risk

A very deep hierarchy becomes hard to govern. Before adding another level, ask whether the distinction belongs in class structure, a characteristic value, product hierarchy, or another master-data object.

Material Classification

Use class type 001 when materials need searchable reusable attributes.

Material classification is useful when the normal product description is not enough for search, engineering reuse, reporting, integration mapping, or business grouping.

Engineering search

Find an existing material for a BOM by dimensions, material grade, voltage, pressure class or another technical property.

Commercial grouping

Expose attributes used for catalogue navigation, product selection or downstream analytics without creating dedicated fields for every property.

Integration mapping

Send controlled attributes to PLM, PIM, commerce, warehouse or external product services where Classification is part of the agreed data contract.

Batch Classification

A batch is often selected by what it contains, not only by its batch number.

Batch characteristics can hold values such as potency, country of origin, production date, quality grade, concentration or other lot-specific properties. Batch determination can then use those values as selection criteria.

01

Create batch characteristics

Define the lot attributes and controlled values.

02

Build the batch class

Use the batch class type relevant to the configured batch level, commonly 023 or 022.

03

Classify the material and/or batch

Maintain values at the correct object level. Class type 023 supports a material-to-batch object hierarchy.

04

Consume in determination

A batch search strategy can use characteristic values to identify batches that satisfy the business requirement.

science

Important: batch classification and batch determination are different layers. Classification stores the attributes. The batch determination strategy decides which attributes are used for selection and how candidate batches are sorted.

Variant Configuration

Class type 300 turns characteristics into selectable product options.

In Variant Configuration, the class is not only used for search. It becomes part of the configuration model. A configurable material is linked to a variant class, and the characteristics describe the options available during configuration.

Classification view

A characteristic is simply an attribute of an object.

Variant Configuration view

The same characteristic concept participates in configuration logic, dependencies and product structure.

Lead implication

Do not change a shared characteristic casually. A seemingly harmless value change can affect sales configuration, BOM selection, pricing dependencies or production planning.

Purchasing Release Strategy

Classification can select an approval strategy.

In the classic release procedure with classification, purchasing document values are passed to the Classification system. If they match the characteristic conditions of a release strategy, SAP assigns that strategy.

01

Communication structure

Relevant purchasing document fields are exposed to the release-classification model.

02

Characteristics

Characteristics represent fields such as document value, purchasing group, plant or other supported release criteria.

03

Class

The release class groups the characteristics, typically in class type 032.

04

Strategy values

Each release strategy carries the characteristic values or ranges that define when it should be selected.

05

Runtime determination

When the document is created or changed, SAP compares its values with the strategy conditions and determines the matching release strategy.

approval

Diagnostic point: if the wrong strategy is selected, do not start with workflow. First prove the document values, characteristic mapping and classification values that determine the strategy. Workflow processes the approval after strategy determination.

Integration

Classification is master data with its own replication dependencies.

When classes and characteristic values are consumed outside the originating system, transport or master-data replication must include the whole dependency chain.

ObjectCommon ALE message typeWhat to verify
CharacteristicsCHRMASThe characteristic definition exists before dependent classifications are consumed.
ClassesCLSMASClass type, class and assigned characteristics are aligned between systems.
Object classificationCLFMASThe target object exists and the class assignment / valuation is replicated consistently.
sync_alt

Integration rule: sending only an object value is not enough if the receiving system does not have the same characteristic and class semantics. Treat characteristic definition, class structure and object valuation as one dependency chain.

Runtime use

Trace the value from definition to consumer.

When a result is wrong, prove each link in order instead of changing global classification master data immediately.

01

Class type

Is the object classified in the correct class type?

02

Characteristic

Is the characteristic definition correct: type, units, values and restrictions?

03

Class

Is the characteristic actually assigned to the class used by this object?

04

Object assignment

Is the exact material, batch, equipment or document assigned to the expected class?

05

Valuation

Does the object carry the expected value, including units and multiple-value behavior?

06

Consumer

Does the search, batch strategy, release logic, configuration model or interface read that exact characteristic?

Design decisions

Use Classification when the attribute should be reusable and searchable.

Good fit

Many objects need the same attribute model, users search by those attributes, or several applications consume the values.

Questionable fit

A value is really a transactional result, a one-off note, or a dedicated standard field already owns the meaning.

Governance need

Define ownership, naming, value catalogue, units, reuse rules and change impact. Classification can become a second uncontrolled data dictionary if every team creates its own characteristics.

Assessment

Answer from model to runtime.

A Lead-level answer should explain both what Classification stores and how another logistics process consumes it.

record_voice_over

Assessment answer: “SAP Classification is a cross-application attribute model. I define characteristics in CT04, group them in a class of the correct class type, assign the class to an object, and maintain valuations. Then a consumer such as object search, batch determination, Variant Configuration or a purchasing release strategy uses those values. For troubleshooting I trace class type → characteristic → class → object assignment → valuation → consuming logic.”
