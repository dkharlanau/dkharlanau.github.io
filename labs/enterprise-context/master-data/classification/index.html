SAP S/4HANA / Logistics / Classification

Classification turns attributes into a reusable logistics language.

SAP Classification is a cross-application framework. We define characteristics, group them in classes, assign business objects, and maintain values. Search and logistics processes can then use the same structured description instead of relying on material numbers or free text.

Variant Configuration reuses classification concepts, but adds configuration-specific rules, dependencies, and a runtime configuration instance. Mental model

Five layers are enough to reason through most Classification questions.

The important point is not the transaction. It is the chain from reusable attribute definition to the process that consumes the values.

01

Characteristic

A reusable attribute definition such as color, voltage, viscosity, length, or a purchasing document property. It controls data type, units, allowed values, intervals, and other value rules.

02

Class

A class groups related characteristics. Instead of adding attributes directly to every object, we define the reusable description once and assign objects to the class.

03

Class type

The class type connects Classification to an object type or business function. A material class and a batch class can use different rules even when some characteristics have the same names.

04

Object assignment

The material, batch, equipment, document, or another supported object is assigned to the appropriate class. Multiple classification is possible where the class-type settings allow it.

05

Values and consumption

Characteristic values describe the concrete object. Users can search by them, and other processes can use them as selection or determination inputs.

Core capabilities

Classification separates the attribute model from the object that carries the values.

This is why the framework can be reused across different logistics domains instead of creating one custom field model for every process.

Capability What it controls Why it matters in logistics
Characteristic definition Data type, unit, allowed values, intervals, defaults, and other value rules. Creates a controlled vocabulary instead of uncontrolled free-text attributes.
Class definition A reusable set of characteristics for one classification purpose. Keeps common attributes consistent across many materials, batches, or technical objects.
Class type The object category and special behavior supported by the class. Prevents us from treating all classification use cases as one generic material-master extension.
Object classification Assignment of an object to a class plus the object's characteristic values. Makes the object searchable and provides structured data for downstream selection logic.
Class hierarchy Superior and subordinate classes; supported class types can inherit characteristics from higher levels. Useful when a large catalog needs broad families and more specific subgroups without repeating every characteristic.
Multiple classification An object can belong to several classes where the class-type settings permit it. Provides different search paths, but values inside one class type still belong to the object rather than to an individual class assignment.
Object search Find objects from characteristic values instead of exact object numbers. Supports material reuse, engineering search, maintenance search, and other high-volume master-data scenarios.

Remember the class type because it tells you what is being classified.

Where logistics uses it

The classification value becomes useful only when another process consumes it.

A Lead should name both layers: the classification data and the runtime mechanism that uses it.

Material search and reuse

When an engineer or planner knows the required properties but not the material number, Classification can find existing materials by characteristic values. This reduces duplicate master data and helps reuse an existing component in a BOM.

Batch determination

Batch characteristics can describe properties such as quality or process attributes. Batch determination can use classification-based selection criteria, while availability, strategy configuration, and stock status still decide whether a batch can actually be selected.

Purchasing release strategy

In the classic classification-based release procedure, purchasing document values are transferred into characteristics and matched against the release-class conditions. Classification helps identify the strategy; release configuration owns the approval sequence and status behavior.

Variant Configuration

Variant Configuration uses classes and characteristics to describe configurable products. It then adds configuration-specific rules, dependencies, and a runtime configuration instance that can influence BOM, routing, pricing, procurement, and production.

Technical objects and documents

Equipment, functional locations, work centers, and documents can be classified in supported scenarios. The value is the same: structured search and grouping without changing the core identity of the object.

Batch example

Classification can define eligibility, but it does not replace stock or determination logic.

Suppose a material has batches with a characteristic for viscosity. The material-level classification can restrict the allowed range for its batches. A delivery requirement may then search for a batch inside a required value range.

01

Material and class type

Confirm that the material is assigned to the expected batch class and that the architecture uses the expected batch classification level.

02

Characteristic definition

Check the data type, unit, allowed values, intervals, and any material-level restriction.

03

Batch value

Verify the value stored for the actual batch. A batch cannot match a selection characteristic that is missing or inconsistent.

04

Selection strategy

Confirm that batch determination is using the expected classification criteria and search strategy.

05

Execution evidence

Only then check available stock, batch status, shelf-life or quality restrictions, and the execution layer that performs the final selection.

Diagnostic sequence

Do not change the characteristic until you know which layer is wrong.

Most incidents can be narrowed by proving five facts in order.

01Scope

Which object and class type are actually involved?

Evidence

Object key, class type, assigned class, and deployment model. This prevents debugging a material class when the runtime process is reading a batch or variant class.

02Definition

Is the characteristic itself correct?

Evidence

Data type, unit, allowed values, interval settings, restrictions, and validity. A wrong model can make every object value look wrong.

03Structure

Does the class contain the expected characteristic?

Evidence

Direct assignment, inherited characteristic, class hierarchy, and any class-level restrictions or overwrites.

04Object

Is the object assigned and valued correctly?

Evidence

Class assignment, classification status, and characteristic values on the concrete material, batch, document, or technical object.

05Consumer

Which process consumes the value, and what other rules does it apply?

Evidence

Object search, batch strategy, release procedure, Variant Configuration, or another consuming mechanism. If Classification is correct, move downstream instead of changing shared master data.

Lead-level design questions

Classification is powerful because it is shared. That also increases its blast radius.

Reuse or create?

Before creating a new characteristic, check whether an existing one already represents the same business meaning. Duplicate characteristics create inconsistent search, migration, integration, and reporting behavior.

Where should the rule live?

Keep descriptive truth in Classification. Keep process decisions in the owning mechanism. Do not encode a purchasing, batch, or configuration rule into characteristic values simply because Classification is flexible.

Who owns value quality?

Define who creates the characteristic, who approves class changes, who maintains object values, and which downstream processes depend on them. Shared classification data needs explicit governance.

Assessment recall

Characteristic → Class → Class type → Object → Value → Consumer.

record_voice_over

60-second answer: “SAP Classification is a cross-application framework for describing and finding business objects with structured characteristics. I define a characteristic, group characteristics in a class, use the correct class type for the object or business function, assign the object, and maintain its values. Logistics processes can then consume those values for material search, batch selection, purchasing release strategy, or Variant Configuration. In diagnosis I first prove the class type, assignment, and actual characteristic value, and only then move to the consuming process. Classification describes the object; the downstream mechanism makes the business decision.”
