Material Listing / Exclusion

Listing and exclusion control whether a customer is allowed to order a product. A listing is restrictive in a positive way: only listed products are allowed for the relevant context. An exclusion blocks specific products. Both act before downstream fulfillment can proceed normally.

Object profile

01MD.SD.LISTEXCLCatalogue ID
02condition recordData class
Listing/exclusion type, customer/partner context, product and validity.

Mental model

This is an eligibility gate, not a product attribute.

database

Scope: Listing/exclusion type, customer/partner context, product and validity.

Important data

Listing or exclusion condition type, key combination, customer or partner fields, material/product and validity dates.

Configuration boundary

The condition record contains the allowed or blocked relationship. The procedure and access sequence that search those records are configuration.

Lead decision

Choose whether the policy is “allow these” or “block these”.

Listing and exclusion express opposite governance models. The design should match how the business wants new customer-product combinations to behave by default.

Listing

Use a positive eligibility model when only maintained combinations should be allowed. It gives tighter control but requires complete maintenance.

Exclusion

Use a negative eligibility model when combinations are normally allowed and only known exceptions should be blocked.

Trade-off

Listing reduces unintended sales but can stop new valid combinations if governance is slow. Exclusion is easier to scale but depends on exceptions being identified and maintained on time.

Lead check: ask what should happen to a new customer-product combination when no record exists.

Runtime use

The check asks whether this customer may buy this product in this context.

During order entry the configured procedure controls which listing or exclusion rules are evaluated. Exclusion is a negative rule: a matching record can block the product. Listing is a positive rule: the product must belong to the allowed set for the relevant key and validity.

01

Name the gate

Establish whether the business uses listing, exclusion, or both. They answer opposite eligibility questions.

02

Follow the active procedure

Confirm which condition types and accesses are evaluated for this Sales context instead of searching every maintained record.

03

Build the runtime key

Use the actual customer or partner context, product, date, and configured key fields. A record for a different key or validity does not control this item.

04

Prove the eligibility result

For exclusion, prove the blocking match. For listing, prove whether an allowed match exists. Then explain the order reaction from that result.

Troubleshooting

Separate “no rule”, “wrong key”, and “wrong eligibility result”.

troubleshoot

If a product is unexpectedly blocked, first prove which procedure and condition type executed. Then inspect the exact runtime key and validity. If the expected record exists but SAP never reaches its key, diagnose procedure or access logic; if the key is reached but the record does not qualify, diagnose the master record. Do not change the product master to repair an eligibility rule.

Assessment recall

Explain the positive and negative gate.

record_voice_over

60-second answer: Listing and exclusion control customer-product eligibility. Listing is a positive list: the product must be allowed for the relevant context. Exclusion is a negative list: a matching rule blocks the product. I diagnose the active procedure first, then the runtime key and validity, then the actual record found or missed. That keeps an order rejection in the eligibility mechanism instead of turning it into an unrelated product-master change.
