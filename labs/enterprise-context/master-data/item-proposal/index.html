Sales Item Proposal

An Item Proposal is a reusable basket for Sales order entry. It works well when a customer repeatedly buys the same group of products and the order desk should not type the same materials every time. The important design question is not only how to create one in VA51, but whether the business needs a fixed basket, a dynamic proposal, or a different mechanism completely.

Think of it as controlled order-entry assistance, not as pricing, ATP, substitution, or entitlement logic.

Mental model

A saved basket and a recommendation engine are two different designs.

SAP uses similar language around Item Proposal and Product Proposal, but there are two useful mental models. A classic Item Proposal is an explicit list maintained as a Sales document. Dynamic Product Proposal can build a customer-specific list from several sources such as order history, listing, exclusion, item proposals and customer-material information.

Static Item Proposal

A person maintains the basket. The proposal contains products and optional quantities. It is stable, simple to explain, easy to audit, and useful when repeat orders are predictable.

Dynamic Product Proposal

The system determines candidate products through a procedure and access sequence. It is better when the proposal should react to order history, assortment rules, exclusions, or several customer-specific sources.

rule

Lead rule: do not build dynamic logic just because it is available. If a customer orders the same 12 products every week, a controlled static proposal may be easier to own than a complex determination procedure. If the basket changes with history, assortment or commercial rules, static maintenance becomes the wrong tool.

Where it fits

Use it where repetitive entry is the real problem.

Good fit

Inside Sales, telephone orders, repeat wholesale orders, regular replenishment baskets, opening-order packs, and customer-specific product sets where users still control the final order.

Poor fit

Automated inbound orders, hard product-substitution rules, mandatory assortment restrictions, complex recommendations, or scenarios where another system already sends the final order items.

lightbulb

Project lesson: an Item Proposal saves keystrokes, but it also creates master-data ownership. Someone must decide who owns the basket, when it expires, how obsolete products are removed, and whether quantities are still meaningful. Without ownership, proposal lists slowly turn into historical clutter.

Classic setup

The static proposal is a special Sales document.

In classic SD, the proposal is created through the Sales document framework. Many standard systems use an Item Proposal document type such as MS; customer systems may copy or rename it. The important control is the Sales document category D — Item Proposal, not the literal document-type key.

01

Define the proposal document type

Review the Item Proposal document type in VOV8. A typical proposal type has document category D and no normal delivery or billing follow-on because the proposal is an entry object, not an order to fulfil.

02

Allow it for the Sales area

If your design restricts document types by Sales area, maintain the assignment in OVAZ. Do not diagnose VA51 first if the document type itself is not allowed for the Sales organization, distribution channel and division.

03

Create the basket

Use VA51, enter Item Proposal Type and Sales area, then maintain materials and proposed quantities. A description can be used as a search term. The system assigns a proposal number when you save.

04

Assign it to the customer

Maintain the proposal in the customer Sales-area data. In S/4HANA this is normally handled through Business Partner customer role FLCU01; classic systems may use XD02/VD02. The technical customer field is KNVV-VSORT.

05

Use it during order entry

In VA01, use Propose Items. The user can copy the whole list with quantities, without quantities, or use a selection list and choose only the required lines.

Runtime

The proposal explains how an item entered the order. It does not own the item afterwards.

This boundary is useful in production support. A proposal can put a material and quantity in front of the user, but it does not decide the final item category, price, confirmed date, plant, route, delivery block, billing relevance, or account determination.

01

Resolve the customer context

Start with sold-to party and Sales area. For a static proposal, check whether the expected proposal is assigned to that exact customer Sales-area segment.

02

Present proposal lines

The user sees candidate materials and, where maintained, proposed quantities. A static proposal can also be called manually by proposal number.

03

Convert a proposal line into an order item

When the user copies or enters quantity for a proposed material, SAP creates a normal Sales document item. From here the usual Sales logic starts to matter.

04

Hand off to normal SD determination

Item-category determination, pricing, ATP/aATP, plant determination, shipping, schedule lines, delivery and billing are diagnosed from their own configuration and master data.

sync_alt

Useful diagnostic split: “the product was not proposed” is an Item/Product Proposal problem. “the product was proposed but has the wrong price or confirmation” is normally no longer an Item Proposal problem.

Dynamic Product Proposal

Dynamic proposal is procedure-driven and can combine several sources.

The dynamic framework is useful when a single saved basket is too rigid. SAP can build the proposal from several source types and define the order in which those sources are evaluated.

Customer procedure

The customer Sales-area data can hold the Product Proposal customer procedure. The technical field is KNVV-PVKSM. This is not the same field as the static Item Proposal assignment in KNVV-VSORT.

Document procedure

The Sales document type can contribute a document procedure. Together with the customer procedure, this helps determine which Product Proposal procedure is used during online processing.

01

Define customer procedure

Classify the customer for Product Proposal processing.

02

Define document procedure

Classify the Sales document type so different order types can use different proposal behavior.

03

Maintain sources

Typical sources include order history, listed materials, excluded materials, Item Proposal and Customer-Material Info Records. Customer-specific sources can also be added.

04

Build the procedure and access sequence

Control which sources are called, in which sequence, and how their results are combined.

05

Choose online or background access

For several or expensive sources, background generation can reduce online load. Online determination is useful where fresh context matters more than precomputation.

speed

Performance decision: if the proposal reads multiple sources for many customers, moving expensive work to background generation is not only a technical tuning step. It is an architecture choice between freshness and order-entry response time.

Procedure determination

The DPP procedure is selected from business context, not from the customer alone.

The customer procedure and document procedure are only part of the key. Procedure determination can also use the Sales organization, distribution channel, division, Sales office and Sales group. This gives the design a useful level of control: the same sold-to party can receive different proposal behavior in another channel, order type or Sales organization.

01

Customer procedure

Read KNVV-PVKSM from the customer Sales-area data. This classifies the customer for Dynamic Product Proposal.

02

Document procedure

Read the Product Proposal document procedure assigned to the Sales document type. An order and a quotation do not have to behave in the same way.

03

Organizational context

Sales area is the main context, with Sales office and Sales group available for more specific determination where the business needs it.

04

Resolve the DPP procedure

The matching determination entry points to the Product Proposal procedure that contains the actual accesses and source-processing logic.

account_tree

Support shortcut: if DPP works for one customer or order type but not another, compare the complete procedure-determination key before debugging the source functions. Many “missing proposal” incidents are determination mismatches rather than missing history.

Access sequence internals

Think of the access sequence as a proposal pipeline.

Each access says where SAP should get candidate products and which function should process that source. The sequence matters because the same material can be found more than once. SAP keeps the proposal result coherent and the displayed source reflects the first source that determined the material according to the configured access sequence.

Order history

SD_DPP_HISTORY
Reads prepared purchasing history and proposes products the customer bought before. A common design is to limit the history horizon so very old purchases do not dominate current behavior.

Static Item Proposal

SD_DPP_PRODUCT_PROPOSAL
Pulls materials from maintained Item Proposal documents and makes the controlled basket one source inside the dynamic framework.

Customer-Material Info

SD_DPP_CUSTOMER_MATERIAL_INFO
Uses customer-specific material relationships as proposal candidates.

Listing

SD_DPP_LISTING
Adds products allowed by listing logic. This can be useful when the commercial assortment itself should feed the proposal.

Exclusion

SD_DPP_EXCLUSION
Removes or identifies products excluded for the customer. Treat this as assortment control, not as a VA51 basket.

Cross-selling / read layer

SD_DPP_CROSS_SELLING and SD_DPP_READ are additional standard building blocks. Their presence is a reminder that DPP can orchestrate several existing Sales mechanisms rather than owning every source itself.

manage_search

Diagnostic habit: inspect the proposal line's Source before opening configuration. If a material exists in both order history and listing, the source shown is driven by access order. That immediately tells you which branch of the pipeline to investigate first.

History generation

Order-history DPP is prepared data, not a live scan of every old order.

For history-based proposals, background processing can generate and persist Product Proposal data in VBPK and VBPV. Transaction SDPV and report SDPVGEN are the operational tools typically used to generate this data and schedule recurring refreshes.

01

Define the background procedure

Decide which history/source accesses should be calculated outside VA01 and which selection logic controls the result.

02

Generate proposal data

Run SDPV or schedule SDPVGEN with a controlled variant. The accesses execute and their result is stored for later online use.

03

Store history result

VBPK contains header-level Product Proposal data; VBPV contains the material and quantity-level result used by the proposal framework.

04

Read fast during order entry

VA01 can consume the prepared result instead of performing every expensive history read while the user is waiting.

schedule

Operational consequence: background DPP introduces data freshness as an explicit SLA. When users say “the proposal is wrong,” check the generation timestamp and job variant before changing customizing. The logic may be correct while the stored proposal is simply stale.

Important runtime nuance

A dynamic proposal line is not yet a fully processed Sales item.

For Dynamic Product Proposal, SAP can display proposal rows before standard item-level processing is executed. Pricing, availability, incompletion and similar checks are triggered when an order quantity is entered and the material becomes a real document item with an item number.

fact_check

This explains a common test result: a product may be visible in the proposal with historical quantity information, but it does not yet have the same calculated state as a normal order item. Do not compare proposal-row behavior with a completed VBAP item too early.

BOM behavior

The proposal can hold a BOM header, but VA51 is not where the BOM is exploded.

SAP allows a BOM or configurable header material to be included in an Item Proposal. The explosion or configuration happens when the material is copied into the Sales order. The determined Sales item category must allow the required structure processing.

account_tree

Practical check: if a user says “the BOM does not explode in VA51,” that is normally expected. Test the transfer into the actual Sales order and then inspect item-category structure scope and configuration behavior.

Technical anchors

Know which object you are actually debugging.

Classic static proposal

VBAK — Sales document header for the Item Proposal.
VBAP — proposal items/materials.
KNVV-VSORT — Item Proposal assigned to the customer Sales area.

Dynamic Product Proposal

KNVV-PVKSM — customer procedure for Product Proposal.
VBPK — Product Proposal header/result data.
VBPV — Product Proposal material/quantity data.

warning

Do not use VAKH/VAKP as Item Proposal database tables. Static Item Proposals are Sales documents and are anchored in VBAK/VBAP. VAKP is also the name of an SAP transaction used for T180 configuration, which makes this naming mistake easy to repeat.

Integration boundary

Do not assume UI proposal logic will run for inbound automation.

The classic Dynamic Product Proposal framework has important execution constraints. SAP documents that Product Proposal is not generated in several technical creation paths, including batch input, incoming IDocs, BAPIs, change/display processing and creation with reference.

hub

Architecture consequence: if EDI, API or middleware already creates Sales orders automatically, do not design the business requirement around a VA01 entry aid without proving the exact runtime path. For interfaces, the safer contract is usually explicit order items or a separately designed proposal/enrichment service.

Intelligent Product Proposal

S/4HANA can extend the dynamic framework with quantity prediction and API access.

Intelligent Product Proposal builds on Dynamic Product Proposal. SAP supports predictive quantity logic such as exponential smoothing and provides the OData service API_INTELLIGENTPRODUCTPROPOSAL_SRV for reading generated product and quantity proposals.

analytics

Lead question: before enabling “intelligence,” define the decision it improves. If users only need a stable repeat-order basket, prediction adds complexity without solving a real problem. If quantities change over time and order history is meaningful, the intelligent layer becomes more relevant.

Troubleshooting

Start with the symptom, then move to the owning layer.

Proposal number is not offered

Check the sold-to party, Sales area, KNVV-VSORT, proposal validity and whether the Item Proposal document exists in the expected Sales area.

Dynamic list is empty

Check customer procedure, document procedure, online/background procedure determination, source access sequence and whether the selected source has usable data.

Wrong products are proposed

Identify the source indicator first. Then inspect source priority, listing/exclusion, order-history window, explicit Item Proposal content and customer-material data.

Quantities look old

Separate static maintained quantity from background-generated history quantity. If background processing is used, check when the proposal data was last generated.

Product appears but price/ATP is missing

For dynamic proposals this can be expected before an order quantity is entered. Standard checks start when the proposal row becomes a real order item.

Works in VA01, fails through interface

Verify the creation channel. Classic Product Proposal has execution limits for IDoc/BAPI and other non-interactive paths.

Decision guide

Pick the mechanism that owns the business rule.

Item Proposal

“This customer often buys this basket.” Use it for fast, user-controlled entry of a known set.

Dynamic Product Proposal

“Build a relevant basket from several customer-specific sources.” Use it when the list should change with history or assortment context.

Cross-Selling

“When this product is entered, suggest another product.” The trigger is the product, not simply the customer basket.

Material Determination

“Replace or substitute the requested material according to a rule.” This is substitution logic, not order-entry convenience.

Customer-Material Info Record

“This customer uses a different product number or customer-specific material data.” It maps the relationship; it is not a reusable basket.

Listing / Exclusion

“This customer may or may not buy this material.” It controls eligibility rather than simply proposing a convenient list.

Lead-level design checks

Before configuration, answer the operating questions.

01

Who owns the basket?

Sales operations, key-account team, product team, or automated generation? Ownership matters more than the transaction used to maintain it.

02

How often does it change?

Stable for months suggests static maintenance. Changing every order suggests a dynamic source or another recommendation design.

03

Are quantities meaningful?

Copying stale quantities can be worse than copying no quantities. Decide whether the business wants a product reminder or a true repeat-order template.

04

Which channel consumes it?

VA01, Fiori, Interaction Center, EDI, API, mobile sales, or another application can have different runtime support. Prove the channel before finalizing the design.

05

How will we remove old data?

Define review, validity and retirement rules. A proposal that nobody cleans becomes a source of wrong products and user distrust.

Assessment recall

Explain the difference between entry assistance and determination.

record_voice_over

90-second answer: An Item Proposal is a reusable list of materials and optional quantities used to speed up Sales document entry. In the classic setup I create it in VA51 as a Sales document with category D and can assign it to the customer Sales-area data through KNVV-VSORT. In VA01 the user can copy all items with quantities, without quantities, or select individual lines. I keep it separate from Dynamic Product Proposal: DPP uses customer and document procedures plus an access sequence to combine sources such as order history, listing, exclusion, Item Proposal and Customer-Material Info. Another key point is ownership: once a proposal line becomes a real Sales item, normal item-category, pricing, ATP, delivery and billing logic take over. So in support I first decide whether the failure is in proposing the item or in processing the resulting Sales item.

Strong follow-up

If asked about tables, name VBAK/VBAP for the static proposal, KNVV-VSORT for customer assignment, KNVV-PVKSM for the dynamic customer procedure, and VBPK/VBPV for Product Proposal data.

Strong architecture point

If the process is automated through IDoc/API, verify support before reusing UI proposal logic. An entry aid for a human order taker is not automatically an integration rule.
