Pricing Condition Record

A pricing condition record is the maintained commercial value that pricing searches for. Price, discount, surcharge, freight or another condition can be stored against a specific key combination such as customer/material or price list/product hierarchy.

Follow the runtime path arrow_downward

Object profile

01MD.SD.PRICECatalogue ID
02condition recordData class
Condition type, condition table/key combination, validity, currency/unit and scales.

Mental model

The record owns the commercial value; the pricing engine owns the search.

database

Scope: Condition type, condition table/key combination, validity, currency/unit and scales.

Important data

Condition type, key fields, amount or percentage, currency, pricing unit, valid-from/to dates, scales and condition-specific control data.

Configuration boundary

Condition type, access sequence and pricing procedure are configuration. The condition record is master data. This distinction is central when troubleshooting pricing.

Lead decision

Choose the smallest commercial key the business can govern reliably.

Every extra key field can make a price more precise. It also creates more records, more overlap risk, and more effort to explain why one value was selected.

Specificity

Add a dimension when it changes the commercial meaning of the price or discount and the business can maintain it consistently.

Fallback

Design the search path so a missing specific record has an intentional result. A fallback should be a policy, not an accidental side effect.

Time

Validity is part of the commercial rule. Overlapping or stale periods can produce a technically valid value that is commercially wrong.

Trade-off: precision versus maintainability and explainability. The best key is not automatically the key with the most fields.

Runtime use

A condition record is reached only after several pricing decisions are already correct.

The document first uses a pricing procedure. The expected condition type must participate, and its access sequence must reach a condition table whose runtime key matches the document. Only then can a valid condition record supply a rate, amount, scale, currency, unit, or other maintained commercial value.

01

Prove the procedure

Confirm the pricing procedure used by the actual document before checking condition records.

02

Find the condition

Check whether the expected condition type is present, relevant, and allowed to participate.

03

Follow the access

Read the access sequence and the runtime key values used for each condition table.

04

Validate the record

Check key fields, validity, amount or percentage, currency, unit, pricing unit, and scales for the record SAP actually found or failed to find.

05

Continue into calculation

If the record is found but the final amount is wrong, move beyond master data into base value, formulas, exclusions, grouping, and other pricing interactions.

Troubleshooting

“The record exists” is not a pricing diagnosis.

troubleshoot

Start from pricing analysis and identify the condition type, access attempted, and actual runtime key. If SAP never reaches the expected key, the record is not the root cause. If the key is reached, validate the record's validity, currency, unit, pricing unit, scale, and value. If the record is found correctly, continue into calculation rather than creating another record.

Assessment recall

Separate search logic from maintained value.

record_voice_over

60-second answer: A pricing condition record is master data that contains a commercial value for a defined key and validity. It does not decide how SAP searches. I first prove the pricing procedure and condition type, then follow the access sequence with the actual runtime key. Only when SAP reaches that key do I validate the record, currency, unit, scale, and validity. If the record is found but the amount is still wrong, I move into pricing calculation rather than duplicating master data.
