Pricing Condition Record

A condition record is where the commercial number lives. It may store a price, discount, surcharge, freight value, tax-related rate or another pricing value for a defined key and validity period. It does not decide whether SAP will search for that value.

Trace the pricing path arrow_downward

Lead mental model

01recordcommercial data
02accesssearch logic
03price elementdocument result
Do not debug all three layers as if they were the same object.

Mental model

The record stores a commercial value. Configuration decides if SAP reaches it.

This distinction is the fastest way to avoid weak pricing diagnosis. A valid record can exist in the database and still be irrelevant to the current document.

Master data

The condition record contains the maintained value and its business scope: condition type, key combination, validity, amount or percentage, currency, pricing unit, unit of measure, scales and supported condition-specific data.

Configuration

Condition table, access sequence, condition type, pricing procedure, requirements, formulas and procedure determination decide how SAP searches and calculates.

Runtime result

The sales or billing document contains the price elements produced by pricing. A manual document condition is a document result or override; it is not automatically a change to the master condition record.

database

Useful question: “Is the problem in the maintained value, in the search path, or in the calculation after the value was found?” This question normally removes a large part of the search space.

Record anatomy

Most production pricing errors are not caused by the numeric rate alone.

The same number can be correct or wrong depending on the key, date, currency, unit and scale context.

Record element What it controls Typical failure signal
Condition type Business meaning of the value: price, discount, surcharge, freight or another pricing element. The right number is maintained under a condition type that is not used by the active pricing procedure.
Condition table / key The dimensions that make the record specific, for example Sales Org + Distribution Channel + Customer + Material. The record exists, but the runtime access uses a different customer, material, hierarchy, price list or sales-area value.
Validity The time window in which the record may be selected. A price works yesterday or next month but not on the document pricing date.
Amount / percentage The maintained commercial rate. The expected record is found, but the commercial value itself is wrong.
Currency The currency in which an amount is interpreted. The amount looks numerically correct but converts or compares incorrectly in the document currency.
Pricing unit and UoM Defines whether the rate means, for example, EUR 10 per 1 EA or EUR 10 per 100 EA. The price is wrong by a clean factor such as 10, 100 or 1,000.
Scales Changes the rate when quantity, value, weight, volume or another configured scale basis crosses a threshold. The price changes only when the order quantity or value reaches a specific level.
Release / approval status Where supported, controls whether the record is usable for productive pricing. The record is visible in maintenance but is blocked, in review or rejected and therefore not usable in normal pricing.

Lead decision

Choose the smallest pricing key the business can govern reliably.

More fields make a record more specific, but they also multiply master-data volume, overlap risk, testing effort and the number of explanations needed when a price is wrong.

Specificity

Add a dimension only when it changes the commercial meaning. “We might need it later” is usually not enough reason to create another pricing dimension.

Fallback

Design the access sequence so a missing specific record has an intentional result. A generic fallback should be a commercial policy, not an accidental side effect.

Governance

Every key field needs a stable source and an owner. A pricing key is weak when one of its dimensions is populated inconsistently or has no clear maintenance process.

Example

Access 10 may search Customer + Material, access 20 Customer Group + Material, and access 30 Material only. The sequence expresses business priority. The record itself does not.

Lead check

Before adding a new key combination, estimate record volume and ask who will maintain it during price changes, annual renewals, acquisitions, product launches and customer reorganizations.

Runtime use

A condition record is reached only after several earlier decisions are already correct.

Debug pricing in the same order in which SAP builds the answer. Starting directly in VK13 or a condition table often proves only that some record exists, not that the document can use it.

01

Prove the pricing procedure

Confirm which pricing procedure the actual document uses. In classic SD, the determination combines sales area, document pricing procedure and customer pricing procedure.

02

Find the expected condition type

Check that the condition type is present in the procedure and that requirements or other controls do not make it irrelevant.

03

Read the access sequence

Follow the accesses in order. Check which condition table each access uses and whether the access was executed or skipped.

04

Compare the runtime key

Use the document values SAP actually used: customer, material, sales area, hierarchy node, price list, customer group or other fields in the key.

05

Validate the record

Check validity, release status, amount, currency, pricing unit, UoM, scales and any condition-specific fields.

06

Continue into calculation

If the correct record was found, move to base value, calculation type, formulas, exclusion, group logic, subtotals, manual changes and repricing behavior.

fork_right

Important nuance: “The access sequence always stops at the first hit” is too simple. An access can be marked as exclusive, which controls whether the search stops after a successful access. Always read the actual access configuration before assuming first-hit behavior.

Validity and lifecycle

Time is part of the pricing rule, not just record housekeeping.

A pricing record is only meaningful together with the pricing date used by the document and the way overlapping validity periods are maintained.

Pricing date

Do not assume the system is checking “today”. Diagnose the pricing date in the actual document and the relevant pricing logic. Different business scenarios can use different date sources.

Overlaps

When a new record overlaps an existing record with the same pricing key, maintenance tools can delimit, split or replace existing validity periods depending on the function used. Treat overlap handling as a data-change event, not only as a warning.

Retirement

When audit history matters, prefer controlled validity delimitation instead of deleting historical pricing data. Use the correct last-valid date rather than blindly setting every old record to “today”.

approval

Approval-aware maintenance: in deployments that use sales price approval workflows, blocked or in-review prices cannot be used in normal pricing. Not every condition record participates in this workflow, so confirm whether release status is supported for the condition record in question.

Scales, units and calculation

A condition record can hold more than one simple rate.

When pricing becomes wrong only at certain quantities or values, scales and units become higher-probability suspects than the access sequence.

Scale basis

Scales can be based on quantity, value, weight, volume or other supported bases. The threshold logic belongs to the condition record and condition design together.

Calculation type

The condition type defines whether SAP interprets a rate as an amount, percentage, quantity-based value or another calculation form. The record supplies the maintained value for that rule.

Pricing unit

Always read amount + pricing unit + UoM together. “100 EUR” is incomplete information when the record actually means “100 EUR per 100 pieces”.

Diagnostic pattern: if the result is wrong by a stable factor, check pricing unit and unit conversion before changing the condition amount.

Maintenance surfaces

Know the classic transactions, but design for the deployment you actually run.

On-premise, Private Cloud and Public Cloud can expose different maintenance paths. A Lead answer should separate durable pricing concepts from a specific GUI transaction.

Tool / transaction Purpose Practical note
VK11 / VK12 / VK13 Create / change / display sales condition records in classic SD. Useful references for on-premise and Private Cloud landscapes where the classic transactions are available.
Set Material Prices – Sales Maintain material price condition records one by one. Used in SAP S/4HANA Cloud. The app ID can be VK12; do not confuse that app ID with availability of the classic GUI transaction.
Set Service Prices – Sales Maintain service price condition records. Separate maintenance surface for service pricing in supported Cloud scenarios.
Set Tax Rates – Sales Maintain sales tax rates. Keep tax-rate maintenance separate from general commercial price maintenance.
F4111 — Manage Prices – Sales Search, create, edit, copy, import and mass-maintain multiple condition records. Strong operational choice when the business needs list-based maintenance, import, reference-based creation or approval-aware price management.
V/03 Create condition tables in classic Customizing. Configuration, not master-data maintenance. Change/display transactions are separate.
V/06 Define condition types. Controls pricing behavior such as calculation type and manual/automatic characteristics.
V/07 Define access sequences. Search order, tables, requirements and exclusive behavior belong here.
V/08 Maintain pricing procedures. Controls sequence, requirements, subtotals, account keys and other procedure-level behavior.
OVKK Classic pricing procedure determination. Connects sales area, document pricing procedure and customer pricing procedure to a pricing procedure.
V/LD Execute pricing reports. Useful for controlled listing and analysis of condition master data in classic environments.
API_SLSPRICINGCONDITIONRECORD_SRV Create, read, update and delete pricing condition records through a released API. For SAP S/4HANA Cloud integration, SAP documents communication scenario SAP_COM_0294.
cloud

Public Cloud: do not answer “use VK11” as a universal maintenance instruction. Classic VK11/VK12/VK13 transactions are not available as classic transaction apps in SAP S/4HANA Cloud Public Edition; use the supported price-maintenance apps for the target scope.

Mass maintenance and migration

Loading prices is not only a file-import task. It is a commercial cutover.

Record count proves that data moved. It does not prove that customers will receive the intended price.

Operational mass change

Use supported price-maintenance apps and controlled import or reference-based creation for recurring business changes. Separate normal maintenance from project migration.

Initial migration

For S/4HANA projects, prefer supported Migration Cockpit objects and current migration content where they fit. Treat LSMW and SCAT as legacy techniques, not the default recommendation for a new S/4HANA design.

Integration

For repeatable external creation or updates, use a released API where possible. Build idempotency, error handling, ownership and reconciliation around it instead of treating the API as a simple upload pipe.

Before load

Freeze the key design, clean duplicate and overlapping records, define ownership, validate currencies/UoM, and agree the effective date.

After load

Test representative orders across specific and fallback accesses, scale boundaries, future-dated prices, billing repricing and exceptional customer/product combinations.

Technical data model

Do not confuse condition master data with document pricing persistence.

This is a common S/4HANA troubleshooting trap because the word “condition” appears in both places.

Condition master

In the classic technical model, generated A* condition tables hold the key combination and reference the condition record. KONH and KONP are important classic master-data tables around the condition record header and item/value data.

Document price elements

In SAP S/4HANA, transactional pricing-result persistence moved from the classic KONV model to PRCD_ELEMENTS. This is evidence about document pricing results, not the master condition record itself.

Lead rule

Start with supported applications and pricing analysis. Go to tables only when you know which layer you are proving and when direct table inspection is appropriate for the deployment.

Troubleshooting

“The condition record exists” is not a diagnosis.

Pricing Analysis is normally stronger evidence than browsing condition records in isolation because it shows what the document tried to do.

01

Define the symptom

One customer, one product, one sales area, one date, one quantity? Or a broad population? This tells you whether to suspect data or design first.

02

Open pricing analysis

Identify the condition type, the accesses attempted, skipped or successful, and the reason SAP gives for the result.

03

Prove the key

Compare the actual runtime fields with the record key. Do not substitute what the user expected the customer group or material to be.

04

Check the record lifecycle

Validate pricing date, validity, release status and overlap history.

05

Check units and scales

Validate currency, pricing unit, UoM and threshold behavior.

06

Move downstream

If the correct rate was found, investigate calculation base, formulas, exclusions, group conditions, manual changes, copy control and billing repricing.

Symptom Higher-probability check Do not do first
Price missing for one customer/material Runtime key, validity, release status, specific access Create another generic record
Wrong price for many customers Pricing procedure, access order, generic fallback, mass change Edit one customer's record
Correct below 100 EA, wrong above 100 EA Scale basis, threshold and pricing unit Change the base condition type immediately
Order correct, invoice different Billing pricing type / copy-control repricing and billing date context Assume the sales-order record was overwritten
Record visible but not used Access execution, key fields, validity and release/approval status Assume database existence means runtime eligibility

Governance

Commercial authority and technical authority should be visible.

Pricing master data can change revenue immediately. That makes ownership, approval and auditability part of the solution design.

Commercial owner

Owns the intended price, discount policy, effective dates, approval thresholds and who may request a change.

SAP / pricing owner

Owns condition design, key combinations, access behavior, deployment-specific maintenance tooling, transportable configuration and technical controls.

Operations

Owns controlled mass changes, failed imports/interfaces, reconciliation, production evidence and rollback or correction procedures.

policy

Practical control: high-impact price changes should have an effective date, owner, approval path where supported, representative order tests and evidence that the intended population changed — not only a successful save or import message.

Patterns worth remembering

Small details create large commercial effects.

KEY

A more specific record wins only if the search reaches it first.

Specificity is not automatic precedence. Access sequence order expresses the priority.

DATE

Do not debug against today's date by habit.

Use the pricing date of the document and the validity period SAP evaluates.

UNIT

Read rate, pricing unit and UoM as one value.

A clean factor error often points to the unit context rather than the commercial price itself.

STATUS

Existing does not mean usable.

A condition record may be blocked or in an approval state where it cannot participate in productive pricing.

DOCUMENT

Manual order conditions do not rewrite master data.

Separate a document override from the maintained condition record and from a later billing repricing event.

CHANGE

A new validity period can change old records.

Overlapping maintenance may delimit or split existing records. Review the resulting time line, not only the new row.

Assessment recall

Separate value, search and result.

A strong Lead answer shows both SAP knowledge and diagnostic order.

record_voice_over

60-second answer: A pricing condition record is sales master data that stores a commercial value for a defined condition type, key combination and validity period. It can also contain currency, pricing unit and scales. The record does not control how SAP searches for it. I first prove the pricing procedure and condition type, then follow the access sequence and the actual runtime key. If SAP reaches the record, I check validity, release status, unit, currency and scales. If the right record is found but the amount is still wrong, I continue into calculation logic, exclusions, manual changes and billing repricing. For operations, I also separate classic VK11/VK12/VK13 maintenance from current Fiori apps, mass maintenance, approval and API-based integration.

Likely follow-up

Why can a record exist but not be used? Wrong pricing procedure, condition type not active, access skipped, runtime key mismatch, invalid date, release status, wrong scale context or another pricing interaction.

Lead-level follow-up

How would you design price maintenance? Start from commercial ownership and volume, keep the key as small as possible, define intentional fallback, use deployment-appropriate maintenance, control approvals and prove representative business results after mass change.
