Variant Configuration

Variant Configuration lets one configurable product represent many valid product combinations. The customer chooses or receives characteristic values, the model checks the rules, and SAP turns the configuration into executable consequences: price, BOM components, routing operations, planning, procurement and production.

Mental model

Separate the product model, the configuration instance and the execution result.

This separation is the fastest way to understand Variant Configuration and to diagnose it. The reusable model says what is possible. A sales order or other business object stores one concrete configuration. Downstream processes consume that configuration and turn it into components, operations, requirements and prices.

1. Product model

The configurable product, variant class, characteristics, allowed values, dependencies, variant tables, configuration profile, super BOM and super routing define the solution space.

2. Configuration instance

A sales order item, material variant or another business object stores the values selected or derived for one concrete configuration.

3. Execution result

BOM explosion, routing selection, pricing, planning, procurement and production use the configuration to decide what must happen.

rule

Lead rule: if the configuration instance is correct but the component, operation, price or requirement is wrong, do not change characteristics blindly. Move to the downstream mechanism that consumes the configuration.

Core model

The model is a stack of objects, not one “KMAT setting”.

A configurable material is only the entry point. The business result comes from the objects connected to it.

Object What it answers Typical maintenance in classic/on-premise Lead check
Configurable material Which product is being configured? MM01 / MM02, usually material type KMAT or another configurable material type Confirm the configurable indicator and the organizational views used by Sales and planning.
Characteristic Which feature can vary? CT04 Use stable business semantics. Do not create a new characteristic for every screen requirement.
Variant class Which characteristics describe this configurable object? CL01 / CL02, class type 300 Keep technical and commercial characteristics understandable and governed.
Configuration profile How should this object be configured? CU41 / CU42 / CU43, PMEVC Check process, BOM explosion, class assignment, engine mode and profile priority.
Object dependency Which combinations, values, components and operations are valid? CU01 / CU02, PMEVC Prefer reusable global logic when the rule is shared; local logic is easier to create but easier to duplicate.
Super BOM Which components can appear in any valid variant? CS01 / CS02 Selection conditions should explain why a component is selected, not hide unexplained product logic.
Super routing / task list Which operations can be required to build the variants? CA01 / CA02 Check operation selection separately from BOM selection.
Material variant Is one frequent configuration important enough to have its own stockable material? Material master linked to the configurable material and pre-valuated with characteristic values Use variants for repeatable stocked combinations, not as a substitute for a clean configuration model.

Classic transaction names are useful for on-premise and Private Edition assessment discussions. Public Cloud and newer AVC scenarios use app-based tooling, so always separate the concept from the UI used to maintain it.

Implementation path

Build the model in an order that keeps responsibility clear.

Starting with dependencies before the product semantics are stable usually creates a model that is difficult to test and maintain.

01

Create the configurable product

Set the material as configurable and maintain the Sales, plant and planning views required by the target process. Standard KMAT is common, but other material types can be configurable when the material type and classification settings allow it.

02

Design characteristics

Create characteristics with clear values, ranges and units. Decide which values are entered by the user, defaulted, derived or hidden from the commercial UI.

03

Create the variant class

Group the characteristics in class type 300 and assign the configurable material. The class describes the configuration vocabulary.

04

Create the configuration profile

Assign the class and define how configuration should run: engine mode, process, BOM explosion, profile priority and other scenario-specific settings.

05

Build the product structure

Create a super BOM and, where production needs it, a super routing. Include all variant and non-variant components or operations that can be required.

06

Add dependencies

Restrict impossible choices, derive values and select the correct components or operations. Keep rules explainable and avoid duplicating the same business rule in many local objects.

07

Add pricing and planning behavior

Map configuration values to variant condition keys where price changes by option, and select the planning strategy and requirements behavior that fit MTO, MTS or procurement.

08

Simulate before business use

Test valid and invalid combinations, BOM and routing results, pricing, material-variant matching and downstream planning. Classic LO-VC can use tools such as CU50; AVC provides its own simulation environment.

Dependencies

Use the dependency type that matches the business rule.

The dependency language is powerful, but model quality depends on keeping each rule in the right place.

Type Purpose Simple example Design note
Precondition Controls whether a characteristic or value is available. Show Battery Capacity only when Drive = Electric. Good for narrowing the user choice space.
Selection condition Selects an object that is required for the configuration. Select the electric motor BOM item when Drive = Electric. Common on BOM items and routing operations.
Procedure Derives or changes values in a defined processing sequence. Derive voltage from market and drive type. Order matters. A procedure is imperative logic, so keep its side effects visible.
Constraint Defines relationships between several characteristics or objects and keeps the configuration consistent. Allowed engine, gearbox and axle combinations must be solved together. Especially important in AVC, where the constraint engine can rule out impossible values early.
Action Legacy derivation mechanism in classic LO-VC. Infer one value after another value is selected. SAP documents actions as obsolete. Prefer procedures or constraints for new model design.
account_tree

Global vs local: a global dependency can be reused and governed centrally. A local dependency belongs to one object. Use local logic for a truly local rule, not because it is faster to create during a workshop.

Super BOM and routing

The configuration is only useful when it produces the right product structure.

A super BOM contains components used by all variants and components used only by some variants. A super routing follows the same idea for operations. Object dependencies turn the full superset into the structure needed for one configuration.

01

Interactive configuration

The customer or sales user selects the product values.

02

High-level rules

Preconditions, procedures and constraints validate or derive characteristic values.

03

BOM explosion

Selection conditions determine which variant components survive the explosion.

04

Routing selection

Operations and resources required by the chosen variant are selected.

05

Planning and execution

MRP and production consume the selected structure according to the planning scenario.

Do not confuse high-level interactive configuration with low-level background configuration. In planning and production, SAP can explode BOMs and routings again using the configuration values transferred from the originating requirement.

Sales and pricing

The sales order stores a configuration instance; pricing can react to selected options.

When a configurable product is entered in a sales order, the configuration UI collects characteristic values and runs the model. The item then carries the configuration instance used by pricing and later logistics processes.

Variant condition key

A characteristic value can trigger a variant condition key. That key connects configuration with condition technique.

Variant pricing

Classic standard condition types include VA00 for an absolute amount and VA01 for a percentage surcharge or discount. Condition records still depend on Sales organization, distribution channel, material and the variant key.

Keep pricing ownership clear

Use configuration to express which option exists. Use pricing to express its commercial value. Avoid calculating commercial price directly inside dependency logic when condition technique can own it cleanly.

payments

Diagnostic split: if the characteristic value is wrong, stay in the VC model. If the variant key is correct but the amount is wrong, move to pricing procedure, condition records and pricing date/context.

Planning patterns

Variant Configuration does not force one planning strategy.

The planning setup must follow the business model. A common classic make-to-order pattern uses item category group 0002 and strategy group 25, but these are scenario values, not universal VC requirements.

Make to Order

The sales-order configuration creates demand for that customer-specific product. MRP and production use the configuration to select components and operations.

Make to Stock

Frequent configurations can be represented by material variants, planned and produced before the customer order, then sold from stock.

External procurement

A configured requirement can also lead to procurement when the product or components are externally sourced. The exact transfer of configuration into purchasing depends on the process design.

Engineer to Order

Complex scenarios can use order-specific engineering and order BOM concepts when the standard model is not enough. Treat this as an engineering process, not only a configuration-screen extension.

warning

Assessment trap: ERLA belongs to Sales BOM header-level processing. It is not a generic requirement for every configurable material. Likewise, availability check values and requirements classes depend on the chosen planning and fulfillment design.

Material variants

A material variant is a reusable stocked configuration, not another name for the sales-order instance.

A material variant has its own material master and is linked to the configurable material. Its characteristic values describe one preconfigured combination that can be manufactured and stocked repeatedly.

When it helps

Use a material variant when the same configuration is ordered often enough that forecasting, stock, ATP, procurement and reporting benefit from a dedicated material number.

Variant matching

During configuration, SAP can search for material variants that match the selected values. Full matching can support replacement of the configurable product in the sales order according to scenario settings.

BOM and routing

A variant can have its own BOM and routing or use the configurable material's structures, with the configuration selecting the correct items and operations.

Model change

When characteristics or dependencies change, existing material variants must be reviewed or updated. Do not assume that old variants or existing orders will automatically adopt the new model result.

inventory_2

Design trade-off: too few material variants push every order through dynamic configuration and MTO. Too many variants create material-master, stock, planning and lifecycle overhead. Create a variant when repeatability has business value, not because a combination is technically possible.

AVC vs classic LO-VC

They share the product-model idea, but the configuration engines are not identical.

SAP S/4HANA supports classic Variant Configuration and Advanced Variant Configuration. AVC is the current advanced configurator for integrated product configuration across Sales, planning, production and engineering. Existing LO-VC models should be compared, not assumed to behave identically after switching engines.

Area Classic LO-VC Advanced Variant Configuration
Core idea Configurable material, class, characteristics, profile, dependencies, BOM/routing and configuration instances. Same business model family, with a newer high-level engine and stronger constraint-solving behavior.
Dependency behavior Procedural processing order is important; actions also exist as obsolete legacy dependencies. Preconditions, selection conditions, procedures and constraints are the main dependency types; the engine can exclude impossible values predictively.
User experience Classic characteristic-value assignment and GUI-oriented tools are common. Reusable Fiori configuration UI and modern simulation/modeling tools are available.
Multi-level models Supported with profile and scenario rules. Supports single-level and multi-level variant configuration models, but integration restrictions still depend on the process.
Transition Existing productive behavior is the baseline. Use SAP comparison and transition tooling to identify differences before conversion. Material-variant switching is irreversible after successful conversion, so test before changing productive objects.
compare_arrows

Lead decision: a migration project is not “change the profile to AVC”. Compare actual sales orders, material variants, purchasing and production configurations against the new engine, then resolve semantic differences before rollout.

Integration boundary

An external configurator needs a versioned product model, not only a material number.

When product configuration runs outside the S/4HANA transaction — for example through SAP Variant Configuration and Pricing or a commerce/CPQ channel — model replication and version control become part of the architecture.

01

Model in S/4HANA

Maintain the configurable product, classes, characteristics, dependencies, BOMs and profiles in their owning product-model environment.

02

Create a knowledge base / runtime version where required

SAP Variant Configuration and Pricing cannot simply read live S/4HANA master data during every remote configuration call. Relevant model data is packaged and replicated as runtime content.

03

Keep identifiers stable

External channels should exchange stable product, characteristic and value identifiers rather than UI labels that can be translated or renamed.

04

Control model version

A quote created against one model version must not silently be reinterpreted against a later incompatible model. Effectivity and release governance matter.

05

Trace configuration and pricing separately

When an external order is wrong, prove which values the configurator produced and which price conditions were returned before debugging S/4HANA order processing.

End-to-end runtime

For MTO, trace one configuration from Sales to production and delivery.

This is the assessment-level flow to remember. The exact document types and planning details depend on the scenario.

01

Sales enters the configurable product

The order item starts from the KMAT or another configurable product and its active profile.

02

User and rules complete the configuration

Values are selected, defaulted or derived. Preconditions and constraints prevent invalid combinations.

03

Pricing evaluates the commercial result

Variant condition keys can add surcharges or discounts for selected options.

04

Demand reaches planning

The requirements class, strategy and schedule-line logic determine how the sales requirement enters planning.

05

MRP explodes the selected structure

The transferred configuration controls the required BOM components and routing operations during low-level configuration.

06

Production or procurement executes

The selected product structure drives supply creation according to the make/buy design.

07

Delivery and billing follow the material flow

Once the configured demand is supplied and available, normal fulfillment controls take over.

Diagnostics

Start with the first wrong layer and stop changing unrelated objects.

Symptom First checks Likely owner if configuration is correct
Value is missing or cannot be selected Characteristic definition, precondition, constraint, default or effectivity VC model
Configuration is inconsistent Conflicting user values, procedures, constraints and dependencies across levels VC model / product engineering
Wrong BOM component Configuration instance, BOM validity, selection condition, BOM application and low-level explosion BOM / dependency / planning
Wrong routing operation Selected values, task-list validity and operation dependencies PP routing / dependency
Wrong variant surcharge Characteristic value, variant condition key, pricing procedure and condition record Pricing when the key is correct
Material variant not found Variant valuation, full vs partial matching settings, excluded characteristics and engine/profile Material variant / matching settings
MRP or production ignores the expected configuration Requirement source, strategy/requirements class, configuration transfer, low-level explosion and production master data PP/MRP after the instance is proven correct
LO-VC and AVC results differ Run engine comparison on real existing configurations and review unsupported or differently evaluated model logic Transition design, not a random master-data fix

Assessment traps

Five shortcuts create weak answers.

“KMAT means Variant Configuration”

KMAT is the standard configurable material type, but configurability is an object behavior. Other material types can be configurable when the relevant settings allow it.

“Strategy 25 is mandatory”

Strategy 25 is a classic MTO strategy for configurable materials. The correct strategy depends on whether the business is MTO, MTS, procurement-led or another scenario.

“All dependencies are the same”

Preconditions restrict choices, selection conditions select objects, procedures derive values and constraints solve relationships. The type communicates the intent.

“A material variant is the sales-order configuration”

The order configuration belongs to one document item. A material variant is a reusable material master representing one stocked configuration.

“AVC is LO-VC with a new screen”

The engine behavior is different enough that SAP provides comparison and transition tools. Test actual configurations before switching productive models.

Assessment recall

Model → instance → explosion → execution.

record_voice_over

60-second answer: Variant Configuration lets one configurable product represent many valid combinations. I model the product with class type 300, characteristics, a configuration profile, dependencies, a super BOM and, where needed, a super routing. The sales order stores one configuration instance. That instance can drive variant pricing and is transferred to planning, where BOM components and operations are selected for production or procurement. Frequent configurations can become material variants and be stocked. For diagnosis I first prove the item configuration, then move to the consuming layer: BOM, routing, pricing, MRP or integration. In S/4HANA I also separate classic LO-VC from AVC because the engine behavior and tooling are not identical.
