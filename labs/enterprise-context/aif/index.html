Integration / Application Interface Framework

SAP AIF makes application-side interface processing operable.

SAP Application Interface Framework sits in the SAP backend and gives interface processing a business-readable operating layer. It can identify an interface, run mappings and checks, expose application errors, route them to responsible users, and support controlled correction or reprocessing where the interface technology allows it.

See how the model fits together arrow_downward
hub

The useful boundary: middleware moves or mediates messages between systems; AIF works inside the SAP application layer. A successful middleware delivery can therefore coexist with an AIF error, and an AIF success still does not replace business reconciliation.

Interface model

An AIF interface is more than a monitor entry.

In classic AIF configuration, an interface is identified by namespace, interface name and version. Depending on the technology, the definition also connects raw and SAP-side structures and the engines used for application processing, persistence, selection and logging.

The next layer is the processing contract. Structure and value mappings transform incoming data. Checks decide whether the data is acceptable. Actions execute the application-side step, for example by calling standard or custom application logic. These blocks are useful because the error can remain tied to the interface and the business context instead of disappearing into a generic technical log.

This model is technology-dependent. AIF can work with several interface technologies, including IDoc and ABAP proxy scenarios, and it also has its own persistence/runtime options. That does not mean every engine, correction function or restart behavior is available for every interface type.

Monitoring

The design becomes useful when support can find the message in business terms.

AIF key fields can make values such as an external order number, purchase order or other business identifier searchable in monitoring. They can also participate in authorization design. Recipients provide the other half of the operating model: monitored interfaces are assigned to the users or groups responsible for them, so the Interface Monitor or Message Dashboard can show a relevant worklist instead of one undifferentiated technical queue.

For SAP GUI-based operation, /AIF/IFMON provides the Interface Monitor and /AIF/ERR opens Monitoring and Error Handling. The web/Fiori variants present the same basic idea through message dashboards and monitoring apps. The exact screen and available action depend on the release and interface.

Find

Search by interface, status, time range and configured business key instead of starting from an opaque middleware identifier.

Understand

Read the application log and the data context that caused the mapping, check or business-processing error.

Assign

Use recipient and authorization design so the error reaches someone who can actually resolve its cause.

Correction and reprocessing

AIF can shorten recovery, but it should not turn support into a second source system.

Monitoring and Error Handling can expose the message payload, application log and message-specific resolution functions. SAP also supports changing message data and restarting or reprocessing messages in suitable scenarios. Those capabilities are deliberately configuration- and technology-dependent.

The distinction matters. If an interface fails because a value mapping or SAP configuration is missing, fix that shared cause and process the original message again. If a field is wrong in the authoritative source, changing a convenient copy in AIF can hide the real data problem. Some product-specific AIF scenarios even place additional restrictions on reprocessing, so “AIF error” never implies that a restart button is valid or available.

For duplicate handling, commit-state analysis, ordering and replay safety across technologies, use the Integration Operations model. AIF is one application-side runtime in that larger recovery chain.

Where responsibility changes

AIF closes a visibility gap; it does not collapse the architecture into one tool.

Integration layer

Connectivity, authentication, routing, adapter behavior and middleware transformations still belong to the transport or mediation layer that performs them.

AIF / SAP application

Interface-specific mappings, checks, application logs, business keys, recipients and supported reprocessing belong close to SAP application processing.

Business process

The created sales order, posting, delivery, master-data change or other target state is the real outcome. Monitoring status is evidence about processing, not a substitute for that outcome.

Example

A web order reached S/4HANA, but no sales order exists.

Suppose the integration flow reports successful delivery. That tells us the message reached the receiver path; it does not prove that SD created a document. If the interface is AIF-enabled, support can search the external order number as a configured key field, open the application error, and see that an organizational value failed a mapping or application check.

If the mapping or SAP configuration is wrong, the shared rule should be corrected before the message is processed again. If the source sent invalid master data, the owning process should correct that source instead. After recovery, the useful proof is the intended sales order and its downstream state, not simply a green message tile.

Deployment boundary

Keep classic AIF configuration separate from delivered cloud monitoring.

In SAP S/4HANA on-premise and comparable ABAP Platform deployments, current 2025 FPS01 documentation still describes classic AIF Customizing through /AIF/CUST, the Interface Monitor and Monitoring and Error Handling. The interface definition, engines and error-handling model are visible parts of that framework.

SAP S/4HANA Cloud Public Edition also uses AIF-backed Message Monitoring for delivered communication scenarios, but this is not a promise that customers receive the complete classic workbench or the same actions for every interface. Even in current SAP documentation, restart or reprocessing can be interface-specific. Treat the communication scenario and its product documentation as the authority for what can actually be done.

Hands-on configuration / Alerting

Configure an AIF alert that reaches the right person.

An AIF error does not automatically become a useful email. You need an AIF message with an error, a recipient rule, a user assignment, an alert category, and a working notification channel. The recipient determines responsibility; the alert category determines the notification content.

Message error→ AIF recipient→ Alert category→ User notification
  1. Define responsibility. Open /AIF/CUST → Error Handling → Define Namespace-Specific Features → Define Recipients. Create a recipient for a business support group, such as ZSD_ORDER_SUPPORT.
  2. Connect the recipient to the interface. For simple routing, use Error Handling → Define Interface-Specific Features → Assign Recipients Without Key Fields. If a recipient assignment table is maintained under Configure Alerts, check that table first: it can take precedence over the simple interface assignment.
  3. Assign actual users. In /AIF/RECIPIENTS, assign the responsible users to the recipient. Check authorizations and whether the interface is included in their monitor overview.
  4. Start with the delivered alert. SAP supplies /AIF/ALERT_CAT_DEF. Trigger a controlled test error and verify that the default notification reaches the intended user before adding a custom template.
  5. Customise the email in ALRTCATDEF. Create a customer alert category, for example Z_AIF_SD_ERROR. Maintain its priority, title, short/long text and container variables. To reuse AIF's namespace, interface name and interface version, copy the corresponding container element names from /AIF/ALERT_CAT_DEF. You can also include one configured key field, such as an external order reference.
  6. Assign the category and test delivery. In /AIF/CUST → Error Handling → Define Namespace-Specific Features → Configure Alerts, assign the category to the relevant interface settings. Confirm the email text, link, recipient and business key in the actual delivered notification.

No email

The user does not receive email notifications for that interface/recipient combination.

Email for next alert

A further alert may be suppressed until the existing alert is confirmed or expires. This is useful for reducing repeated emails from the same unresolved problem.

Email for every error

The user receives an email for each error. Use this only when volume and business criticality justify it.

Users can manage these options in /AIF/IFMON or the corresponding Message Dashboard. When email is missing, check the AIF alert state first, then the user email and SAPconnect delivery in SOST and SCOT. Creating an alert category alone does not configure SMTP. For country-, company- or business-key-specific routing, use AIF key fields and a recipient assignment table instead of hard-coded email logic in the action function module.

SAP references: Recipients and custom alert categories; Interface Monitor notification modes.

Event-driven integration / Two distinct patterns

“Event-triggered AIF interface” can mean two different architectures.

One pattern starts an outbound AIF process after a classic SAP Business Workflow event. Another uses AIF to monitor events consumed through Enterprise Event Enablement. They share AIF monitoring concepts, but they do not use the same trigger configuration.

Business Workflow event → outbound AIF

Use the classic Workflow Event Trigger feature when an existing BOR object event must start reading business data and sending an outbound proxy. Configure event linkage in SWE2.

Enterprise Event → AIF monitoring

Use event monitoring for an event consumer registered through Enterprise Event Enablement. AIF observes the consuming interface by repository, registration and topic. This does not itself publish a new event.

Custom business event → integration

An application may use a separate BAdI, released business event, API or custom action to produce data. Adding an AIF monitor does not automatically create the event producer, queue or external subscription.

Pattern A: trigger an outbound proxy from a Business Workflow event

BOR event→ SWE2 linkage→ AIF reading interface→ AIF sending interface→ Outbound proxy
  1. Identify the BOR business object and event. The standard AIF Workflow Event Trigger described here supports BOR Object Type events, not arbitrary ABAP class events. Use SWO1 to inspect the object key.
  2. Use /AIF/WET_GEN to generate the reading-interface SAP structure from a suitable business-object read function module or BAPI.
  3. In SWE2, activate the event linkage with receiver function module /AIF/WET_EVENT_TRIGGERED. Maintain the runtime group in /AIF/WET_CONFIG and the event-trigger scenario in /AIF/CUST → Interface Development → Event Trigger Settings.
  4. Create the reading interface: raw structure /AIF/WET_EVENT_DETAILS_PROXY, generated SAP structure, XML application and persistence engines, event-key mapping, after-mapping FM /AIF/WET_FILL_SAP_STRUCT, and action /AIF/WET_AC_TRIGGER_NEXT_INF. Assign the read BAPI under Event Trigger Settings → Define Interface-Specific Settings and the runtime group in /AIF/WET_INF_CONFIG.
  5. Create the sending interface: map the read data to the outbound proxy structure, assign action /AIF/WET_AC_TRIGGER_PROXY_OUT, and specify proxy class and method under Define Proxy-Specific Settings. Use /AIF/WET_PRXY_CONFIG when a non-default proxy logical port is required.
  6. Trigger a test event. Use SWELS/SWEL for the workflow event trace, SM58 for possible tRFC delivery problems, and /AIF/ERR for errors in the AIF stages. Confirm the receiver outcome, not only the local event record.

This is the classic SAP-supported configuration flow. It is not a general instruction to activate workflow events for every integration; first check that the object and proxy scenario are available in the target release.

Pattern B: monitor a consumed Enterprise Event

  1. Confirm that the Event Consumption Model and event subscription already exist. Record the repository ID, registration ID/version and event topic.
  2. Create an AIF interface and suitable event payload structure. SAP documents /AIF/EVENT_GEN_CONTAINER_RAW_S for generic JSON attribute-value pairs. A dedicated DDIC payload mapping can require BAdI /AIF/GET_PAYLOAD_EVENT_RT.
  3. In /AIF/CUST → Interface Development → Additional Interface Properties → Define Event Settings, bind the interface to the repository, registration, version and topic.
  4. Assign recipients, deliver a controlled event, and inspect it in AIF Monitoring and Error Handling. If several AIF interfaces match the same event identifiers, review interface determination; SAP documents BAdI /AIF/EVENT_SELECT_INTERFACE for a unique selection.

SAP references: Workflow Event Trigger; Configuring Event Monitoring.

Connectivity / Destination ownership

Choose the destination by transport, not by the AIF interface name.

An AIF interface is a processing and monitoring definition. Its target connection may live in an RFC destination, a partner profile, a SOAP logical port or an external service configuration. “Destination” also means something different for an alert going to SAP BTP than for a business message going to a receiver.

For a remote application call, keep the connectivity configuration with the component that actually sends the request. Test the destination independently before investigating business mapping. Do not put service URLs, passwords or client secrets into AIF mapping tables, alert texts or source code.

Optional extension / SAP BTP

Route AIF message alerts to SAP Alert Notification service.

If the operating model needs notifications beyond classic AIF email, SAP documents an integration with SAP Alert Notification service for SAP BTP. This is an additional service integration, not the default behavior of ALRTCATDEF.

  1. Enable SAP Alert Notification service in the relevant BTP subaccount and obtain a service key through the approved platform administration process.
  2. In the ABAP system, configure an SM59 HTTP destination (type G) for the service endpoint. SAP's published setup uses path /cf/producer/v1/resource-events and an HTTPS connection.
  3. Use OA2C_CONFIG with OAuth profile /AIF/CP_ANS_OAUTH_PROFILE to configure client-credentials authentication from the service key. Let Basis/security manage the secret and certificates.
  4. Maintain the destination and OAuth configuration reference in /AIF/ANS_DEST according to the documentation and maintenance procedure supported by your installed AIF version.
  5. Where the documented deployment applies, activate monitoring via /AIF/CONTENT_EXTRACT for SAP_COM_0578, then assign namespace /AIFAL, recipient RECIPIENT_ALERTING_ANS in /AIF/RECIPIENTS. In BTP, configure the matching notification condition for event type MessageMonitoringAlertingEvent.
  6. Cause one controlled application error. Check AIF alert creation, HTTP/OAuth delivery and the actual BTP notification. Confirm the underlying alert before expecting another “next alert” notification.

Follow the SAP setup guide for AIF and Alert Notification service for the precise configuration supported by your release; this route and its objects are not a universal setup for S/4HANA Cloud Public Edition.

Verification / Troubleshooting

Prove each hop before changing the configuration.

Use a synthetic test message and record its message ID, external business key, timestamp, interface and expected business result. A missing email, missing AIF message and missing receiver document are different incidents.

Practice case: monitored sales-order mass upload

Illustrative design, not a statement about an existing client system: a Fiori application accepts a file of sales orders, calls a custom ABAP function module, and that logic invokes a sales-order creation API/BAPI. AIF can be used to monitor the processing if the application actually registers the data and errors through a supported AIF runtime or enabler. Merely calling a BAPI and adding text to an application worklist does not prove that a complete AIF interface is configured.

Start with three synthetic rows: one valid order, one with a missing mapping, and one duplicate external request. Check that the valid order exists in SAP, the failed row is searchable in /AIF/ERR, the intended support recipient gets one actionable alert, and the duplicate cannot create a second order on retry. If any of those checks fail, locate the responsible layer before calling the design ready.

Design quality

AIF works best when the support model is designed with the interface.

The strongest design choices are simple: expose identifiers that appear in real tickets, log errors that explain the failed condition, route them to a responsible recipient, restrict correction to fields that are safe to change, and make the business result easy to reconcile. When those decisions are missing, AIF can still collect messages, but support remains dependent on technical specialists and repeated manual investigation.

BRFplus can complement this design when a mapping or check is genuinely a reusable business rule. Keep the responsibilities separate: BRFplus evaluates rules; AIF keeps the interface context, processing and error-handling lifecycle.
