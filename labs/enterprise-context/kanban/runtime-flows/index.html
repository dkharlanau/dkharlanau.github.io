Procurement flow

EMPTY → purchasing object → goods receipt → FULL.

This is the cleanest way to understand externally supplied Kanban: one signal starts a purchasing response, and the later receipt restores usable material.

01signal

Demand consumes a container

Did the correct Kanban become EMPTY?

Inputs

  • Material and PSA
  • Kanban ID
  • Control cycle

Expected output

  • EMPTY status
  • Trigger timestamp

Failure signal

Wrong container, blocked status sequence, duplicate scan, or no trigger.

02replenishment

SAP creates the purchasing response

Was the expected PO, schedule line, or contract release created?

Inputs

  • Replenishment strategy
  • Supplier or outline agreement
  • Container quantity
  • Purchasing parameters

Expected output

  • Correct purchasing reference
  • Correct quantity and delivery date
  • Correct receiving destination

Failure signal

Missing source, invalid agreement, wrong destination, or document-creation error.

03physical receipt

Material arrives

Was the real delivered quantity posted?

Inputs

  • Purchasing reference
  • Actual quantity
  • Storage location or PSA route

Expected output

  • Material document
  • Stock increase at the intended location
  • Open purchasing quantity updated

Failure signal

Status says FULL but stock was never received, or the receipt went to the wrong location.

04restore

Kanban returns to usable state

Did FULL represent real availability?

Possible trigger

  • Goods receipt action
  • Board action
  • Barcode scan

Expected output

  • FULL status
  • Purchasing object completed or reduced correctly

Failure signal

FULL without sufficient stock, duplicate receipt, or purchasing document still open unexpectedly.

Scheduling-agreement nuance

Do not assume one Kanban equals one schedule-line receipt.

A schedule-line process can aggregate physical delivery. Several empty containers can be covered by one supplier delivery, and receipt quantity may then restore several Kanbans depending on the process design.

  • Check the agreement item and Kanban relevance.
  • Check that the receiving storage location aligns with the supply area.
  • Separate the number of Kanban signals from the number of supplier delivery events.
  • When goods receipt quantity does not match one container, trace how the quantity is distributed across waiting containers.

Production flow

EMPTY can create production work, but production completion and Kanban completion are not always the same click.

The exact path depends on whether the loop uses manual production, repetitive manufacturing, or production orders.

01

EMPTY requests internal supply

The control cycle determines whether SAP creates a production order, run-schedule quantity, or no separate replenishment document.

Proof: the expected production object exists, or the no-document process is explicitly designed.
02

Production starts

If the sequence requires IN PROCESS, the container should enter that state before completion. A direct EMPTY → FULL jump can be rejected.

Proof: status sequence matches actual execution.
03

Components and output are posted

Backflush can post component consumption and finished quantity. In an order-based design, confirmation and goods receipt can also be handled as separate production events.

Proof: production document, component issues, and receipt quantities reconcile.
04

Container becomes FULL

The status can be linked to backflush/receipt or updated separately, depending on the design.

Proof: FULL corresponds to material physically available at the demand point.
error

Typical production failure: the user tries to set a replenished container to FULL, but the status sequence requires IN PROCESS first. This is not a stock problem. It is a state-machine problem until proven otherwise.

Stock-transfer flow

EMPTY can request movement of existing stock.

The source stock already exists. The runtime question is how SAP represents the planned move and how the actual transfer updates the receiving state.

Reservation-style flow

  • EMPTY creates a transfer requirement or reservation.
  • Source warehouse prepares the quantity.
  • Transfer posting moves stock.
  • FULL indicates restored receiving availability.

Direct flow

  • No separate reservation is required.
  • Posting moves stock source → receiving location.
  • Status and physical movement can be tightly coupled.

Two-step flow

  • Goods issue removes stock from the source.
  • Transit state becomes meaningful.
  • Goods receipt creates receiving stock.
  • Only then is demand-side availability restored.

Evidence chain

Use the same four questions for every runtime trace.

SIGNAL

What did the Kanban say?

Container ID, old status, new status, timestamp, user/device, actual quantity if quantity signals are used.

OBJECT

What replenishment element exists?

Production order, repetitive quantity, PO, schedule line, reservation, transfer document, or an explicitly designed no-document execution.

STOCK

What material movement exists?

Material document, movement semantics, actual quantity, source and destination, batch or stock type where relevant.

VALUE

What consumption or cost effect exists?

Backflush, cost-center issue, order cost, valuation, or another accounting effect that should follow the physical event.

Logical versus physical stock

The Kanban board can be right while inventory is wrong — and the reverse.

A status loop can progress without immediately posting every physical consumption event. This creates a deliberate distinction between logical container state and book stock.

Logical state

  • EMPTY means the container no longer protects the demand point.
  • IN USE can represent partial consumption.
  • FULL means available in the Kanban control model.

Book stock

  • Changes only when an Inventory Management or production posting changes quantity.
  • Can remain visible in the storage location after the physical container is already being consumed.
  • Can be corrected only by understanding the real business event, not by changing a Kanban color.

Lead diagnosis

  • Compare board state with stock overview.
  • Find material documents and production postings.
  • Check whether backflush timing explains the difference.
  • Confirm physical quantity at the demand point before posting corrections.

Kanban cards

The card design should support the physical route.

Printing is part of execution when the signal moves physically with the material.

CIRCULATE

Card travels with the container

The same physical card moves between demand and supply together with the container.

SUPPLY

Card stays at the source

Demand sends the signal electronically or through the board; the supplier attaches or uses the local card for the refill.

DEMAND

Card stays at the demand point

The board communicates which container is required while the physical card remains close to consumption.

PRINT

Print at a lifecycle event

Classic flows can print cards when replenishment is triggered, when goods receipt is posted, collectively, or from a preprinted blank design.

Classic GUI implementations can use PK17 for Kanban card printing. Validate output technology and supported apps in the target release.

Assessment scenario

“The board is green, but the line says the material never arrived.”

  1. Identify the exact Kanban ID that became FULL.
  2. Check what event changed it to FULL: scan, board action, goods receipt, or automatic action.
  3. Find the replenishment document linked to that Kanban.
  4. Find the material document and verify actual quantity and destination.
  5. Check whether the goods were received to a central storage location instead of the line-side PSA.
  6. Confirm physical stock and transport status before creating any corrective posting.
