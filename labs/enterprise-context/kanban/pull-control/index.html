Kanban / 01

Pull is not “MRP switched off.”
It is a different control point.

In a push model, planning decides what should be available and when. In a Kanban pull loop, the demand point says: this container was consumed, replace it. The difference looks simple, but it changes where inventory, responsibility, and execution decisions sit.

Push versus pull

Planning and execution answer different questions.

A production plan can be correct and the line can still run out of material. Kanban moves one part of the execution decision closer to the point of consumption.

Push control asks

  • What will be needed?
  • On which date?
  • In what lot size?
  • Which dependent requirements come from the BOM?
  • What supply element should be created in advance?

Pull control asks

  • Was a defined quantity actually consumed?
  • Which container now needs replacement?
  • Which supply source owns the refill?
  • Can the source restore the buffer inside the replenishment time?

The Lead asks

  • Which horizon belongs to planning?
  • Which horizon belongs to shop-floor execution?
  • Where should stock be visible?
  • What is the recovery path when a signal cannot be fulfilled?
warning

Anti-pattern: using Kanban to compensate for unstable production, long supplier lead times, bad master data, or missing capacity. A pull loop exposes these problems; it does not remove them.

Fit test

Five conditions make the pull loop credible.

If several of these conditions are weak, the design normally needs larger buffers, a different supply strategy, or more planning control.

01

Fast replenishment

The source must be able to refill the consumed quantity quickly enough that the remaining containers protect production.

Check: real lead-time distribution, not only master-data lead time.

02

Small and repeatable lots

Kanban works naturally when the source can deliver in practical container-sized quantities without expensive setup for every signal.

Check: setup time, batch constraints, transport unit, minimum order quantity.

03

Available capacity and parts

A perfect signal is useless if the source has no machine capacity, labor, packaging, transport, or upstream components.

Check: the real bottleneck behind the source.

04

Stable enough consumption

Demand does not need to be flat, but the loop needs a usable relationship between consumption, container quantity, and replenishment time.

Check: seasonality, campaign peaks, engineering changes.

05

No hidden overproduction

The source should not keep producing “just in case.” Otherwise Kanban becomes a label on top of a push process and inventory grows outside the control loop.

Check: WIP and stock outside the defined containers.

FAIL

Variable one-off demand

Rare components, long project lead times, configurable low-volume materials, or supply with long campaigns may need a different planning and execution model.

Check: whether the signal frequency is high enough to justify a fixed cycle.

MRP coexistence

Decide what MRP should see.

Kanban can be designed with or without MRP participation for the local material segment. That choice changes how future requirements and live replenishment interact.

WITHOUT MRP

Signal-driven local supply

The Kanban-managed storage-location segment can be excluded from normal MRP. Replenishment is then created from the Kanban signal rather than from MRP receipt proposals.

Use when the local loop is deliberately self-controlling.
WITH MRP

Planning remains visible

MRP can still calculate future material needs and create or propose supply elements while the Kanban process controls short-cycle consumption and staging.

Use when planning visibility is still required.
SIMULATION

Forecast without disturbing execution

Long-term or simulation planning can help estimate future dependent requirements for Kanban materials without turning every forecast into immediate shop-floor replenishment.

Useful for capacity and medium-term supply conversations.

Design rule: document the MRP boundary by plant, material, and storage-location segment. “Kanban material” is too vague to explain the planning behavior.

Inventory logic

The buffer should be visible and finite.

A container is not only a visual aid. It represents a controlled quantity and therefore a defined amount of inventory in the circulation loop.

Assessment questions

What a SAP Lead should be able to explain.

  • Why can MRP be technically correct while Kanban still improves line-side execution?
  • What happens if replenishment time becomes longer than the protection offered by the remaining containers?
  • Why is adding more containers not always the right fix?
  • When would you exclude a storage-location segment from MRP, and what visibility do you lose?
  • Which business conditions would make you reject Kanban for a material?
