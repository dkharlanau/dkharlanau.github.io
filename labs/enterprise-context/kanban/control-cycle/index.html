The control cycle is the contract
between consumption and supply.

It tells SAP what material is being controlled, where the demand point is, how many containers circulate, how much each container represents, which replenishment strategy applies, and which status logic governs the loop.

Start with the demand point arrow_downward

Production supply area

The PSA is the operational address of line-side supply.

A production supply area is a staging zone close to one or more work centers. It acts as a local buffer for material needed by production and connects physical delivery with Inventory Management responsibility.

LOCATION

Storage location

A PSA is assigned to a storage location. Several PSAs can use the same storage location, but one PSA should not point to several storage locations at once.

Lead question: can book stock be reconciled with the physical staging area?

OWNER

Responsible person

Assign operational responsibility for monitoring supply and responding when the loop is not restored in time.

Lead question: who owns an EMPTY container that stays empty?

DOOR

Unloading point

For external supply, the supplier may deliver directly to a defined line-side or staging destination. The unloading point becomes part of the physical design.

Lead question: does the document destination match the real receiving route?

WORK CENTER

Consumption relationship

A PSA can serve one or more work centers. The design should be specific enough to make replenishment ownership and stock visibility clear.

Lead question: is one buffer hiding several unrelated consumption patterns?

Control-cycle content

Seven settings shape most of the runtime behavior.

The exact screen depends on release, but the design logic remains recognizable.

01

Material + demand location

Plant, material, production supply area, and related storage-location context identify the demand side of the loop.

If this is wrong, every later document can be correct for the wrong place.
02

Number of Kanbans

Defines how many containers or signals circulate at the same time.

This is capacity of the loop, not a decorative count.
03

Quantity per Kanban

Defines the material quantity represented by one container and normally the replenishment quantity generated by one signal.

Container size should match the physical handling unit where practical.
04

Maximum empty

Defines a control threshold for how many containers may be empty before the situation becomes exceptional.

Useful as an operations signal, not as a substitute for lead-time design.
05

Replenishment strategy

Determines whether the signal is handled by internal production, external procurement, or stock transfer, and which execution object is expected.

The strategy is the bridge from signal to supply.
06

Flow control

Status sequence, independent supply-source logic, separate goods receipt, trigger quantity, and related controls determine how the loop progresses.

This is where allowed transitions become process logic.
07

Output and calculation

Printing, barcode behavior, calculation profile, safety settings, and replenishment-time inputs support physical execution and sizing.

These settings make the loop operable and maintainable.

Container identity

A container needs a stable identity if the status should be trusted.

Each Kanban can have an internal identifier. In barcode-based operation, the scanned identity tells SAP which exact container changed state.

Why identity matters

  • Trace which container is EMPTY or FULL.
  • Link a status change to its replenishment object.
  • Prevent operators from updating the wrong loop.

Signal lock

  • A short lock interval can protect against duplicate scans.
  • Useful when scanners or operators can send the same status quickly twice.
  • It reduces accidental double processing, but does not fix wrong process design.

Physical design

  • Card on container.
  • Card stays at supply source.
  • Card stays at demand source and the board communicates the refill.
  • Electronic signal with barcode or equivalent identifier.

Sizing

Size the loop from consumption and replenishment time.

Automatic calculation can use a profile, but the underlying business logic is simple: the loop must cover material consumption while a container is away being replenished, plus the selected protection against variation.

AC

Average consumption

How much material is normally used per time unit in the demand area?

Risk: averages hide peaks and shift patterns.

RT

Replenishment time

How long from the EMPTY signal until usable material is back at the demand point?

Risk: master-data time may not include queueing, transport, receiving, or supplier variability.

QTY

Container quantity

How much material fits one physical or logical Kanban unit?

Risk: a mathematically neat quantity may be operationally awkward.

SAFE

Safety factor or buffer

How much additional protection is required for normal variation?

Risk: too much safety converts a lean loop into hidden inventory.

Validation rule: after any automatic calculation, test the proposed number of containers against actual consumption peaks, real replenishment-time distribution, packaging, route frequency, and source capacity. Validate the exact calculation profile and formula in the target SAP release.

Classic versus event-driven

Not every pull loop needs a fixed set of circulating cards.

Classic Kanban normally manages a defined number of containers. Event-driven variants can create or activate a Kanban from an actual requirement rather than from a fixed permanent circulation pattern.

Classic

  • Fixed circulation.
  • Stable container quantity.
  • Strong visual control.
  • Best for repetitive demand.

Event-driven

  • Signal can be created for a requirement event.
  • Useful when permanent container circulation is not the best representation.
  • Still needs clear source and status logic.

Lead decision

  • Choose the model that matches the physical replenishment pattern.
  • Do not introduce dynamic logic only because the fixed cycle was badly sized.
