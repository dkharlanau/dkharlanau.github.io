Kanban / 04

A Kanban status is not a color.
It is a control event.

Changing a status can start replenishment, post goods receipt, trigger backflush, print a card, or reject an invalid transition. The sequence therefore belongs to process design, not only to the board layout.

Status sequence

EMPTY and FULL are the anchors; intermediate states make execution visible.

A practical sequence can include waiting, replenishment work, transport, use, and error states. The exact sequence should represent the physical process rather than create artificial clicks.

WAITWaitingThe demand side has signaled a need, but the actual replenishment trigger is controlled separately.hourglass EMPTYContainer emptyThe demand-side container no longer protects consumption and normally requests replenishment.inventory_2 PROCESSIn processThe supply source is producing or preparing the refill.precision_manufacturing TRANSITIn transitThe refill has left the source but is not yet usable at the demand point.local_shipping FULLContainer fullThe replenished quantity is available again for the demand side.check_circle IN USEMaterial being consumedUseful when a quantity signal tracks partial consumption before the container becomes empty.remove_circle ERRORProcessing failedThe requested transition or linked business action failed and needs correction.error

Classic implementations often use a sequence close to WAIT → EMPTY → IN PROCESS → IN TRANSIT → FULL → IN USE, with ERROR as an exception state. Treat the exact sequence as configurable process logic.

Allowed transitions

Mandatory, optional, and forbidden states create a state machine.

A good sequence prevents impossible business jumps while keeping normal work fast.

MANDATORY

Must be passed

If IN PROCESS is mandatory, trying to move directly from EMPTY to FULL should fail until the required intermediate state is reached.

Use for: steps that are operationally important and must be visible.

OPTIONAL

May be passed

Optional states support richer visibility without blocking a simpler path where the physical step is not always separate.

Use for: transport or handling states that depend on scenario.

FORBIDDEN

Cannot be used in the path

Not every status belongs to every control cycle. Removing irrelevant states reduces bad scans and ambiguous recovery.

Use for: states that would not represent a real event in this loop.

ERROR

Technical or business failure

When the linked action fails, the container can remain or move into an error condition so operations do not silently lose the failed request.

Use for: repairable failures that need evidence and correction.

Actions on status change

A status can carry business logic.

Examples include automatic goods receipt, backflush, card printing, or creation of a replenishment object. This is why a status-only correction must be used carefully.

EMPTY

Create replenishment

The EMPTY transition can create the expected supply object according to the replenishment strategy.

Check: did the correct object appear, with correct source and quantity?
FULL

Post receipt or completion

A FULL transition can be linked to goods receipt or backflush in selected designs. In other designs the posting is separate.

Check: does FULL mean physically available, or only a status update?
PRINT

Create physical signal

A card can be printed when replenishment is triggered, when receipt is posted, or according to another defined lifecycle.

Check: where does the physical card live during the cycle?
inventory

Critical boundary: Kanban status and book stock are related but not identical. Setting a container to EMPTY does not automatically mean a goods issue happened. Setting it to FULL does not prove that receipt was posted unless the configured action actually created the material document.

Independent supply source

Separate “we need material” from “start replenishment now.”

Some loops should not let the demand side directly create the replenishment object. A waiting state can record demand while the supply source controls the actual trigger timing.

Demand side

  • Consumption creates the need.
  • Container moves into a waiting condition.
  • The request is visible without immediately creating new supply.

Supply side

  • Monitors the waiting queue.
  • Decides which Kanbans to release into replenishment.
  • Can group work around production or logistics constraints.

Lead risk

  • WAIT can become a hidden backlog.
  • Define owner, trigger rule, aging threshold, and escalation.
  • Measure waiting time separately from physical replenishment time.

Signal lock

Protect the process from duplicate scans.

Barcode operation is fast enough that the same container can be scanned twice before the user notices the first update. A short signal lock can reject another status change within a defined interval.

  • Use the lock to prevent accidental double input, not to hide slow transactions.
  • Investigate repeated scans as an ergonomics or process-training signal.
  • If devices retry automatically after network failure, test idempotency and the real status result.

Quantity signal

You can trigger from consumption quantity, not only from EMPTY/FULL clicks.

In a two-Kanban or quantity-signal design, withdrawals reduce the actual quantity in the active container. When the remaining quantity reaches the trigger, SAP can make the next Kanban available for replenishment.

STEP 1

Start using a full container

The first withdrawal can move the active Kanban from FULL to IN USE and reduce its actual quantity.

The status now represents partial consumption.
STEP 2

Reach the trigger

As withdrawals continue, remaining quantity approaches the configured trigger quantity.

The next container can be signaled before the current one is completely empty.
STEP 3

Spill consumption correctly

If one withdrawal is larger than the remaining quantity, the logic can consume the rest of the current container and continue against the next one.

This keeps quantity and status rotation aligned.

Trade-off: quantity signals give better visibility of partial consumption but require reliable quantity reporting. If users do not record withdrawals correctly, the status model becomes more precise than the real process.

Fixed quantity boundary

Kanban manages a control quantity, not demand variability forever.

Fixed container quantities work inside a reasonable demand and lead-time range. If consumption changes materially, the number of containers or quantity per container should be reviewed.

  • Recalculate after sustained demand change, route change, supplier lead-time change, packaging change, or production-rate change.
  • Do not keep obsolete safety containers because “the line likes them.” Make the reason explicit.
  • Compare status history with real stock and consumption before changing the cycle.
