Kanban / 06

Do not repair the color.
Repair the broken business event.

Kanban operations becomes difficult when teams see only the board. The board is the symptom surface. Diagnosis must continue into the control cycle, replenishment element, material document, source capacity, and real physical state.

Use the diagnostic path arrow_downward

Operations priorities

1AgeHow long in current state?
2ProofWhich document exists?
3RecoverFix cause before status
A healthy loop is fast enough that abnormal aging becomes visible quickly.

Diagnostic path

Start from the failed state and walk outward.

The shortest reliable path is status → control cycle → replenishment object → posting → physical process.

01state

Read the exact Kanban

Which container is wrong, and what is its current status?

Collect

  • Kanban ID
  • Material / plant / PSA
  • Current and previous status
  • Status timestamp

Interpret

  • Was the transition allowed?
  • Is the container simply late?
  • Is it in ERROR?

Do not

Change status only because the board looks wrong.

02design

Read the control cycle

What should this status have triggered?

Check

  • Replenishment strategy
  • Status sequence
  • Automatic actions
  • Source and receiving location

Interpret

  • Expected object type
  • Expected quantity
  • Required intermediate state

Failure clues

Wrong master data, missing source, invalid status path, or obsolete cycle sizing.

03document

Find the replenishment element

Did SAP create what the strategy promised?

Possible objects

  • Production order
  • Run-schedule quantity
  • Purchase order / schedule line
  • Reservation / transfer object

Check

  • Status and quantity
  • Deletion or completion flag
  • Source and date

Failure clues

Deleted object, scheduling failure, invalid source, or document still open after physical completion.

04posting

Find stock and production postings

Did the business event change book stock or consumption?

Evidence

  • Material document
  • Goods issue / receipt
  • Backflush or confirmation

Compare

  • Actual quantity
  • Source / destination
  • Posting time

Failure clues

Status completed but posting missing, duplicate posting, or quantity mismatch.

05physical

Confirm the real material

Where is the container physically?

Check

  • Line-side quantity
  • Source stock
  • Transit location
  • Wrong PSA or unloading point

Interpret

  • System wrong?
  • Physical process wrong?
  • Both wrong?

Recovery

Correct only after the intended business state is agreed.

Operational views

Different reports answer different questions.

The Kanban board is excellent for current execution. Historical and exception views are needed for system improvement.

BOARD

Current status

See containers by demand or supply view, status, quantity, and control-cycle context. Use it for immediate shop-floor action.

Classic reference: PK13N.

EVALUATE

Control-cycle detail

Inspect Kanban states together with replenishment elements and material-document references.

Classic reference: PK18.

DELAY

Delayed replenishment

Focus on containers whose expected replenishment has not arrived in time. This is more actionable than scanning every red card.

Classic reference: PKAL.

ANALYSIS

Historical performance

Analyze status times, operation counts, quantities, and other historical indicators to see whether the cycle is structurally healthy.

Classic reference: MCQ.

PLANT

Plant overview

Look across materials and supply areas to see how many containers are waiting, empty, full, or in other states.

Use for: pattern detection and prioritization.

ERROR

Error processing

Filter failed Kanbans by plant, PSA, source, material, strategy, status, and time, then open the exact correction context.

Classic reference: PK50.

Alerts

Alert on conditions that need action, not on every normal status.

Kanban can produce useful exception signals when a container enters error, too many containers are empty, a replenishment element is deleted, or a replenishment is delayed.

ERROR

Container processing failed

The signal could not complete its linked business action.

Owner: process support or operations depending on the failure.
EMPTY LIMIT

Too many empty containers

The protective buffer is shrinking faster than replenishment restores it.

Owner: production/supply controller; investigate source lead time and demand spike.
DELETED

Replenishment element removed

A user or downstream process deleted the object that was supposed to refill the Kanban.

Owner: identify why the object was removed before recreating anything.
DELAY

Replenishment overdue

The object exists but the refill has exceeded the expected timing.

Owner: source-specific — supplier, production, warehouse, or transport.

Classic implementations can activate Kanban alert behavior through configuration. Treat the exact alert framework and transaction mapping as release-specific.

rule

Operations rule: a useful alert must answer four things: what failed, how long it has been abnormal, which production risk it creates, and who owns the next action.

Error correction

Fix the cause, then repair the Kanban state.

A failed status transition normally means a linked action could not complete. The correction tool should be the final step of diagnosis, not the first.

1

Read the error message

Identify whether the failure came from scheduling, master data, source determination, production data, stock, or another linked process.

Preserve the original error as evidence.
2

Repair root data

Correct the invalid master data, production setting, purchasing source, stock condition, or other cause.

Do not manually force a status past a still-broken action.
3

Use Kanban correction

Apply the supported correction function to move the Kanban into the correct next state or repeat the intended action where appropriate.

The target state must match the real physical situation.
4

Reconcile linked documents

After correction, confirm the production/purchasing/transfer object and material postings are not duplicated or left inconsistent.

Recovery is complete only when the evidence chain is coherent.

Reversal

Reversing a signal is more than changing the status back.

Where supported, reversing the last Kanban signal can reset the container to its previous state and reverse or mark related replenishment actions for deletion.

What may be reversed

  • Previous container status.
  • Linked purchasing, reservation, production, or schedule-line action depending on process.
  • Related posting where the supported reversal logic permits it.

Important limits

  • An already processed correction may no longer be reversible.
  • A Kanban that has already been reversed should not be repeatedly reversed as a repair technique.
  • Downstream business processing can make technical reversal inappropriate even if the button exists.

Lead rule

  • Check downstream use first.
  • Prefer business reversal over database-like status repair.
  • After reversal, retest the normal signal path.

KPIs

Measure the loop, not the number of scans.

The best Kanban metrics show whether replenishment protects production with minimal inventory.

TIME

Replenishment lead time

EMPTY or trigger → usable FULL material. Split waiting, processing, transit, and receiving time where the statuses support it.

RISK

Empty-container exposure

How often and how long the loop operates near or above the maximum-empty threshold.

ERROR

Failed signal rate

Share of signals entering error or requiring correction. Group by root-cause family.

STOCK

Circulation inventory

Total container quantity in the loop compared with actual consumption and service requirement.

VARIANCE

Logical/physical mismatch

Frequency of board state not matching the real stock or physical container position.

CHANGE

Cycle recalculation need

Materials where sustained demand or lead-time change makes the original number of Kanbans obsolete.

Assessment answer

How to explain a Kanban incident as a Lead.

Use this structure: “The visible symptom is the container status. I first confirm the control-cycle expectation, then the replenishment object, then the actual stock or production posting, and finally the physical location. I correct the root cause before using Kanban correction or reversal. After recovery, I check whether the failure was one-off or whether lead time, source capacity, or cycle sizing needs redesign.”
