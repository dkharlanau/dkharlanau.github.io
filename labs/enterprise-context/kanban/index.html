SAP Logistics / Kanban

A Kanban container is a control signal, not a planning document.

SAP Kanban controls short-cycle replenishment close to the point of use. When material is consumed, the container status changes. That signal can trigger production, external procurement, stock transfer, or warehouse replenishment according to the control cycle. The important idea is simple: demand is created by consumption, but the downstream document and stock posting depend on the chosen replenishment strategy.

The control loop

EMPTY requests supply; FULL makes the container available again.

SAP documentation describes EMPTY and FULL as the basic Kanban statuses. Additional statuses such as WAIT or IN PROCESS can appear when the replenishment design needs a more detailed execution state.

A normal cycle starts with usable material at the demand point. Once the container is consumed, the demand side reports it EMPTY. SAP reads the control cycle and starts the configured replenishment process. When the material returns, the container becomes FULL again. Depending on the strategy and configuration, status changes can also trigger goods movements or other background processing.

This distinction matters because a status change is not a universal material document. In one process, setting a container to EMPTY can create a purchase order. In another, it can create a production order or a stock-transfer action. In warehouse-managed supply, it can create warehouse tasks. Likewise, the FULL signal may post a goods receipt in some processes while other designs separate the physical receipt from the status change.

Control cycle

The control cycle connects a demand point to a supply method.

The container does not decide where its replacement comes from. That logic sits in the control cycle.

Demand side

Material, plant, production supply area, and storage-location context identify where the material is consumed and where the Kanban stock belongs.

Circulation

The number of containers and the quantity per container define how much material circulates in the loop. SAP can also calculate proposals for these values from requirements and calculation parameters.

Supply side

The replenishment strategy tells SAP whether the source is in-house production, external procurement, or stock transfer and which execution object should be used.

That is why a Kanban problem often starts in master data rather than in the board itself. If the production supply area, storage location, source, strategy, or container sizing is wrong, SAP can process the status correctly and still create the wrong operational result.

Replenishment

The same EMPTY signal can lead to different business documents.

Kanban is a control method. The replenishment strategy defines how the signal becomes executable work.

In-house production

The signal can trigger production-based replenishment, for example through a production order or another supported in-house strategy. The production version or responsible production source can be part of the control-cycle definition.

External procurement

The control cycle can point to a supplier or supplying plant and use supported procurement objects such as a purchase order or scheduling agreement. With a standard purchase-order strategy, SAP can create the purchase order when the container becomes EMPTY.

Stock transfer

The source can be another storage location or plant. The exact execution can range from Inventory Management transfer logic to warehouse tasks when the source is warehouse-managed and the configured process supports it.

The useful troubleshooting question is therefore not “why is the Kanban empty?” but “which replenishment strategy owns this control cycle, and what object should that strategy have created?”

Planning boundary

Kanban can work with MRP or deliberately outside it.

Pull execution and material planning are separate design choices. SAP supports both combinations.

With MRP integration, the storage-location segment used by the production supply area remains in planning. MRP can provide preview and future supply visibility, while the actual short-cycle material flow is still triggered by Kanban status changes.

Without MRP integration, the Kanban storage-location segment is excluded from planning, commonly through an MRP-area and MRP-type design. SAP then creates the replenishment element from the Kanban signal instead of from the regular planning run. This boundary must be explicit because it also affects dependent requirements and the way BOM components are planned.

So “this material uses Kanban” is not enough to explain its planning behavior. We need to know the plant, storage-location or MRP-area context, and whether that local segment participates in MRP.

When the loop breaks

Find the first layer where expected state and actual state diverge.

A red Kanban, a missing purchase order, and wrong stock are different failures even when they appear in the same replenishment cycle.

SIGNAL

1. Container state

Did the correct container change to the intended status, and was that transition allowed for this process?

Evidence: container identity, status history, and control cycle.
SUPPLY

2. Replenishment object

Did the configured strategy create the expected production, procurement, transfer, or warehouse object?

Evidence: object type, reference, source, and quantity.
STOCK

3. Material movement

Did the required goods issue, transfer, goods receipt, or warehouse confirmation occur, and did book stock move to the intended location?

Evidence: material or warehouse document and before/after stock.
PROCESS

4. Business completion

Is the material physically usable at the demand point, or is the system only showing an intermediate technical state?

Evidence: container availability plus the relevant production or logistics result.

For example, an EMPTY container can successfully create a purchase order while the line still runs out because the supplier lead time exceeds the protection offered by the remaining containers. That is not a failed Kanban signal; it is a replenishment design problem.
