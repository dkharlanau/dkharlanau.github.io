Cross-process / Integration Operations

A successful message is only one checkpoint.

An integration incident is closed only when the intended business state exists in the receiver. Middleware, queues, IDocs and AIF can each prove part of the path, but none of them alone proves that the business process completed correctly.

Trace the path end to end arrow_downward
sync_problem

Keep three states separate: transport state, application-processing state, and business state.

A message can be technically delivered while the receiver rejects it, or application processing can finish while the resulting document is still wrong for the business process.

End-to-end trace

Start with one business message, not with a monitor.

The fastest investigation usually follows one message from the business event to the receiver outcome. Every hop should add evidence, not replace the evidence from the next layer.

Business event→ Message identity→ Transport / queue→ Receiver processing→ Business object

Begin with a stable correlation value: an IDoc number, external document number, message ID, business key, queue unit or another identifier that survives the handoff. Then establish where the message last had a known-good state. Only after that should we decide whether the next action is a retry, a data correction, a queue recovery, an application reprocessing step, or no replay at all.

The important boundary is the receiver commit. A timeout or missing acknowledgement can leave the sender unsure whether the receiver already wrote the business object. Replaying in that state without checking the receiver can turn an integration incident into a duplicate-business-object incident.

Delivery semantics

Reliability and ordering solve different problems.

SAP runtimes use different mechanisms to control delivery. The names vary, but the design questions are stable: may a message be retried, can duplicates appear at the receiver boundary, and must related updates remain in sequence?

qRFC

qRFC extends transactional RFC with queues so calls assigned to a queue can be serialized. Outbound and inbound queues place ordering at different sides of the connection. If a predecessor in the same sequence cannot complete, later work can remain blocked behind it.

bgRFC

bgRFC stores processing units in the database and supports transactional units as well as queued units. Queued units follow FIFO processing. The bgRFC monitor shows the state of those units; it does not replace validation of the application object created by the unit.

Integration Suite

Cloud Integration can provide retries, queues and duplicate-handling patterns, but end-to-end exactly-once behavior depends on the complete sender, middleware and receiver design. SAP explicitly recommends duplicate handling as close as possible to the application that writes the data.

Ordering should be requested only where the business dependency requires it. A sequence such as create → change → cancel must not be reordered for the same object. Independent messages usually do not need to share one serialized queue, because one bad item can then hold back unrelated work.

Application processing

Transport success ends where application responsibility begins.

An IDoc, AIF interface or application API can fail after the transport layer has already done its job. At that point, the useful evidence is application-specific: processing status, application log, failed mapping or validation, target document reference, and whether the receiver transaction committed.

SAP Application Interface Framework is particularly useful when an interface is AIF-enabled because it can expose business keys, application errors and supported correction or reprocessing actions inside the SAP backend. Those capabilities depend on the interface technology and configuration; an AIF error does not automatically mean that the payload can be edited or restarted.

IDoc processing has the same operating principle. A technical IDoc record is not the final business result. Read the current status and application message, then follow the reference to the sales order, delivery, posting, master-data object or other target that the interface was meant to create or change.

Recovery

Replay only after the failure class is clear.

Repeatedly pressing restart is not a recovery strategy. The safe action depends on what has already happened.

Nothing reached the receiver

After correcting the connectivity or transient transport problem, a retry may be the correct action if the interface contract supports it.

The receiver rejected the message

Fix the shared cause—such as mapping, configuration or authoritative master data—then reprocess through the supported application mechanism. Do not turn the error monitor into a second source system.

Commit state is uncertain

Check the receiver first. Search by the business key and correlation ID, then determine whether the intended object already exists before replaying anything.

Queues add one more rule: repair the earliest blocking unit before treating later queued work as separate incidents. With serialized qRFC or queued bgRFC processing, later messages can be waiting correctly because an earlier dependency has not completed.

Duplicates and idempotency

“Exactly once” is not permission to ignore duplicate design.

Duplicate handling is strongest when the receiver can recognize the same business request and make that check part of the same transaction that writes the application data. SAP's Cloud Integration guidance makes this boundary explicit: when a receiver is not idempotent, middleware can reduce duplicate risk, but a lost acknowledgement after a successful receiver commit can still leave a residual duplicate scenario on retry.

The practical design question is therefore not only “what quality of service did we configure?” It is “what identifier lets the receiver prove that this business operation has already been applied?” For an order, that may be an external order ID; for master data, a source-system key; for an event, a stable event or message identifier plus application-side duplicate logic.

Business reconciliation

The last check belongs in the business process.

Integration monitoring tells us how a message was processed. Reconciliation tells us whether the business intent arrived intact.

For a sales-order interface, the useful proof is not a completed integration-flow log. It is one correctly created sales order with the expected external reference, partners, quantities and status. For master-data replication, the proof is the expected target object and relevant attributes. For a posting interface, it is the intended accounting or logistics document and the values that matter to the process.

This is also where ownership becomes clear. Integration support can prove transport and mediation. The receiving application team can prove processing and commit state. The business process owner decides whether the resulting state is actually acceptable. Closing an incident before those views meet is how technically green interfaces produce recurring business defects.

Example

The integration flow completed, but no sales order appears.

Start with the external order number and message ID. Confirm that the sender created one request and that the middleware delivered it to the expected receiver. If the receiver uses IDoc or AIF-backed processing, inspect that application state next. A mapping or organizational-data error may explain why transport completed while SD did not create the document.

After fixing the cause, establish whether an SAP sales order was already committed under the same external reference. If none exists and the interface supports controlled reprocessing, replay the original request through that mechanism. If an order already exists, do not create another simply to make the middleware log look clean. Reconcile the original request to the one SAP document and close on that business evidence.
