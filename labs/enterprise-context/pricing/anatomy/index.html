Deep vertical / Pricing Anatomy

A condition is more
than a rate.

In SAP Sales, a pricing result comes from several controls working together: the pricing procedure gives a condition its place, the condition type defines its behavior, master data can provide a rate, and the calculation base, scales, grouping, and interaction rules decide the final value.

The calculation path

Follow the condition from permission to amount.

A useful pricing analysis does not begin with the condition record. First establish whether the condition belongs in the active procedure and is allowed to participate. Then trace where its amount comes from and how SAP turns that amount into a condition value.

1 · PROCEDURE

The pricing procedure gives the condition a place in the calculation.

Its row establishes sequence and can add controls such as a requirement, subtotal, statistical treatment, calculation-base override, or amount-calculation override.

2 · TYPE

The condition type defines reusable behavior.

It describes what kind of pricing element this is and controls important behavior such as calculation type, conversions, scale handling, group treatment, and what users may change in the document.

3 · SOURCE

The amount needs a source.

For an automatically determined price, discount, or surcharge, pricing can search condition records through the configured access logic. Other condition types can receive their amount from a different supported source or from controlled manual entry.

4 · BASE

The amount and the base are separate inputs.

A percentage is meaningless until we know what value it is applied to. Quantity, monetary value, weight, volume, a previous subtotal, or another calculated basis can all change the result without changing the visible rate.

5 · INTERACTION

Scales, grouping, and exclusion can change the active result.

The selected rate can depend on a scale. A group condition can calculate with several related items. Condition exclusion can leave one valid condition inactive because another one wins.

Pricing procedure

The row tells SAP how this condition participates.

The condition type alone does not explain the document result. The same type only becomes meaningful in the procedure that places it among earlier and later price elements.

Sequence and eligibility

Step order determines what has already been calculated. A requirement can prevent the condition from being considered even when valid master data exists.

Intermediate values

Subtotals and from/to references can make earlier pricing results available to later rows. This is why a wrong upstream value can surface much later in the procedure.

Calculation controls

The row can change the normal calculation base or amount calculation and can mark a price element as statistical or relevant for downstream processing.

A condition record answers “what data was found?” The procedure row answers “what is SAP supposed to do with it here?”

Condition type and condition record

Behavior is configuration; commercial values are master data.

This distinction prevents a common design mistake: using condition records to compensate for a condition type whose calculation behavior is wrong.

Condition type

Defines reusable pricing behavior: for example, whether a value is percentage- or amount-based, how units and currencies are handled, how scales are processed, whether items are evaluated together, and which document changes are allowed.

Condition record

Stores the commercial value for a particular key and validity period when the condition uses condition technique. The key may include attributes such as customer, product, sales area, or another configured field combination.

Access logic

Defines where pricing searches and in which order. A missing result can therefore mean that no matching record exists, that the key differs from what was expected, or that the relevant row never became eligible.

Rate and base

A correct percentage can still produce the wrong amount.

Separate the visible rate from the value to which it applies. This is one of the fastest ways to understand a pricing difference.

Synthetic patterns: the numbers below are illustrative. Use the actual pricing document and analysis data when diagnosing a real case.

Suppose a document shows a 10% discount. If the intended base is EUR 1,000, the discount is EUR 100. If the actual base is EUR 900 because an earlier price element or subtotal changed it, the same 10% produces EUR 90. Changing the condition record would hide the real problem.

For quantity-based prices, the same principle applies to pricing quantity and pricing unit. For freight or other physical measures, weight, volume, and unit conversion can become part of the calculation boundary.

Scales and grouping

The decisive number may be larger than one item.

Scales select a value according to a configured basis and threshold model. Group conditions extend that idea by taking related document items into account when the scale base or condition value is calculated.

From / to scales

The agreement can define a value from a threshold upward or up to a threshold. The first check is therefore the scale basis SAP actually calculated, not only the ordered quantity a user remembers.

Interval logic

Where interval or graduated logic is configured, different parts of the quantity can be evaluated with different scale values instead of applying one value to the full quantity.

Group conditions

Related items can be cumulated for scale determination. A single item may appear too small for a discount while the combined group qualifies for it.

Interaction

“Found” does not always mean “active.”

Several valid pricing elements can coexist. The final set depends on the rules that govern how they interact.

EXCLUSION

Competing conditions can be compared and one can be deactivated.

This is different from a failed search. The condition can be visible in pricing analysis but intentionally excluded from the commercial result.

SUPPLEMENT

A supplement travels with its main condition.

When conditions share the same dependency and validity, SAP can store supplementary conditions with the main condition record and determine them together. The supplement is not an independent search problem.

MANUAL

Manual entry is a separate source of document pricing data.

Whether users may add or change a condition depends on the condition-type and procedure design. A manual value should not be mistaken for evidence that automatic determination worked.

Free Goods

Free-goods determination changes quantity before it becomes a pricing question.

Free-goods determination creates a free-of-charge sales-order item. Inclusive and exclusive free goods differ in what happens to the main item quantity.

First prove the quantity determination; then inspect how the resulting item is priced.

Inclusive

The free quantity is taken from the ordered quantity, so the main item quantity is reduced and the free quantity is represented separately.

Exclusive

The ordered quantity remains unchanged and the customer receives an additional free quantity.

This boundary matters because treating free goods as a normal discount can send the investigation into pricing records when the real question is whether free-goods determination created the expected item and quantity.

Custom calculation

Change only the part the standard model cannot express.

Pricing already separates eligibility, condition amount, calculation base, and final condition value. Keep that separation when custom logic is necessary.

Eligibility

If the business rule decides whether a condition should participate, keep the logic at the eligibility boundary rather than hiding it inside amount calculation.

Base

If the standard rate is correct but the commercial agreement requires a different basis, change the base calculation rather than the master-data value.

Amount

If the arithmetic itself is different, use the supported formula or extension mechanism for the relevant deployment model. Do not assume that a classic routine and a cloud extension point are interchangeable.

For implementation choices and deployment-specific extension patterns, continue with Pricing Configuration.

Reading a pricing result

Explain the difference in one chain.

When two documents price differently, compare the first point where the chain diverges instead of scanning every condition in the document.

01

Same active pricing procedure and same relevant row?

02

Same condition type behavior and same eligibility result?

03

Same source record or manual value, with the same key and validity?

04

Same calculation base, scale level, units, and currency context?

05

Same group, exclusion, supplement, and manual interaction?
