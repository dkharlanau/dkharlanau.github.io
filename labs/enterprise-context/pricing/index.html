Deep vertical / Sales Pricing

Pricing is a determination chain,
not a condition record.

SAP Sales pricing builds a commercial value from document context, a pricing procedure, condition types, access sequences, condition records, and calculation rules. When a price looks wrong, the fastest route is usually to find the first place where that chain differs from the expected design.

The pricing model

The system first chooses a procedure, then works through its conditions.

Current SAP documentation describes pricing procedure determination from the sales area, the customer pricing procedure, and the document pricing procedure. The resulting pricing procedure defines the condition types that can participate and the sequence in which they are processed.

Document context→ Pricing procedure→ Condition type→ Access sequence→ Condition record→ Price element

The distinction matters during support. If the wrong pricing procedure was selected, adding another condition record cannot repair the real cause. If the correct procedure and condition type are present but no record is found, the problem has moved further down the chain into the access sequence, runtime key, validity, or master data.

SAP's current Example of Pricing Process shows this same sequence explicitly: determine the pricing procedure, read its condition types, follow the assigned access sequence, and use the valid condition record that matches the runtime values.

Condition technique

An access sequence is a search strategy.

A condition type can use an access sequence to search several condition tables in a defined order. Each table represents a key combination such as customer and material, a broader customer group, or a more general material price.

Suppose a list price first searches customer + material, then price list + currency + material, then material. If the first access finds nothing and the second finds a valid record, pricing can use the second result. An exclusive access can stop the search after the first successful match. The result therefore depends on the actual runtime key, not on which record looks most specific when viewed separately.

Condition records are pricing master data. They hold values such as prices, discounts, surcharges, freight, or tax-related amounts together with their key fields and validity. SAP's current Sales documentation also supports APIs for condition records, pricing procedures, condition types, access sequences, condition tables, and the pricing field catalog. That separation is useful: the master data and the determination design are related, but they are not the same object.

Condition type and pricing procedure

The condition type defines the commercial role. The pricing procedure defines how that role participates.

We keep these two layers separate. A condition type describes what kind of pricing element we have and how it can calculate. The pricing procedure decides where that condition sits in the calculation, whether it is allowed to run, and how its result is used by later steps.

Condition type

Controls the category of the condition, calculation type, scale basis, plus/minus behavior, manual-entry rules, header/item behavior, and other condition-level properties.

Step and counter

The step controls processing order. The counter lets several conditions sit at the same step, which is useful when manual conditions must keep their entry sequence.

Requirement and formulas

A requirement can stop a condition from participating. Alternative base or amount formulas can change how the condition is calculated after it is found.

Subtotal and flags

Subtotals preserve intermediate results. A procedure line can also be mandatory, manual-only, or statistical. Those flags change runtime behavior without changing the condition record itself.

A common assessment trap is to say that the pricing procedure is only a list of condition types. It is more than a list: it is the calculation sequence and control layer. That is where we see requirements, subtotals, alternative calculations, manual-only logic, statistical conditions, and other rules that explain why the same condition type can behave differently in another procedure.

Lead answer: condition table defines the record key; access sequence defines where we search; condition type defines the pricing element; pricing procedure defines how the elements work together; procedure determination selects the procedure for the document.

Calculation

Finding a record is only the start of the calculation.

The pricing procedure controls how individual price elements interact. Requirements can decide whether a condition is relevant; scales can change a rate; formulas can change the base or amount; subtotals can feed later conditions; and condition exclusion can suppress one result in favor of another.

This is why the useful evidence is the complete price element, not only its rate. A 10% discount can be technically correct and still produce the wrong value if its base is wrong. A condition can be found but inactive. A manual condition can coexist with automatic pricing. Group conditions can also make one item's pricing depend on quantities or values across related items.

Rate

What amount, percentage, or quantity-based rate was determined?

Base

Which value or quantity did the condition use for its calculation?

Interaction

Did a requirement, scale, formula, exclusion rule, subtotal, or group condition change the final effect?

Condition records in daily work

Pricing design and condition maintenance are different jobs.

Condition records hold the commercial data that automatic pricing reads: prices, discounts, surcharges, freight, tax-related values, validity periods, scales, currencies, and units. In S/4HANA, the Manage Prices - Sales app is the practical center for bulk work with those records.

Create and copy

We can create records directly, copy existing records, or create new records with reference. This is useful when a new period or customer group starts from an existing commercial structure.

Mass change

Validity and condition amounts can be changed for many records together. Spreadsheet export and import support larger maintenance sets and controlled updates.

Dynamic keys

The condition type and key combination decide which fields are relevant. The app therefore changes its filters and columns according to the condition design.

Validity overlap

Overlapping validity is not just a visual warning. New or changed intervals can shorten or replace existing intervals, so mass maintenance needs a clear effective-date strategy.

For troubleshooting, we do not start from the maintenance app. We first prove the runtime key in the sales document. Only after we know the exact customer, material, hierarchy, currency, unit, date, and other access fields do we judge whether the maintained condition record is correct.

Special pricing functions

Some pricing questions are about interaction between conditions, not about finding one record.

Group conditions, exclusion, condition update, supplements, and hierarchy pricing all change how individual records combine into a commercial result.

Group conditions

The system can accumulate quantities or values across several items before applying a condition. Standard group-condition routines can work across the full document, all condition types, or a material pricing group.

Condition exclusion

A condition or condition record can trigger exclusion logic. Requirements in the pricing procedure then deactivate later conditions. Exclusion groups can also compare alternatives and keep the configured best or worst result.

Condition update

Cumulative values can be written back and checked against limits such as maximum condition value, condition base value, or number of orders.

Condition supplements

A main condition can bring additional conditions with it. Supplements are maintained together with the main record rather than searched independently through their own access sequence.

Customer hierarchy pricing is another important pattern. A price or rebate agreement can be maintained at a hierarchy node and inherited by lower-level customers. The access sequence decides which hierarchy level is checked first, so the hierarchy path becomes part of the pricing search strategy.

A concrete example

“The condition record exists, but the sales order has no price.”

This symptom is useful because it shows why pricing should be read from the document outward rather than from master data inward.

First confirm which pricing procedure the document actually uses. Then check whether the expected condition type is in that procedure and whether its requirement allows it to run. If the condition type uses an access sequence, pricing analysis should show which accesses were attempted and the field values used for each key. Only then does the existence, validity, currency, unit, and scale of the condition record become decisive.

If the record is found, continue into the calculation. A zero or unexpected value may come from the condition base, a scale, a formula, an exclusion rule, or another condition that changes the result. The diagnosis is complete when we can name the first pricing decision that differs from the expected design—not when we have merely found a table entry that looks plausible.

Manual, header and special conditions

Not every price element comes from an access sequence.

Manual pricing is part of the design. Header conditions, net-price conditions, minimum-price logic, rounding, and statistical conditions each solve a different business problem.

Header conditions

Standard header conditions are entered manually and apply to all items. SAP can distribute the amount by net value, or the procedure can use another base such as gross weight, net weight, or volume.

HM00 and PN00

HM00 sets a manual order value at header level and distributes it to items. PN00 sets a manual net price for one item and deactivates the original item pricing conditions.

PMIN and DIFF

PMIN adds the difference when a material does not reach its minimum price. DIFF handles currency rounding differences and distributes the result as a group condition.

New pricing

Pricing types control what happens when pricing is updated. The same idea is used in sales documents and, through copy control, when billing decides whether to copy or redetermine pricing.

The important distinction is automatic versus manual, not “standard versus exception.” A manual condition can be a designed business control. The question is whether the procedure allows it, whether it replaces or supplements automatic pricing, and whether the same behavior is expected in billing.

Statistical pricing

A statistical condition can be commercially invisible and still be operationally important.

Statistical conditions do not normally change the sales net value, but they can carry cost, comparison, cash-discount, or management-reporting information.

VPRS

Standard SAP uses VPRS to bring material cost into pricing. With condition category G, it reads standard or moving-average cost according to material valuation. Margin logic can then compare cost with net value.

SKTO

SKTO reads the cash-discount rate from payment terms and shows the calculated amount statistically in the pricing procedure.

EDI1 / EDI2

Customer-expected price or value can be compared with the seller's calculated price. A material difference can make the order incomplete until the discrepancy is resolved.

CO-PA relevance

Some statistical price conditions can also be marked relevant for account determination so that their values are available for account-based profitability analysis without changing the Sales net value.

Tax in the pricing chain

Tax uses condition technique, but tax ownership crosses into Finance and external tax services.

In a standard sales scenario, the rate depends on the business transaction and the tax classifications of the customer side and the material. The destination country and partner used for tax determination also matter.

Condition type MWST is a standard example. It uses an access sequence to find the applicable tax condition. For the United States, SAP also documents different tax procedures such as TAXUS, TAXUSJ, and TAXUSX. The exact architecture determines whether Sales calculates the tax itself, uses tax jurisdiction logic, or integrates with a central or external tax engine.

account_balance

Lead boundary: Sales owns the pricing integration point, but it does not mean Sales owns every tax rate. Finance or a tax service can own the tax logic and rates. We diagnose the interface and determination chain before changing SD condition records.

Order and billing

The invoice does not have to repeat the order's pricing calculation.

When a billing document is created with reference to an earlier document, copying control decides how relevant data moves into Billing. Pricing is one of those controls.

SAP's 2025 FPS01 documentation states that, for delivery-related billing, quantities can come from the delivery while prices can come from the sales order. The same copying-control layer can also specify whether pricing is copied or redetermined according to the configured pricing type. Correct pricing in the order therefore does not prove that the billing document will have the same price elements.

This boundary becomes especially important when a billing document has a different pricing date, tax context, custom field, manual condition, or repricing rule. Compare the order and billing document as two pricing contexts and identify the first difference. The Billing guide covers the broader copying-control and invoice lifecycle.

Extensibility

Extend the pricing model at a defined point, not wherever code is convenient.

Pricing extensions are deployment- and scenario-specific. The important design question is which input or calculation the standard model cannot express, and which supported extension point owns that gap.

In SAP S/4HANA Cloud, released key-user extensibility supports custom fields for Sales and Billing pricing communication and custom logic for selected pricing functions such as requirements, condition base values, and condition amounts. Classic and private-edition landscapes can also contain established pricing routines and enhancement patterns. Those mechanisms should not be described as interchangeable across editions.

A custom pricing field also needs an end-to-end path. The business value must exist in the document context, be available to pricing communication, be exposed through the pricing field catalog where required, participate in the condition-table or calculation design, and be populated in every runtime context that depends on it. Creating the field alone does not make it a pricing input.

Process boundaries

Pricing owns the commercial value, not every downstream consequence.

Several neighboring processes consume pricing results, but they answer different questions.

Sales document

Which pricing procedure and runtime context apply, and which price elements are calculated?

Billing

Which pricing elements are copied, retained, or redetermined when the invoice is created?

Finance

How do the resulting billing values feed account determination, receivables, revenue, tax, and other accounting effects?

If the commercial price is correct but the accounting result is wrong, the investigation has crossed out of Pricing. Continue with FI/CO for Logistics rather than changing condition records.

Assessment memory

Explain pricing as a controlled search and calculation pipeline.

For a Lead answer, we should show the order of reasoning. Transaction codes can come later.

record_voice_over

60-second answer: In SAP Sales, pricing starts with pricing procedure determination from sales area, document pricing procedure, and customer pricing procedure. The procedure contains condition types in a controlled sequence. A condition type can use an access sequence, which searches condition tables until it finds a valid condition record for the runtime key. After that, SAP calculates the value using the rate, base, scale, formulas, subtotals, requirements, and exclusion logic. Manual and statistical conditions can participate as designed. When pricing is wrong, I first prove the procedure, then condition eligibility, access, runtime key, record, calculation, and finally billing repricing or custom logic.

Why does a record exist but pricing miss it?

Wrong procedure, condition not eligible, different access key, validity mismatch, currency or unit mismatch, scale issue, or a custom field not present in pricing communication.

Why is the rate correct but value wrong?

Check the condition base, scale base, calculation type, subtotal, alternative base or amount formula, rounding, and group-condition accumulation.

Why is order correct but invoice wrong?

Compare pricing type in copy control, pricing date, runtime fields, manual-condition handling, tax context, and any custom field or formula used in both documents.

Where does CCM fit?

Ordinary SD pricing calculates the current document. Condition Contract Management handles agreements that are settled later against accumulated business volume.
