Deep vertical / Sales Pricing

Pricing is a determination chain,
not a condition record.

SAP Sales pricing builds a commercial value from document context, a pricing procedure, condition types, access sequences, condition records, and calculation rules. When a price looks wrong, the fastest route is usually to find the first place where that chain differs from the expected design.

Assessment recall

Choose → search → calculate → compare.

A strong pricing answer follows the runtime chain instead of starting from a condition record or a table.

record_voice_over

60-second answer: I first confirm which pricing procedure the document uses. Then I check whether the expected condition type is present and allowed to run. If it has an access sequence, I follow the accesses with the actual runtime key until SAP finds or does not find a valid condition record. If the record is found but the result is wrong, I move to rate, base, scales, formulas, exclusion, and interaction with other conditions. For billing differences, I compare the order and invoice as separate pricing contexts before changing master data.

Fast model

Four questions before touching a condition record.

These questions reduce most pricing incidents to the layer that actually owns the result.

1. Which procedure?

Prove the pricing procedure selected for this document context.

2. Which condition?

Check whether the condition type is present, relevant, and allowed to participate.

3. Which source?

Follow the access sequence, runtime key, validity, unit, currency, and scale to the actual value source.

4. Which calculation?

If a value is found, inspect the base, formulas, exclusions, subtotals, scales, and interaction with other conditions.

Agent / MCP investigation

Read the runtime price before you change pricing master data.

Machine assistance is most useful when it preserves the same pricing chain: prove the document result first, then move outward to procedure, access, record, and calculation. A condition record is evidence about master data, not proof that the document selected it.

The pricing model

The system first chooses a procedure, then works through its conditions.

Current SAP documentation describes pricing procedure determination from the sales area, the customer pricing procedure, and the document pricing procedure. The resulting pricing procedure defines the condition types that can participate and the sequence in which they are processed.

Document context→ Pricing procedure→ Condition type→ Access sequence→ Condition record→ Price element

The distinction matters during support. If the wrong pricing procedure was selected, adding another condition record cannot repair the real cause. If the correct procedure and condition type are present but no record is found, the problem has moved further down the chain into the access sequence, runtime key, validity, or master data.

SAP's current Example of Pricing Process shows this same sequence explicitly: determine the pricing procedure, read its condition types, follow the assigned access sequence, and use the valid condition record that matches the runtime values.

Condition technique

An access sequence is a search strategy.

A condition type can use an access sequence to search several condition tables in a defined order. Each table represents a key combination such as customer and material, a broader customer group, or a more general material price.

Suppose a list price first searches customer + material, then price list + currency + material, then material. If the first access finds nothing and the second finds a valid record, pricing can use the second result. An exclusive access can stop the search after the first successful match. The result therefore depends on the actual runtime key, not on which record looks most specific when viewed separately.

Condition records are pricing master data. They hold values such as prices, discounts, surcharges, freight, or tax-related amounts together with their key fields and validity. SAP's current Sales documentation also supports APIs for condition records, pricing procedures, condition types, access sequences, condition tables, and the pricing field catalog. That separation is useful: the master data and the determination design are related, but they are not the same object.

Calculation

Finding a record is only the start of the calculation.

The pricing procedure controls how individual price elements interact. Requirements can decide whether a condition is relevant; scales can change a rate; formulas can change the base or amount; subtotals can feed later conditions; and condition exclusion can suppress one result in favor of another.

This is why the useful evidence is the complete price element, not only its rate. A 10% discount can be technically correct and still produce the wrong value if its base is wrong. A condition can be found but inactive. A manual condition can coexist with automatic pricing. Group conditions can also make one item's pricing depend on quantities or values across related items.

Rate

What amount, percentage, or quantity-based rate was determined?

Base

Which value or quantity did the condition use for its calculation?

Interaction

Did a requirement, scale, formula, exclusion rule, subtotal, or group condition change the final effect?

One condition, one reasoning chain

Read a pricing result from permission to amount.

A rate alone never explains a condition result. We need five questions in order. This replaces the separate mandatory Anatomy reading path.

  1. Place: Is the expected condition type in the active pricing procedure, and does its requirement allow it to participate?
  2. Behavior: What reusable behavior does the condition type define: calculation type, manual behavior, scale basis, plus/minus effect, grouping, or another rule?
  3. Source: Where does the value come from: a valid condition record, manual entry, formula, or another supported source?
  4. Base: Which quantity or value is the rate applied to? A correct percentage on the wrong base is still a wrong price.
  5. Interaction: Do scales, group conditions, exclusion, supplements, statistical behavior, or another condition change whether the result is active and how it contributes?

Compact example: a 5% discount can be found correctly and still produce the wrong amount if the base is wrong, the scale level is different, or an exclusion rule deactivates it. Compare working and failing documents at these five layers before changing condition records.

Configuration path

Configure the rule in layers, then test its lifecycle.

Pricing configuration is easier to review when every layer has one job. This replaces the separate mandatory Configuration Playbook reading path.

  1. Business rule: state who receives the price or discount, for which product and context, from which date, and under which quantity or value condition.
  2. Search key: choose the business fields that identify the commercial record. Do not add dimensions that the business cannot maintain reliably.
  3. Condition type: define the reusable behavior of the price, surcharge, discount, or statistical value.
  4. Access logic: define how SAP searches from more specific to more general records where condition technique is used.
  5. Procedure row: place the condition in the pricing procedure and define sequence, eligibility, subtotals, requirements, and calculation controls.
  6. Commercial data: maintain rates, validity periods, currencies, units, and scales separately from the configuration that interprets them.
  7. Lifecycle test: test creation, quantity/date changes, copying to follow-on documents, billing repricing where relevant, cancellation/correction, and one negative case.

Lead rule: do not solve a master-data problem with configuration, and do not solve a configuration problem with custom code. Use an extension only when the standard model cannot express the rule cleanly and the deployment model supports the extension point.

The detailed sequence and test matrix remain available in pricing-configuration.json.

A concrete example

“The condition record exists, but the sales order has no price.”

This symptom is useful because it shows why pricing should be read from the document outward rather than from master data inward.

First confirm which pricing procedure the document actually uses. Then check whether the expected condition type is in that procedure and whether its requirement allows it to run. If the condition type uses an access sequence, pricing analysis should show which accesses were attempted and the field values used for each key. Only then does the existence, validity, currency, unit, and scale of the condition record become decisive.

If the record is found, continue into the calculation. A zero or unexpected value may come from the condition base, a scale, a formula, an exclusion rule, or another condition that changes the result. The diagnosis is complete when we can name the first pricing decision that differs from the expected design—not when we have merely found a table entry that looks plausible.

Order and billing

The invoice does not have to repeat the order's pricing calculation.

When a billing document is created with reference to an earlier document, copying control decides how relevant data moves into Billing. Pricing is one of those controls.

SAP's 2025 FPS01 documentation states that, for delivery-related billing, quantities can come from the delivery while prices can come from the sales order. The same copying-control layer can also specify whether pricing is copied or redetermined according to the configured pricing type. Correct pricing in the order therefore does not prove that the billing document will have the same price elements.

This boundary becomes especially important when a billing document has a different pricing date, tax context, custom field, manual condition, or repricing rule. Compare the order and billing document as two pricing contexts and identify the first difference. The Billing guide covers the broader copying-control and invoice lifecycle.

Extensibility

Legacy and cloud pricing use different extension contracts.

The business question is the same in every edition: which pricing input or calculation cannot be expressed by standard configuration? The technical answer is different. Classic SAP ERP and many private-edition systems can contain VOFM routines, communication-structure appends, and SD user exits. SAP S/4HANA Cloud Public Edition uses released custom fields, Custom Logic BAdIs, configuration activities, and released developer objects.

Classic / Private Edition

Expect VOFM routines, KOMK/KOMP extensions, and document-specific user exits. These are powerful, but they create upgrade and clean-core responsibilities.

Public Cloud — key user

Use Custom Fields, Custom Logic, and released pricing configuration. A BAdI implementation is mapped to a routine number instead of editing a generated VOFM routine.

Public Cloud — developer

ABAP Cloud development can use only released APIs, released objects, and predefined extension points. Classic includes such as MV45AFZZ or RV60AFZZ are not a Public Cloud extension model.

Migration rule: do not translate old custom code line by line. First classify the intent: add a pricing field, control whether a condition runs, change the base, change the condition amount, change document data, or integrate an external pricing service. Then select the released extension point for that intent.

Legacy technical map

In classic pricing, the communication structures are the main hand-off point.

The pricing engine does not read every sales or billing table directly for every decision. The calling application prepares pricing communication data. Header data is carried in KOMK/TKOMK; item data is carried in KOMP/TKOMP. Requirements, accesses, and formulas work with this pricing context.

  1. Add a field: the classic pattern is to add header fields through KOMKAZ or item fields through KOMPAZ, activate the structures, and add the field to the pricing field catalog.
  2. Populate it at runtime: for sales-order processing, the well-known preparation exits are USEREXIT_PRICING_PREPARE_TKOMK and USEREXIT_PRICING_PREPARE_TKOMP in MV45AFZZ. For billing, the corresponding exits are in RV60AFZZ.
  3. Use it in condition technique: create or extend the condition table, place it in an access sequence, assign that access sequence to a condition type, and use the condition type in the pricing procedure.
  4. Change calculation logic: VOFM provides classic routines for requirements, alternative condition-base calculation, alternative condition-value calculation, and related pricing formulas. Keep customer routines in the customer namespace and document where each routine is assigned.
  5. Transport carefully: classic VOFM changes may require generation in the target system. A common transport pattern includes the XPRA RV80HGEN; follow the release-specific transport procedure used by the landscape.

Preparation exits

USEREXIT_PRICING_PREPARE_TKOMK and ...TKOMP enrich the pricing context before access and calculation. In billing, SAP support guidance recommends using the runtime buffers such as XVBRK/XVBRP where the standard flow requires them.

Pricing-result exits

Classic pricing also exposes exits around XKOMV, including patterns such as USEREXIT_XKOMV_FUELLEN and evaluation exits. Treat these as high-impact code: they can change or suppress results after condition access.

Repricing and copying

Legacy code can influence pricing types and repricing during document changes or copying. Before changing such code, inspect copying control and the configured pricing type, because the standard layer may already own the behavior.

Runtime objects worth knowing: PRICING performs item pricing and PRICING_COMPLETE completes document-level pricing work. Classic debugging often follows the pricing communication structures, the condition list in XKOMV, and the condition-access path. A requirement that fails early can prevent database access completely, so checking the requirement is often faster than debugging the condition table first.

Legacy persistence: in SAP ERP, condition access uses generated A-tables for the search key and the condition record number KNUMH to reach condition data such as KONH, KONP, and scale tables. For business-document pricing results, SAP S/4HANA replaced KONV as the persistence table with PRCD_ELEMENTS. New integrations should use released APIs or CDS views instead of building new direct-table dependencies on the old model.

The legacy patterns above are useful for reading inherited systems and for assessment discussions. They are not a recommendation to introduce new classic exits when a released clean-core extension can solve the same requirement.

Public Cloud extension path

Cloud pricing keeps the condition technique, but replaces the old code-entry points.

SAP S/4HANA Cloud Public Edition supports custom pricing keys and custom pricing calculations through released extensibility. The important design step is to make the field available to pricing communication and then connect custom logic to the pricing procedure through supported configuration.

  1. Create the business field: if the value belongs to a sales document, create it in Sales: Sales Document or Sales: Sales Document Item and enable the business scenario that transfers the field to pricing communication. Pricing-specific fields can also use the released pricing communication business contexts where supported.
  2. Publish and expose it: add the custom field to Change Field Catalog for Pricing in Sales. A field that exists in the UI but is missing from the pricing field catalog cannot become a condition-table key.
  3. Build the condition path: create the condition table, add it to an access sequence, assign the access sequence to the condition type, and place the condition type in the custom pricing procedure.
  4. Use Custom Logic for calculations: implement the released pricing BAdI, assign a unique filter value, register a routine number in the relevant configuration activity, and map that routine number to the requirement, alternative base, or alternative amount field in the pricing procedure.
  5. Expose the same key to integrations when needed: the Condition Record for Pricing in Sales OData API can be extended with supported custom key fields. Enable the custom field for the API and keep the API field, field catalog, condition table, and condition records aligned.

Requirement

Cloud provides released BAdIs PRICING_DOCUMENT_REQUIREMENT for document-level checks and PRCG_DOCUMENT_ITEM_REQUIREMENT for item-level checks. The result controls whether the assigned condition or access participates.

Condition base

Use the released Condition Base Value custom logic when the standard base is not the required quantity or value. The implementation is connected to the pricing procedure by a configured routine number.

Condition amount

Use the released Condition Amount custom logic for an alternative condition amount. Item and group-condition scenarios have separate BAdI handling, and SAP requires the related implementations to be mapped consistently when group conditions are used.

Developer extensibility boundary: Public Cloud developer extensibility is available in a three-system landscape and uses the ABAP Cloud model. Custom ABAP can reference only released SAP APIs and objects and can extend SAP behavior only at released extension points. This is the key clean-core difference from classic direct includes and unrestricted table access.

Side-by-side option: if the pricing rule belongs outside the S/4 core—for example, a shared pricing service used by commerce, CPQ, and sales channels—evaluate SAP Variant Configuration and Pricing or another released integration pattern instead of duplicating pricing logic in several document exits.

Process boundaries

Pricing owns the commercial value, not every downstream consequence.

Several neighboring processes consume pricing results, but they answer different questions.

Sales document

Which pricing procedure and runtime context apply, and which price elements are calculated?

Billing

Which pricing elements are copied, retained, or redetermined when the invoice is created?

Finance

How do the resulting billing values feed account determination, receivables, revenue, tax, and other accounting effects?

If the commercial price is correct but the accounting result is wrong, the investigation has crossed out of Pricing. Continue with FI/CO for Logistics rather than changing condition records.

FAQ / fast repetition

Five questions that separate search, calculation, and downstream effects.

01procedure

The condition record exists, but there is no price. What do I check first?

Start with the pricing procedure used by the document. A valid record cannot help if the expected condition type is missing, inactive, or not reached in this procedure.

02access

Why is another record selected instead of the one I expected?

Read the access sequence with the actual runtime key and access order. Pricing uses the configured search path, not the record that looks most specific when viewed separately.

03base

The rate is correct but the amount is wrong. Where is the problem?

Inspect the condition base, scales, formulas, group behavior, and exclusions. A correct rate applied to the wrong base still gives the wrong commercial result.

04billing

The order price is correct but the invoice price differs. Is Pricing broken?

Not necessarily. Billing can copy or redetermine pricing according to copying control and the billing context. Compare the two documents and find the first pricing-context difference.

05extension

When should I use custom logic?

Only after standard condition technique cannot express the business rule cleanly. First classify the missing capability—field, requirement, base, amount, or external service—then use the extension model supported by the deployment.
