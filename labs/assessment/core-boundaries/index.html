Assessment / Cross-route practice

The hard part starts
at the boundary.

Most difficult incidents are not owned by one module. Two local states can look reasonable while the end-to-end result is wrong. These drills train the handoff: find the first wrong owner before changing the final symptom.

Eight drills

Answer the ownership question before opening the reasoning path.

For oral practice, read the scenario and boundary question first. Give a short answer. Only then compare your path with the expected reasoning.

01Sales Order ↔ Pricing

The price looks wrong after the sales-order context changed

Which upstream sales-order decision can change the pricing path even when the condition record itself is valid?

Scenario

A valid-looking condition record exists, but the price changed after the document context changed.

First answer path

Document context → pricing procedure → condition eligibility → access/runtime key → record → calculation.

Red flag

Creating another condition record before proving the procedure and runtime key.

02Shipping ↔ ATP

Late confirmation: Shipping date or ATP promise?

Is ATP wrong, or is it correctly evaluating the wrong upstream date?

Scenario

Physical stock exists, the requested date is not confirmed, and a route change was introduced recently.

First answer path

Plant → shipping point → route/calendars → material availability date → ATP scope/supply → policy controls.

Red flag

Changing ATP scope before checking the date that ATP actually received.

03Procurement ↔ Inventory ↔ FI

Goods receipt exists, but procurement is not financially complete

Which domain owns the missing business event, and which domain only shows its financial consequence?

Scenario

The PO has a goods receipt and usable stock, but GR/IR is still open after the team believes the purchase is complete.

First answer path

PO history → inventory event → invoice receipt → GR/IR matching → source-document reconciliation.

Red flag

Clearing GR/IR manually before finding the missing or mismatched source event.

04Production ↔ Inventory ↔ FI

Production confirmed, stock missing, cost still open

Which completion layer is open: execution, stock receipt, or financial settlement?

Scenario

Operations are confirmed, the finished quantity is not in expected stock, and order cost is still unsettled.

First answer path

Execution evidence → expected GR → inventory state → warehouse handoff → settlement rule/state.

Red flag

Treating confirmation as proof of goods receipt or financial close.

05QM ↔ Inventory ↔ EWM

Quality accepted the material, but warehouse stock is still unusable

Did Quality make the wrong decision, or did Logistics fail to consume a correct one?

Scenario

The inspection has an acceptance decision, but the operational team cannot use the stock in the warehouse.

First answer path

Inspection context → usage decision → IM stock state → EWM stock/execution → reconciliation.

Red flag

Moving stock manually before proving the intended quality-decision consequence.

06MDG ↔ Sales ↔ Procurement

Master data is approved but the consuming process still fails

Does approval prove consumer usability, or only the governance decision?

Scenario

A Material change is approved and active, but Sales and Procurement still consume an old or incomplete organizational view.

First answer path

Governed requirement → active record → replication/filtering/mapping → target version → process proof.

Red flag

Repairing the target locally without protecting the governed source of truth.

07Integration ↔ Sales Order

The integration monitor is green, but the business object is wrong

Which green status is proven: transport, application processing, or business completion?

Scenario

An inbound sales message is technically successful, but the receiver has a duplicate or incomplete business object.

First answer path

Message identity → delivery → receiver commit → duplicate/order controls → business-object reconciliation.

Red flag

Replaying because the business result looks wrong or closing because middleware is green.

08Shipping ↔ EWM

Delivery exists, but warehouse execution never starts

Is the business demand missing, or is EWM failing to turn valid demand into warehouse work?

Scenario

An outbound delivery is due upstream, but no expected warehouse task is available for picking.

First answer path

Delivery relevance → warehouse request → warehouse task creation → WO grouping/queue → confirmation.

Red flag

Changing the delivery to force EWM before proving the warehouse request.

Board method

Draw four columns, not twelve modules.

For each drill, keep the board small. This makes the ownership change visible and prevents the answer from becoming a configuration dump.

01

Expected state

What business state should exist now?

Write one sentence.
02

Owners

Which domain owns each decision or completion layer?

Draw the handoff.
03

First divergence

Where do expected and actual states first differ?

Do not start at the final symptom.
04

Proof

What evidence proves the cause and the final business completion?

Close with reconciliation.
