Assessment rule: do not answer a broad Sales question as a configuration inventory. Start with the business outcome, name the important decisions and owners, show the process boundary, then add technical detail where it changes the result.

Diagnostic rule: start from the symptom, find the first wrong decision or state, collect evidence, identify the owner, and prove the fix end to end.

90-second anchor

One answer should hold the full Order-to-Cash chain.

Do not memorize every word. Memorize the structure and replace detail when the assessor changes the scenario.

Spoken answer

Order-to-Cash starts with customer demand and ends when both the physical and financial results are complete. In Sales I first define the process variant and the sales-order controls. The order determines partners, product behavior, dates, pricing, availability and credit. Shipping then turns the promise into delivery execution, with EWM or TM at the boundary when they are in scope. Goods issue changes stock and creates accounting impact. Billing creates the customer receivable and revenue posting, while tax and account determination must also be correct.

As a Lead, I do not treat these as isolated SD steps. I ask which rule owns each result, where the first wrong decision appears, which system owns the current state, and how we prove completion. For an incident, I start from the business symptom, trace the document and status chain, compare a few hypotheses, and fix the first wrong decision rather than the last broken document.

What the answer signals

  • Business process before transaction codes.
  • Decision ownership before configuration detail.
  • Physical and financial completion.
  • Cross-domain boundaries instead of an artificial “SD-only” view.
  • Evidence-based diagnosis instead of trial-and-error repair.

Answer depth

Use three speeds, not one giant answer.

The first answer should create a map. Detail belongs in the follow-up.

30 seconds

State the business purpose, the main document chain, two or three controlling decisions, the key boundary, and the completion proof.

Use when: the question is broad or the assessor is checking structure.

2 minutes

Add determination logic, master data, integration points, financial impact, one important process variant, and one design trade-off.

Use when: the assessor asks how the process is designed.

Scenario

Start from the symptom. Build a small hypothesis tree. Find the first wrong decision or state. Name the evidence, owner, fix, regression risk, and proof of business completion.

Use when: the assessor gives an incident or ambiguous requirement.

Oral checkpoint

Ten questions a Sales Lead should answer without opening a page.

  1. 01Explain Order-to-Cash end to end.

    Include the main decisions, physical completion, financial completion, and system boundaries.

  2. 02The price is wrong. Where do you start?

    Separate procedure, condition determination, runtime key, record, calculation, manual change, and billing transfer.

  3. 03The requested quantity or date is not confirmed.

    Separate supply reality from ATP design, policy, master data, and downstream scheduling.

  4. 04A credit block appears unexpectedly.

    Explain exposure, check rule, account or segment, trigger, decision owner, release and recheck.

  5. 05The order exists but delivery cannot be created.

    Check due state, blocks, incompletion, item relevance, dates, quantity, shipping determination, and execution boundaries.

  6. 06Delivery is complete but billing is impossible.

    Trace billing relevance, due state, copy control, status, split logic, blocks, and process-specific prerequisites.

  7. 07Billing looks correct but the accounting result is wrong.

    Move across the SD/FI boundary: account determination, tax, value transfer, posting status, and reconciliation evidence.

  8. 08How does a special Sales process differ from standard sell-from-stock?

    Start from the baseline and name the changed rule: supply, ownership, legal entity, production, stock, billing, return, or settlement.

  9. 09Where does Sales ownership stop?

    Name the handoff to FI/CO, MM, PP, EWM, TM, MDG, tax, or integration operations and explain who owns the next state.

  10. 10How do you diagnose an unfamiliar Sales incident?

    Start from business impact, trace the chain, compare hypotheses, find the first wrong state, fix the cause, and prove end-to-end recovery.

Ownership map

Keep the handoffs explicit.

Many weak answers are technically correct inside one component and still wrong end to end because ownership silently changed.

Commercial decision

  • Sales process and order behavior
  • Pricing and commercial conditions
  • Credit and tax dependencies
  • Customer-facing document controls

Promise and execution

  • ATP or aATP owns confirmation logic
  • Shipping owns delivery preparation and scheduling
  • EWM can own warehouse execution
  • TM can own transport planning and execution

Financial truth

  • Goods issue changes inventory and accounting impact
  • Billing creates the commercial accounting handoff
  • FI/CO owns journal, clearing, settlement and reconciliation
  • Completion needs business evidence, not only a green document status

Integration state

  • Define message or business-object identity
  • Know which system owns durable state
  • Separate delivery from processing and commit
  • Design retry, duplicate control and reconciliation

Assessment red flags

Correct detail can still produce a weak Lead answer.

These patterns usually hide the process instead of explaining it.

Configuration dump

Listing customizing objects without first stating the business decision, runtime result, and owner.

Transaction-code answer

Starting from a screen or transaction instead of the process state and evidence. Useful later, not as the map.

Repairing the last document

Changing delivery, billing, or accounting output before proving where the first wrong decision entered the chain.

“It is an SD issue”

Treating FI, MM, EWM, TM, tax, master data, or integration state as somebody else’s mystery instead of an explicit boundary.

No completion proof

Stopping at document creation without checking the physical, financial, integration, and customer-facing outcome.

No trade-off

Presenting one design as universally correct without naming volume, deployment, legal, operational, or governance constraints.

Practice loop

Read less. Retrieve more.

Use the deep pages to correct gaps, then return to oral practice. Re-reading everything feels productive because humans enjoy progress bars; the assessment rewards retrieval under pressure.
