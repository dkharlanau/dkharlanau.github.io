# API Contracts

> **Status**: Under review.  
> **Scope**: Interface design, compatibility, and lifecycle governance for SAP APIs.

An API contract is the part of an interface that consumers are allowed to rely on. It includes the shape and meaning of requests and responses, supported operations, error behavior, authentication expectations, and the rules for changing the interface over time.

The machine-readable specification is only one part of that contract. OpenAPI can describe an HTTP API. OData metadata describes entities, properties, relationships, and operations exposed by an OData service. WSDL describes a SOAP service. None of those formats, by itself, captures every business meaning or every lifecycle promise a consumer needs.

## The useful question is: what can change without breaking a consumer?

A contract becomes important as soon as producer and consumer can change independently. If a field is renamed, a type changes, an operation disappears, or authorization requirements change, the consumer may fail even though the endpoint is still reachable.

We therefore separate three concerns:

- **interface structure** — resources, entities, fields, operations, types, and payload shape;
- **behavior and semantics** — what an operation means, which states are valid, and how errors are represented;
- **lifecycle policy** — how compatible changes, breaking changes, deprecation, and replacement versions are handled.

This is more useful than treating “the Swagger file” as the whole contract.

## How this maps to SAP

For RAP-based services, a service definition exposes the relevant business entities and a **service binding** connects that definition to a communication protocol such as OData. Current SAP documentation supports OData V2 and OData V4 binding types, while newer tooling also supports explicit versions for OData V4 services. The metadata generated by the service is therefore part of what an OData consumer sees as its technical contract.

For REST-style APIs, SAP Integration Suite API Management supports OpenAPI definitions. SAP's current documentation states that OpenAPI 3.0 definitions can be created or imported and then used to create an API proxy. That proxy is not the business contract itself; it is the managed exposure layer where policies such as authentication, traffic control, or other gateway behavior can be applied.

SAP Business Accelerator Hub is the discovery point for many SAP-provided APIs and their specifications. It helps us understand what SAP has published for a product, but we still need to check the concrete API version, product release, communication scenario, and licensing or enablement requirements before designing a productive integration.

SOAP services have a different technical contract in WSDL and XML Schema. Classic RFC-enabled function modules and BAPIs expose a stable callable signature when used as integration interfaces, but they are not described by an OpenAPI- or OData-style contract. That difference matters when we design governance and automated compatibility checks.

## Compatible and breaking changes

Not every change requires a new API version. Adding an optional response field is often compatible for tolerant consumers; removing a field, changing its type, or changing the meaning of an existing value is much more likely to break them. The real test is the documented contract and the consumer behavior, not a generic semantic-versioning rule applied mechanically.

A practical design review should ask:

- Does the consumer depend on this field, operation, error code, or authorization scope?
- Can old and new consumers run at the same time during migration?
- Is the producer changing structure, or changing business meaning under the same structure?
- Is there a published successor and a clear deprecation path?

SAP API Management includes lifecycle states such as Alpha, Beta, Active, Deprecated, and Decommissioned for API proxies. SAP documentation also requires a date and successor information when a proxy is marked Deprecated or Decommissioned. These states are useful metadata, but SAP explicitly notes that the state itself does not enforce lifecycle governance. Teams still need a real migration process.

## A practical failure example

Assume an external consumer reads an S/4HANA API and treats a property as mandatory because it has always been present. The producer changes the service projection and the property disappears. The HTTP call can still return `200`, but the consumer parser or business logic fails.

The incident is not primarily an “API gateway problem.” We would compare the old and new service contract, identify whether the removed property was part of the supported interface, check the deployed service version, and then decide whether to restore compatibility or move the consumer to a new version. Gateway logs help locate the failure, but they cannot repair a broken business contract.

## Contract tests help, but only for what they encode

Schema-diff checks and consumer contract tests are useful because they turn some compatibility rules into executable tests. They can catch a removed field or changed type before deployment. They cannot prove that a field still means the same business thing, that an authorization change is acceptable, or that an API remains fit for a process after a product upgrade.

That is why mature API governance combines machine-readable specifications, tests, documentation, ownership, and lifecycle decisions rather than relying on one tool.

## Verification limitations

API behavior and lifecycle rules vary by SAP product, release, API type, and deployment model. This page describes the contract model and verified platform capabilities without assuming that all SAP APIs use the same versioning or deprecation policy.
