  <h1>SAP API gateway diagnostics</h1>
  <p class="note-subtitle">Find the layer that made the decision: client, gateway, identity provider, connectivity path, or backend service.</p>
  <div class="atlas-pill-row">{% include atlas/status-badge.html %}</div>
</header>

<div class="note-body">
  <h2>The problem is not the HTTP code alone</h2>
  <p>A gateway sits between the consumer and the backend, so the same HTTP status can come from different places. A 401 may be generated by the gateway or the backend. A 404 may mean a wrong public route, a wrong target path, or a backend resource that does not exist. A 5xx response may be a policy failure, connectivity problem, timeout, or application error.</p>
  <p>The first diagnostic goal is therefore to identify which component produced the response and whether the request reached the backend at all.</p>

  <h2>Classify the decision layer</h2>
  <div class="decision-table"><table><thead><tr><th>Layer</th><th>Question</th><th>Evidence</th></tr></thead><tbody>
    <tr><td>Consumer</td><td>Was the expected method, URL, headers, credential, and payload actually sent?</td><td>Request trace, timestamp, correlation ID, client configuration.</td></tr>
    <tr><td>Gateway route</td><td>Did the public path resolve to the intended API proxy and backend target?</td><td>Proxy revision/configuration, route match, target URL, environment.</td></tr>
    <tr><td>Identity</td><td>Was the credential valid for this API and operation?</td><td>Token/certificate details, issuer, audience, scopes or roles, expiry, identity log.</td></tr>
    <tr><td>Gateway policy</td><td>Did quota, threat protection, transformation, validation, or another policy reject or change the call?</td><td>Policy execution trace, fault name, transformed request/response.</td></tr>
    <tr><td>Backend connectivity</td><td>Could the gateway reach the target within the expected time?</td><td>Connection result, DNS/TLS/connectivity evidence, target latency.</td></tr>
    <tr><td>Backend application</td><td>Did the target receive the request and reject or fail it?</td><td>Backend log, application error, business object result.</td></tr>
  </tbody></table></div>

  <h2>A practical diagnostic workflow</h2>
  <ol>
    <li><strong>Capture one failing call.</strong> Keep method, public URL, relevant headers, payload shape, consumer identity, timestamp, response status/body, and correlation ID. Redact credentials rather than copying secrets into a ticket.</li>
    <li><strong>Find the same call in gateway tracing or analytics.</strong> Confirm whether the gateway received it and which proxy or route handled it.</li>
    <li><strong>Locate the first failing policy or target step.</strong> Do not change authentication, quotas, and routing at the same time. Establish the first decision that differs from a working call.</li>
    <li><strong>Compare with the backend.</strong> Use an approved direct or internal test only when architecture and security allow it. The point is to separate gateway behavior from backend behavior, not to create a bypass around production controls.</li>
    <li><strong>Check identity context.</strong> Validate the credential type, token lifetime, audience, scope/role expectations, and any product-specific identity mapping.</li>
    <li><strong>Check transformations and policies.</strong> A gateway may rewrite paths, headers, query parameters, payloads, or responses. Compare what the consumer sent with what the backend received.</li>
    <li><strong>Confirm the business result.</strong> A technically successful 2xx response is not enough if the target did not create, update, or return the intended object.</li>
  </ol>

  <h2>Rate limits are a capacity decision</h2>
  <p>When legitimate traffic is throttled, increasing the quota is only one option. First understand expected peak volume, retry behavior, concurrency, consumer segmentation, and backend capacity. A higher gateway limit can simply move the overload one component downstream.</p>

  <h2>Useful actions after the failing layer is proven</h2>
  <ul>
    <li>Correct the public route or target mapping when the request reaches the wrong backend.</li>
    <li>Correct identity or authorization configuration when the credential is valid but not valid for this resource.</li>
    <li>Adjust validation or transformation policy when the gateway changes a valid request into an invalid one.</li>
    <li>Tune quotas together with expected traffic and backend capacity rather than removing protection broadly.</li>
    <li>Escalate backend errors with the exact request context and correlation evidence instead of a generic “gateway 500” ticket.</li>
  </ul>

  <h2>What to capture first</h2>
  <p>Record the API/proxy, environment, consumer, timestamp, correlation ID, method and path, HTTP status, sanitized response body, failing policy or target step, and whether the backend received the request. A useful ticket makes the ownership boundary visible.</p>

  <h2>Limitations and boundaries</h2>
  <p>“API gateway” can mean SAP Integration Suite API Management, another SAP component, a hyperscaler gateway, or a third-party platform. Product features, policy names, tracing, identity options, and deployment models differ. This page provides the diagnostic structure; verify product-specific configuration before changing policies or security settings.</p>
