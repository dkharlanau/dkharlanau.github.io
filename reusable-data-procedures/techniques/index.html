Techniques & field notes

Small rules that save large amounts of boring work.

Repeated data tasks are rarely difficult because of one complex algorithm. They are difficult because dozens of small ambiguities appear together: the header moved, an ID became numeric, a lookup is no longer unique, or somebody added a Total row and called it progress.

These techniques are building blocks for the framework. Each one should be observable, testable and easy to explain.

Field rulePrefer several weak signals over one clever guess.

A filename, one header match or one sample row can lie. A combination of structure, values, history and business rules is usually safer.

Discovery

Know what arrived before deciding what to do with it.

Fingerprint first

Before reading every row, capture file size, hash, workbook sheets, dimensions, table names, headers, basic types and a small safe sample. Fast fingerprints make source matching cheaper.

Role beats filename

Resolve a source to a logical role such as sales_orders or material_master. Filenames are only one signal because people rename files with remarkable creativity.

Sample, then prove

Use a sample for discovery and candidate ranking. Before execution, validate the selected rule against the full relevant dataset.

Compare with history

A previous approved run is valuable evidence. Compare current headers, types, cardinality and row-count ranges with the last good runs.

Detect near-empty sheets

Ignore cover sheets and instruction tabs only after confirming that they contain no required structure. A single hidden data table can make this assumption expensive.

Keep a structural diff

Added column, renamed column, type shift and lost key uniqueness are different kinds of drift. Report them separately.

Finding cells and tables

Use anchors, scoring and boundaries.

Anchor sets

Search for a set of expected labels rather than one cell. Three headers found near each other are much stronger evidence than one Material cell somewhere in the workbook.

Alias dictionary

Keep approved aliases per business field. Example: Sales Document, Sales Doc., VBELN. Do not place all similar words into one global synonym soup.

Row score

For each candidate row, score known labels, non-empty text cells, duplicate labels, merged cells and whether stable data appears below it.

Column score

Candidate key columns often have high completeness, stable format and high uniqueness. A description column tends to have lower uniqueness and longer text.

Region grow

After finding the header, grow the region down and sideways while row width and value density remain stable. Stop on controlled boundaries.

Coordinate fallback

If a vendor file has no better signal, fixed coordinates are acceptable. Mark the locator as fragile and protect it with header checks.

Locator scoring

A simple score is often enough.

The exact weights should be configurable and validated on real files.

header_score =
    0.40 * required_header_matches
  + 0.20 * optional_header_matches
  + 0.15 * text_density
  + 0.15 * stable_rows_below
  + 0.10 * historical_position_similarity
  - 0.20 * duplicate_header_penalty
  - 0.20 * narrative_text_penalty

accept automatically only if:
  score >= threshold
  AND all critical headers are present
  AND region validation passes
Important: confidence is not permission. A high locator score can choose a table candidate, but business validations still decide whether the run may continue.

Cleaning patterns

Build comparison keys without destroying display values.

Dual representation

Keep Customer = "0004711" for output and Customer__key = "0004711" for comparison. Normalization can change the key without rewriting the display field.

Normalize whitespace early

Trim spaces and normalize known non-breaking spaces before duplicate detection. Invisible characters are excellent at creating visible meetings.

Parse after classification

Do not immediately cast every numeric-looking value. First decide whether the field is an identifier, measure, amount, quantity or date-like value.

Locale is metadata

Store decimal, thousands and date conventions in the source contract. Locale should not be guessed from one suspicious cell.

Leading zeros are semantic

If "0010" is an item number, converting it to 10 is a business change. Preserve text unless the field contract says otherwise.

Normalize for joins

A join can use a normalized key while the output keeps original values. This makes reconciliation easier when users ask why two rows matched.

Never invent precision

If Excel already converted a long identifier to scientific notation and lost digits, stop or quarantine. Formatting cannot restore missing information.

Keep rejected parse values

A failed date or number parse should produce an exception with raw value and rule ID, not quietly become null.

Clean columns independently

One bad amount should not prevent safe trimming of a customer field. Stage-level policy decides whether the whole run stops.

Mapping and joins

Do not trust matching names without checking values.

Name + values + cardinality

A mapping is stronger when field names are similar, values overlap and the target behaves like the expected key.

Cardinality before join

Check one-to-one, many-to-one and many-to-many behavior before execution. An accidental many-to-many join can multiply rows without producing an obvious error.

Coverage is not enough

98% lookup coverage looks good until the missing 2% contains the largest values. Report unmatched count and business impact where possible.

Alias maps need ownership

Customer A → Group X may be a business mapping, not cleaning. Store who approved it and its validity period.

Composite keys are normal

Document alone may not identify a row. Use Document + Item, Plant + Storage Location or another explicit compound key when needed.

Join keys need normalization symmetry

If the source key is trimmed and zero-normalized, apply the same comparison policy to the target. One-sided cleanup creates mysterious misses.

Validation gates

Check shape, relation and business meaning at different levels.

Gate 1 · Source

Expected file role, sheet, headers, types and structural fingerprint are compatible.

Gate 2 · Extraction

Header is unique, region is plausible, required columns exist and no accidental footer is included.

Gate 3 · Data quality

Required fields, parse success, uniqueness and accepted value domains satisfy policy.

Gate 4 · Relations

Lookup coverage and cardinality are within approved limits. Ambiguous mappings are blocked or routed to review.

Gate 5 · Reconciliation

Counts, totals or control sums compare with source expectations. This catches technically valid but incomplete extracts.

Gate 6 · Publish

Only approved result states reach Outbox. Warning, review and failure states remain visible in Evidence.

Drift techniques

Repair the procedure carefully, not the current file secretly.

Alias repair

Material Number becomes Material No. and the rest of the structure matches. Propose an alias update.

Position repair

The table moved from row 7 to row 12 but anchors still match. The locator can adapt without changing business logic.

Type drift

An ID that was text becomes numeric. Do not auto-cast until the identifier policy confirms that no information is lost.

Cardinality drift

A lookup key that was unique now has duplicates. Treat this as breaking or business drift, not a harmless format change.

Semantic drift

The same column name can change meaning after a system or process change. Technical fingerprinting cannot solve this alone.

Repair creates a revision

Approved v1.3 stays reproducible. The accepted repair becomes v1.4 with reason, evidence and reviewer.

Field notes

Rules I would keep visible in the project.

Use three real files before calling a pattern stable

One sample proves almost nothing about month-to-month drift.

Store source coordinates for exceptions

Sheet + row + column lets a user return to the exact place that caused a problem.

Every exception needs a reason code

Free-text notes are useful, but reason codes make repeated problems measurable.

Measure manual touch rate

A reusable procedure is improving when fewer rows and fewer structural changes need manual decisions.

Keep canary rules

A few cheap checks such as row-count band, key uniqueness and amount total can catch large failures early.

Prefer explicit thresholds

"Mostly matched" is not a control. "Coverage must be ≥ 98%, otherwise block" is.

Separate warning from failure

An added optional column can be a warning. A missing key field should normally block the run.

Make exceptions reusable too

If the same exception appears every month, it needs a rule, reference record or documented accepted exception.

Do not let AI hide uncertainty

If a semantic suggestion is weak, expose the evidence and confidence. A confident sentence is not stronger data.
