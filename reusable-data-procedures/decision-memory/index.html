Decision memory

Keep the reason, not only the result.

A mapping or exception is hard to trust when nobody remembers why it was approved. Decision Memory stores the business decision, scope, evidence and resulting asset change so future runs can reuse the answer and future reviewers can challenge it.

OverviewReview InboxDecision MemoryReference DataGovernance

Core object

A decision is a governed fact about context.

01Question

What uncertainty was resolved? Keep it precise enough to distinguish similar future cases.

02Decision

Accepted action, rejected alternatives and whether the decision is permanent, temporary or case-specific.

03Scope

Concept, source family, system, company, procedure, reference dataset or other boundaries where the answer applies.

04Evidence

Run IDs, hashes, metrics, safe examples, source contracts, business confirmation and related decisions.

05Validity

Effective dates, review date, expiry, confidence and assumptions that would invalidate the decision.

06Outcome

Which procedure, block, concept, reference dataset, validation or exception policy was created or changed.

Store reusable intent with a small vocabulary.

Applicability

Do not generalize a local answer into a universal rule.

A decision should declare where it applies. A customer mapping confirmed for one legal entity or source system is not automatically valid for every company code, sales organization or migration stream.

Global concept rule

Valid for the semantic concept unless a narrower binding overrides it.

Source-family rule

Valid only for one export, interface, vendor format or workbook family.

Procedure rule

Valid only inside one procedure or procedure pack.

Reference-data rule

Valid for one governed mapping dataset and released version range.

Organization rule

Limited to company, sales organization, plant, purchasing organization or another business scope.

One-run exception

Applies only to one execution and should not influence future automatic decisions.

Negative knowledge

Remember what was rejected too.

Discovery becomes safer when it can retrieve previous rejections. If Customer and Sold-to Party were reviewed and rejected as equivalent for one source family, a later AI or fuzzy matcher should see that negative evidence instead of proposing the same shortcut again.

Rule: accepted and rejected decisions are both reusable evidence. Absence of an approval is not the same as an explicit rejection.

Decision ageing

Business truth can expire.

Permanent until changed

Stable structural or semantic decisions with no planned expiry.

Effective-dated

Rules or mappings valid only for a known business period.

Review by date

Decision stays active but loses freshness after a defined review date.

Hard expiry

Temporary exception becomes invalid automatically and must not silently continue.

Storage rule

Memory should contain evidence references, not a shadow data lake.

Decision records should normally store hashes, safe samples, metrics and links to retained run evidence. Raw production rows remain governed by the run and data-retention policy. A decision registry that copies sensitive data into every record is merely a new leakage surface with excellent documentation.
