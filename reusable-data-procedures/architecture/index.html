Architecture & libraries

Separate discovery, execution and control.

The runtime executes an approved procedure. A deployment decides where and when it runs. A run records what happened. The catalog makes reusable assets discoverable, while governance controls promotion and policy.

OverviewCatalogBlocksDeployment & RunTestingGovernanceArchitecture

Contract boundary

Three runtime objects with different change reasons.

ObjectOwnsTypical change
ProcedureBusiness and data logicKey semantics, parsing rule, mapping, validation or output meaning changes.
DeploymentEnvironment and operationSchedule, folder binding, destination, retry, concurrency or policy profile changes.
RunImmutable execution evidenceNever edited as normal configuration; a new execution creates a new run record.

Logical layers

One platform, replaceable responsibilities.

Source adapters

Read Excel, CSV, Parquet and later enterprise sources. Convert them into a common tabular representation while keeping source metadata.

Profiler + locator

Build structural fingerprints and find the intended data region using tables, names, anchors, scoring and controlled fallbacks.

Discovery engine

Generate candidate keys, mappings, aliases and source-role matches. Combine deterministic signals with optional semantic or AI signals.

Procedure compiler

Turn approved choices, source contracts and reusable block references into a deterministic execution graph.

Execution engine

Apply cleanup, joins, filters, conversions, derived fields, aggregations and exception routing without depending on an LLM.

Validation engine

Run structural, relational, reconciliation and business checks. Produce machine-readable evidence and publication decisions.

Catalog & registry

Index procedures, blocks, patterns, packs, deployments, test cases and reference datasets by stable ID and metadata.

Dependency graph

Track shared blocks, reference data, deployments, tests and consumers. Use the graph for impact analysis, deprecation and test selection.

Deployment & orchestration

Resolve triggers, environment bindings, secrets references, idempotency, retry, concurrency and atomic publication without changing procedure logic.

Run evidence store

Keep immutable run identity, input hashes, resolved versions, plan hash, drift, validations, exceptions, control totals and output hashes.

Test corpus & compatibility

Manage golden, drift, mutation and historical replay cases for procedures, blocks and engine versions.

Governance & policy

Control lifecycle, trust evidence, policy profiles, promotion, review freshness, allowed environments and higher-risk changes.

Interfaces

CLI first, then API and UI. Agents become clients of the same catalog and execution service rather than receiving a private execution path.

Candidate stack

Choose libraries by responsibility.

This remains a working shortlist, not a dependency lock file. Keep adapters thin enough to replace a library when requirements change.

Polars

Strong candidate for the main Python dataframe runtime, especially for columnar operations and lazy execution.

DuckDB

Good embedded SQL engine for joins, aggregations, CSV/Parquet work and analytical steps.

Apache Arrow / PyArrow

Useful common in-memory and interchange layer. Parquet is a good internal artifact format for larger intermediates and fixtures.

openpyxl

Python adapter when workbook-level XLSX details matter. Keep it at the boundary; the core model should not depend on Excel cell objects.

SheetJS CE

Candidate for a future browser client that needs local spreadsheet reading or preview. It is an input adapter, not the procedure engine.

RapidFuzz

Useful for field-name similarity and alias matching. Fuzzy similarity remains one signal, never proof of semantic equality.

Pandera

Good fit for code-centric dataframe schema checks close to the Python runtime.

Great Expectations

Consider when validation becomes a larger governed capability with reusable suites and persisted validation evidence.

Pydantic + JSON Schema

Use for procedure, deployment, run and block contracts, API validation and migrations between spec versions.

FastAPI

A reasonable service boundary later: catalog entries, deployments, runs, reports and approvals become explicit resources.

Runtime choice

Start Python-first. Keep browser execution optional.

ModelGood forTrade-off
Local Python CLIFast development, sensitive local files, repeatable tests, manual or desktop runs.Distribution and environment management need work.
Python serviceCentral catalog, controlled dependencies, scheduling, audit, RBAC and larger files.Files leave the user's browser and need an approved security model.
Browser / WASMLocal-first discovery, privacy-friendly previews and lightweight runs.Memory, browser APIs and library compatibility limit the workload.
HybridProfile locally, send only allowed metadata for semantic assistance, execute approved jobs in a governed runtime.More moving parts, but often a strong enterprise boundary.
Starting point: Python package + CLI + JSON contracts + Git-backed catalog + synthetic test corpus. Add shared orchestration only after manual local execution is reliable.

Enterprise concerns

The boring parts decide whether this can be used.

Security

File classification, encryption, temporary storage, deletion policy, secrets references, approved AI endpoints and dependency review.

Audit

Procedure, deployment and block versions, run ID, source fingerprints, validations, exceptions and output hashes.

Operations

Idempotency, concurrency, retry boundaries, atomic publication, run comparison and actionable notifications.

Change impact

Dependency graph, test corpus, consumer links, replacement chains and pinned versions make shared changes reviewable before rollout.
