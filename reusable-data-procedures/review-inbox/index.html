Human-in-the-loop

Do not ask a human twice for the same decision.

A review queue is useful only when a decision can become reusable knowledge. The framework should capture the signal, evidence, decision and resulting asset change instead of leaving the answer in chat, email or memory.

OverviewCatalogReview InboxDecision MemoryGovernance

Loop

Signal → Review → Decision → Change → Test → Reuse

The queue is not an error log. It is the place where uncertain execution is converted into controlled knowledge.

Signal

A run detects ambiguity, breaking drift, a mapping gap, an unmatched reference value or a policy question.

Review item

Create one structured item with context, evidence, affected assets, candidates and the decision that is needed.

Decision

A reviewer accepts, rejects, limits or redirects the proposed action with a clear scope and reason.

Proposed change

The decision may create a procedure revision, concept binding, reference-data change, validation update or temporary exception.

Test and approve

Behavior-changing changes go through the relevant fixtures, impact analysis and approval policy.

Reuse

Later runs use the approved asset and should not reopen the same question unless the context or evidence changed.

Review item types

Different uncertainty needs different treatment.

Item contract

Show enough evidence to decide without reopening the whole workbook.

Identity

Review ID, type, status, severity, created time and responsible queue.

Context

Procedure, deployment, run, source role, semantic concept and affected dependency references.

Evidence

Hashes, structural facts, safe samples, counts, confidence components and relevant rule results.

Question

One explicit decision request. Avoid a generic “please investigate” item that transfers all thinking to the reviewer.

Candidates

Possible actions with evidence, expected effect and risk. A suggestion is not an approval.

Deadline

Optional due date and business impact when a blocked operational run needs priority.

Queue views

Prioritize by impact and recurrence, not by who complained last.

Blocked runs

Items that prevent publication of an operational or business-critical result.

Recurring exceptions

The same reason or value appears repeatedly. This is a strong signal that reusable logic is missing.

Drift clusters

Several source changes may come from one upstream template release and should be reviewed together.

Reference gaps

Unmatched values grouped by dataset, concept, frequency and business impact.

Stale decisions

Temporary exceptions or assumptions that reached their review or expiry date.

High-impact changes

Review items touching shared blocks, concepts or reference datasets with many downstream consumers.

Practical ranking: combine blocking impact, business criticality, recurrence, affected consumers and due date. Confidence alone is not priority.

Override discipline

“Continue anyway” needs a contract.

A manual override should record scope, reason, approver, affected rule, expiry and whether publication remains allowed. It must not silently rewrite the approved procedure or reference data.

Rule: a repeated temporary override is evidence that the normal procedure, validation policy or upstream contract needs a real change.

SAP example

Material 4711 should not become a monthly debate.

A sales export contains 4711. The target source contains 000000000000004711. The review item should show the semantic concept, both raw representations, source systems and possible actions. If the decision confirms that this is only an approved representation rule, the result becomes a reusable normalization block or concept rule. If the values belong to different value spaces, the decision creates or updates governed reference data instead.
