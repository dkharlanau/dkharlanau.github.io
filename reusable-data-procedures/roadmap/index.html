Detail 04 / Roadmap

Prove the procedure before building the platform.

The main risk is not technical. It is creating a flexible data tool without a clear reusable object. Development should therefore start with the procedure contract, cases and deterministic runtime.

OverviewApproachProcedure ModelArchitectureRoadmap

Phase 0

Build the language first.

Before a UI, collect repeated data-work cases and force them into one procedure model.

Deliverable

Procedure spec v0.2

Sources, mappings, transforms, validations, outputs, provenance, versioning and run-report separation.

Deliverable

Case library

10–20 realistic examples: SAP exports, master-data reconciliation, vendor lists, migration extracts and recurring operational reports.

Test

Can the model express the work?

If a case immediately requires arbitrary code, decide whether the model is missing an operation or the case should use an explicit extension.

Exit

Stable vocabulary

Different cases can be discussed using the same source-contract, mapping, transform, validation and drift concepts.

Phase 1

Make it run locally.

Core

Python package

Procedure parser, source resolution, transform compiler, validation engine and run-report generator.

Interface

CLI

discover, validate-procedure, run, compare-source and explain-run. No web server required.

Quality

Golden cases

Small synthetic fixtures with expected outputs, failures and drift scenarios. Every procedure feature gets regression evidence.

Exit

Repeatability

The same inputs and procedure version produce the same outputs and run evidence.

Phase 2

Add discovery and repair.

Discovery

Profiling and key candidates

Structural fingerprints, uniqueness, nulls, value patterns, safe samples and source-role matching.

Mapping

Evidence scoring

Header similarity, overlap, type compatibility, cardinality and approved dictionary matches remain separate signals.

Drift

Compatibility engine

Classify changes as compatible, resolvable or breaking. Generate a proposed revision rather than silently modifying the saved procedure.

Exit

Less manual work on run two

The system reuses known structure and only asks about meaningful changes.

Phase 3

Build the service around the engine.

Registry

Procedure lifecycle

Draft, review, approved, deprecated. Add owners, tags, versions, change notes and dependency references.

API

Run and discovery resources

Expose procedures, discovery sessions, source profiles, runs, reports and approvals through a stable service contract.

UI

Review, do not hide

The interface should make mappings, evidence, drift and exceptions easy to inspect. A big green Run button is not a governance model.

Exit

Shared use

Several users can reuse the same approved procedure with controlled versions and audit history.

Phase 4

Add enterprise controls.

Security

Deployment profiles

Local-only, internal service and hybrid execution. Define data retention, encryption, access, secrets and AI endpoint policy.

Operations

Observability

Run status, duration, input size, validation trends, drift frequency, failure categories and output lineage.

Integration

Enterprise sources

Object storage, SFTP, APIs, database queries and later SAP-specific adapters without changing the core procedure contract.

Exit

Governed runtime

The tool can be operated, audited and supported instead of living as a clever consultant utility.

Phase 5

Use AI where it reduces uncertainty.

Semantic

Column and source meaning

Explain unfamiliar fields using metadata, enterprise dictionaries and controlled samples.

Retrieval

Find similar procedures

Search approved procedures, mappings and validation patterns before proposing something new.

Assist

Suggest rules

Propose mappings, transforms or validations with visible evidence and confidence decomposition.

Boundary

No hidden execution

Once accepted, a suggestion becomes normal procedure logic. Repeated runs do not depend on free-form model reasoning.

Evaluation

Measure whether reuse actually improves work.

MetricQuestion
Time to first procedureHow much work is needed to turn an unfamiliar file bundle into an approved definition?
Time to repeat runDoes the second run require materially less human effort?
Mapping precisionHow often are top relation candidates accepted by a domain user?
Drift detection recallDoes the system catch changes that would alter output meaning?
False blocking rateHow often does harmless drift stop a valid run?
Procedure portabilityCan the same definition run through CLI, service and scheduled execution?
Audit completenessCan a reviewer explain which inputs, rules and procedure version produced an output?
