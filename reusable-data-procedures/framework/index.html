Operating framework

Make messy file work predictable.

A reusable procedure needs more than a list of transformations. It needs a workspace contract, rules for finding data inside files, a cleaning discipline, validation gates and a clear place for exceptions.

The framework treats every repeated Excel or CSV task as a controlled pipeline: Intake → Inspect → Locate → Extract → Clean → Relate → Transform → Validate → Publish → Learn.

Operating rule Never destroy the evidence that explains a result.

Keep the original input, record what was detected, make changes explicit, and separate automatic repair from business decisions.

Workspace contract

A folder structure is part of the procedure.

The names are not sacred. The responsibilities are. The same model can later map to SharePoint, S3, object storage or a managed service.

Inbox/

New files arrive here. Treat them as read-only. A procedure may copy or reference them, but it should never edit them in place.

Staging/

Run-specific copies, unpacked archives and technical conversions. Everything here can be rebuilt from Inbox plus the procedure.

Quarantine/

Unreadable, ambiguous, password-protected or structurally unsafe sources. Quarantine is a result, not a crash.

Reference/

Controlled lookup files, dictionaries, code lists and approved mappings. Reference data has its own owner and version.

Procedures/

Versioned definitions of source contracts, locators, cleaning rules, mappings, validations and outputs.

Work/

Intermediate tables and temporary artifacts. Useful for debugging, but never the final source of truth.

Outbox/

Published files or datasets only. A failed or review-required run should not quietly publish here.

Evidence/

Run manifest, file hashes, profiles, drift report, validation results, exception rows and procedure version.

Archive/

Optional retention area for immutable run packages or manifests. Retention depends on data classification, not convenience.

Run lifecycle

Ten stages, each with a clear gate.

A stage should have an input, an output and a reason to stop. Otherwise the pipeline becomes one long function that nobody wants to debug.

  1. 00Intake

    Assign run ID, hash files, identify source role candidates and capture arrival metadata.

  2. 01Inspect

    Read workbook structure: sheets, tables, named ranges, hidden content, dimensions, formulas and obvious anomalies.

  3. 02Locate

    Find the real data region. Do not assume that the table starts in A1 or that the first non-empty row is the header.

  4. 03Extract

    Turn the selected region into a logical table while preserving source coordinates and raw values where useful.

  5. 04Clean

    Normalize representation: whitespace, nulls, types, dates, numbers and comparison keys. Keep business changes separate.

  6. 05Relate

    Resolve keys, mappings and lookup relationships using evidence, cardinality and controlled reference data.

  7. 06Transform

    Apply explicit filters, derives, lookups, aggregations, deduplication and routing rules.

  8. 07Validate

    Check structure, row counts, uniqueness, coverage, domains, reconciliation totals and business invariants.

  9. 08Publish

    Create the output and exceptions. Publication is allowed only if the run state satisfies the procedure policy.

  10. 09Learn

    Turn confirmed manual fixes into aliases, rules or a new procedure version. Do not silently change an approved version.

Excel locator

Find meaning before coordinates.

Cell coordinates are fragile. A useful locator uses the strongest available signal and keeps fallbacks for weaker ones.

1. Excel table

If the workbook contains a named table with the expected columns, use it. This is usually stronger than guessing a range.

2. Named range

A stable business-defined range can be a good locator, but still validate its shape and headers.

3. Semantic anchors

Search for expected header labels or aliases such as Material, Customer, Plant or Document. Use several anchors, not one word.

4. Header scoring

Score candidate rows by text density, unique labels, known aliases, non-empty rows below and a change from header-like text to data-like values.

5. Region geometry

Look for a dense rectangle with stable column count and blank boundaries. Useful when headers are weak but the table shape is clear.

6. Fixed coordinates

Use A7:H500 only as a controlled fallback. If coordinates are the main locator, drift risk should be visible.

Locator rule: save the strategy, evidence and fallback order. Do not save only the final cell range found during one run.

Header and region heuristics

Useful signals for ugly workbooks.

Header density

A likely header row has several non-empty text cells and few long narrative values.

Known aliases

Maintain a dictionary: Material / Material No. / MATNR / Product. An alias is evidence, not automatic semantic truth.

Data below

A good header candidate is followed by rows with stable value types and similar width.

Blank boundaries

Two or more empty rows or columns often separate sections. Treat this as a signal, not a universal rule.

Repeated headers

Exports may repeat the header after page breaks. Remove only rows that match the confirmed header fingerprint.

Footer detection

Totals, report timestamps and notes often sit under the table. Route them separately instead of deleting anything below the first blank row.

Multiple tables

One sheet may contain several blocks. Discover regions first, then decide which region has the required source role.

Hidden content

Hidden sheets, rows and columns can be either noise or business logic. Record their presence before deciding to ignore them.

Merged cells

Merged titles are common above tables. Fill-down is acceptable for structural headers only when the locator rule explicitly allows it.

Cleaning discipline

Separate representation cleanup from business transformation.

This distinction matters. Trimming a non-breaking space is not the same kind of decision as changing a customer code.

Layer 1

Raw value

What the source actually contained. Preserve it where traceability matters.

Layer 2

Canonical value

A stable representation used for comparison and joins: trimmed text, explicit nulls, parsed dates, normalized numeric representation.

Layer 3

Business value

A value changed by an approved rule: code conversion, status mapping, unit conversion or master-data substitution.

Whitespace

Trim outer spaces and detect non-breaking or unusual Unicode spaces. Keep aggressive Unicode normalization opt-in.

Nulls

Define which source tokens mean null: blank, N/A, NULL or dash. Never treat zero as empty without a business rule.

Identifiers

Read business IDs as strings unless arithmetic is meaningful. Preserve leading zeros and do not recover digits already lost by Excel.

Dates

Use an explicit locale and accepted formats. Ambiguous values such as 03/04/2026 should trigger a rule or review.

Numbers

Decimal and thousands separators need an explicit locale. A comma can mean decimal, thousands separator or text punctuation.

Case

Use case-folded comparison keys when useful, but keep the display value unless the output contract requires another form.

Formulas

Decide whether a procedure needs formulas, cached results or both. A workbook calculated on another machine may contain stale cached values.

Units

Do not compare 1.2 kg with 1200 g before unit semantics are known. Unit conversion belongs to business transformation, not generic cleanup.

Totals

Do not silently delete subtotal and total rows. Detect and classify them, because they can also be useful reconciliation evidence.

Procedure sketch

Store intent, not a macro recording.

A human-readable definition could look like this. The exact DSL can change later.

workspace:
  inbox: Inbox/
  quarantine: Quarantine/
  outbox: Outbox/
  evidence: Evidence/

source: sales_orders
  file: "sales_*.xlsx"
  sheet:
    prefer: ["Orders", "Sales Orders"]
  locate:
    strategy: header_anchor
    required_headers: ["Sales Document", "Item", "Material"]
    scan_first_rows: 40
    fallback: region_score

extract:
  stop_after_blank_rows: 2
  reject_duplicate_headers: true

clean:
  Material: [trim, as_string]
  Customer: [trim, as_string]
  NetValue: [parse_decimal: "de-DE"]
  CreatedOn: [parse_date: "yyyy-MM-dd|dd.MM.yyyy"]

validate:
  - key_unique: [SalesDocument, Item]
  - not_null: [SalesDocument, Item]
  - row_count_change: "warn if > 30%"
  - mapping_coverage: "block if < 98%"

publish:
  result: Outbox/sales_reconciliation.xlsx
  exceptions: Outbox/sales_reconciliation_exceptions.xlsx

Framework rules

Rules worth making boring and strict.

Inbox is immutable

Never fix the source file in place. A manual correction without evidence is invisible technical debt.

Every run has an ID

Inputs, procedure version, outputs, warnings and validations must be traceable to one run.

Observe before mutate

Profile first. Cleaning should not remove the evidence needed to understand the original problem.

Idempotent cleanup

Running a safe cleanup operation twice should normally produce the same result as running it once.

Unknown means unknown

Do not guess a date format, unit or key when evidence is weak. Quarantine or request review.

Exceptions are data

Keep failed rows with rule ID, reason and source coordinates. An exception file is part of the result.

Auto-repair has a budget

Known alias or harmless formatting drift may repair automatically. Semantic or cardinality changes require review.

Manual fixes must graduate

A repeated manual action should become a rule, reference mapping or explicit exception policy.

Publish through gates

A green file export does not mean a successful run. Publication depends on validation severity and policy.
