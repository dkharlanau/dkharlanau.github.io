Domain packs

Package a working vocabulary, not one giant workflow.

A domain pack is a curated release of compatible procedures, reusable blocks, semantic concepts, reference-data contracts, test scenarios and governance defaults for one area of work.

OverviewCatalogPacksSAP LogisticsTestingGovernance

Why

A catalog can contain hundreds of good assets and still be hard to start with.

A pack gives a team a curated entry point. It says which assets normally belong together, which concepts they share, which tests matter and what is still only a blueprint.

Procedures

End-to-end tasks that solve a clear data job.

Blocks

Shared locators, normalizers, matchers, validators and exception policies.

Concepts

Stable domain meanings used to connect local fields and procedures.

Reference contracts

Expected governed mappings and code lists, without bundling uncontrolled production values.

Test corpus

Golden, drift, failure and mutation cases that define expected behavior.

Policy defaults

Recommended review, evidence and deployment controls for the pack's risk profile.

Release model

The pack pins compatibility; the assets keep their own versions.

A procedure can release independently. A pack release records a tested combination of versions or compatible ranges. This avoids turning the pack into a monolith where one small Procurement fix forces every Sales procedure to pretend it changed too.

Pack release: manifest → pinned or compatible asset versions → pack test suite → release notes → optional deployment profiles.

States

Be explicit about what exists and what is still a blueprint.

StateMeaning
BlueprintUseful procedure or block contract is described but not implemented or production-proven yet.
CandidateAsset exists and is being tested against realistic cases.
ReadyPack requirements and tests are satisfied for the declared scope.
DeprecatedKept for history, but a named replacement should be used for new adoption.

Boundary

A pack is not an installer full of business data.

No raw master data

Reference datasets are contracts and version references. Production values remain controlled by their owner.

No secret configuration

Credentials, paths and schedules belong to Deployment.

No hidden SAP truth

The pack can describe expected concepts and patterns, but project-specific customizing and organizational meaning still need explicit contracts.

No forced adoption

A team can use one module or one procedure without installing every asset in the pack.
