Detail / Catalog & registry

A folder stores procedures. A catalog makes them reusable.

Once procedures become useful, the next problem is finding the right one, knowing whether it is trusted, and understanding what will break if it changes. The catalog is the control plane for that problem.

OverviewFrameworkTechniquesCatalogBlocksGovernance

Catalog record

Every procedure needs a stable identity and enough context to judge it.

IDStable identity

A human-readable ID does not change when the title changes. Example: sales.order-material-reconciliation.

OWNOwner and steward

The owner is accountable for business use. A technical steward may maintain the procedure implementation.

USEPurpose and consumers

What decision or output does this procedure support, and who depends on it?

VERVersion and lifecycle

Current version, status, review date, deprecation date and replacement procedure.

DEPDependencies

Reusable blocks, reference datasets, other procedures, schemas and external systems.

TRUSTTrust evidence

Tests, approvals, recent run health, drift history and review freshness. Trust is evidence, not a decorative green badge.

Classification

Use several simple axes instead of one giant folder tree.

A procedure often belongs to several views at once. The catalog should index metadata rather than force everything into one hierarchy.

Search

The catalog should answer capability questions.

By task

“Show approved reconciliation procedures for SAP sales exports.”

By concept

“Which procedures already normalize Material IDs or Customer numbers?”

By dependency

“What will be affected if reference dataset customer-aliases changes?”

By trust

“Which procedures have regression fixtures, owner approval and successful recent runs?”

By policy

“Which procedures may run locally and never send data to an AI endpoint?”

By similarity

“Find procedures with similar source contracts, fields or mappings to this new task.”

Registry structure

Keep definitions, reusable components and run evidence separate.

registry/
  procedures/
    sales/order-material-reconciliation/
      procedure.json
      README.md
      fixtures/
  blocks/
    locator/
    cleaner/
    validator/
    publisher/
  reference/
    material-aliases/
    customer-mapping/
  packs/
    sap-sales-reconciliation/
  catalog/
    index.jsonl
    dependency-graph.json

runs/
  2026-08-16/run-.../run-report.json
Rule: run history is not the catalog. The catalog describes reusable assets. Run evidence describes what happened when one version was executed.

Collections

Introduce packs before the catalog becomes flat and noisy.

Procedure

One end-to-end reusable task with sources, transforms, validations and outputs.

Block

A smaller typed component such as an Excel locator, SAP identifier cleaner or cardinality validator.

Pattern

A recommended arrangement of blocks for a repeated problem, for example lookup enrichment with exception routing.

Pack

A curated group of procedures, blocks, references and examples for a domain such as SAP Sales or migration checks.

Impact graph

Dependencies should be queryable before changes are approved.

A catalog becomes much more useful when it can answer “who uses this?”. Each procedure should expose consumed blocks, reference data, upstream procedures and downstream consumers.

Example: normalize-material-id@2 → used by 14 procedures → 5 operational → 2 business-critical. A breaking change now has an impact radius before somebody discovers it in Monday's spreadsheet.
