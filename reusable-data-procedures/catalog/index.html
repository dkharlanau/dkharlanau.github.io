Detail / Catalog & registry

A folder stores procedures. A catalog makes them reusable.

Once procedures become useful, the next problem is finding the right one, knowing whether it is trusted, and understanding what will break if it changes. The catalog is the control plane for that problem.

Catalog record

Every procedure needs a stable identity and enough context to judge it.

IDStable identity

A human-readable ID does not change when the title changes. Example: sales.order-material-reconciliation.

OWNOwner and steward

The owner is accountable for business use. A technical steward may maintain the procedure implementation.

USEPurpose and consumers

What decision or output does this procedure support, and who depends on it?

VERVersion and lifecycle

Current version, status, review date, deprecation date and replacement procedure.

DEPDependencies

Reusable blocks, reference datasets, other procedures, schemas and external systems.

TRUSTTrust evidence

Tests, approvals, recent run health, drift history and review freshness. Trust is evidence, not a decorative green badge.

Classification

Use several simple axes instead of one giant folder tree.

A procedure often belongs to several views at once. The catalog should index metadata rather than force everything into one hierarchy.

Search

The catalog should answer capability questions.

By task

“Show approved reconciliation procedures for SAP sales exports.”

By concept

“Which procedures consume or produce sap.material-id?”

By dependency

“What will be affected if reference dataset sales.customer-aliases changes?”

By pack

“Which starter assets and tests belong to the SAP Logistics pack?”

By decision history

“Has this mapping or semantic binding already been reviewed, accepted or rejected?”

By trust

“Which procedures have regression fixtures, owner approval and successful recent runs?”

By policy

“Which procedures may run locally and never send data to an AI endpoint?”

By similarity

“Find procedures with similar source contracts, concepts or mappings to this new task.”

Rule: run history is not the catalog, an open review queue is not decision memory, and a pack manifest is not a deployment. Each artifact has a different job.

Collections

Introduce clear asset types before the catalog becomes flat and noisy.

Procedure

One end-to-end reusable task with sources, transforms, validations and outputs.

Block

A smaller typed component such as an Excel locator, SAP identifier cleaner or cardinality validator.

Semantic concept

A stable business meaning with representation rules, aliases, source bindings and relations.

Reference dataset

A versioned mapping, code list, allowed-value set or controlled exception register.

Review item

A temporary work object for one unresolved ambiguity, drift event, mapping gap or business question.

Decision record

Reusable knowledge about what was accepted or rejected, where it applies and what changed because of it.

Pattern

A recommended arrangement of blocks for a repeated problem, for example lookup enrichment with exception routing.

Pack

A curated release of compatible procedures or blueprints, blocks, concepts, references, tests and governance defaults for one domain.

Impact graph

Dependencies, packs and decisions should be queryable before changes are approved.

A catalog becomes much more useful when it can answer “who uses this?”, “which release includes this?” and “why was this accepted?”. Procedures expose consumed blocks, semantic concepts, reference data, upstream procedures and downstream consumers. Packs curate compatible groups. Decision records add reasoning behind important edges.

Example: sap-logistics-starter@0.1.0 → contains sales.order-material-reconciliation → consumes sap.material-id → requires sap.normalize-material-id → may depend on sap.material-aliases. A change can now be checked against both direct consumers and pack releases.
