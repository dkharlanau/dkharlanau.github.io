Project concept / data work

Turn repeated spreadsheet work into a procedure.

Corporate data work is full of small tasks that repeat every week or month: open several exports, understand their columns, find keys, join them, clean values, check exceptions, and produce a result. The files change. The reasoning often does not.

Reusable Data Procedures is an idea for capturing that reasoning as a versioned, testable object instead of rebuilding it inside another spreadsheet.

Core thesis AI can propose. The procedure must execute deterministically.

Discovery can be probabilistic. Production transformations, validations and outputs should be explicit, reviewable and repeatable.

The loop

Files → Discover → Map → Validate → Result → Save Procedure

The first run is exploratory. The second run should be boring. That is the point.

  1. 01Files

    Bring a bundle of Excel, CSV or corporate extracts. Capture source identity and context.

  2. 02Discover

    Profile schemas, types, nulls, value patterns, uniqueness and candidate keys.

  3. 03Map

    Suggest relations from names, values, known semantics and previous procedures. Keep evidence with every suggestion.

  4. 04Validate

    Test mappings and business rules on real data before they become reusable logic.

  5. 05Result

    Execute an explicit transformation plan and expose exceptions, not only a final file.

  6. 06Save Procedure

    Store source contracts, mappings, transforms, validations, outputs and provenance as one versioned definition.

Next run: match new files to the saved source contracts → detect drift → reuse what is still valid → ask only about what changed.
Today

Knowledge hides in actions.

A person knows that column A in one export is the same business key as column F in another. The rule exists only in memory, formulas or a one-off script.

Problem

Automation starts too late.

Teams automate a finished spreadsheet, but they rarely capture how the structure was discovered, why a mapping was accepted, or what should happen when the source changes.

Target

Make the reasoning reusable.

The reusable asset is not an Excel macro. It is a small data contract plus transformation graph, tests and evidence.

Design principles

What I would protect from the beginning.

Procedure, not recording

Do not replay mouse clicks. Save intent, source contracts, mappings, transformations and checks.

Structure before semantics

Start with observable evidence: columns, types, values, uniqueness and relationships. Add business meaning on top.

AI is advisory

Use AI for semantic hints, mapping candidates and explanation. Do not make an LLM the hidden execution engine.

Drift is normal

Files will gain columns, rename fields and change formats. A procedure needs compatibility checks and a controlled repair path.

Evidence travels with logic

Keep why a mapping exists, when it was approved, what data supported it and which tests protect it.

Raw data is not the procedure

The reusable definition should normally store metadata and logic, not the corporate rows used to discover it.

Example / SAP logistics

A monthly sales reconciliation should become an asset.

Inputs

Sales order export, material attributes, customer mapping and a manually maintained exception list.

Discovered relations

Sales material → material master; sold-to → customer mapping; sales document + item → row identity.

Rules

Normalize leading zeros, reject ambiguous customer mappings, flag missing material references, keep blocked orders separate.

Reusable result

A procedure that can run against next month's files, report source drift and produce the same controlled output.

Boundary

This is a project direction, not a finished product.

The useful work now is to make the procedure model strong, collect realistic file patterns, define drift and validation behavior, and prove the approach with small deterministic runs. A polished upload screen can wait. Humanity has survived this long without another drag-and-drop box.
