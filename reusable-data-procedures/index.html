Project concept / data work

Turn repeated spreadsheet work into a procedure.

Corporate data work repeats in a familiar way: collect files, find the real table inside them, clean identifiers and dates, relate exports, validate the result, handle exceptions and do it again next month.

Reusable Data Procedures is a framework for capturing that operating knowledge as a versioned procedure instead of rebuilding it in formulas, copied scripts or memory.

Core thesisAI can propose. The procedure must execute deterministically.

Discovery can use heuristics and semantic help. Production transformations, validation gates and publication rules remain explicit and reviewable.

Simple view

Files → Discover → Map → Validate → Result → Save Procedure

This is the short explanation. The operating framework underneath is more precise.

  1. 01Files

    Receive Excel, CSV or corporate extracts and resolve their logical roles.

  2. 02Discover

    Inspect workbook structure, find real data regions and profile fields.

  3. 03Map

    Find keys and relations using names, values, history and business evidence.

  4. 04Validate

    Check source shape, parsing, cardinality, coverage, totals and business rules.

  5. 05Result

    Publish controlled output plus exceptions and run evidence.

  6. 06Save Procedure

    Version source contracts, locators, cleaning, mappings, transforms and gates.

Operating pipeline: Intake → Inspect → Locate → Extract → Clean → Relate → Transform → Validate → Publish → Learn.
Today

Knowledge hides in actions.

A person knows where the table starts, which zeros matter, which lookup is safe and which rows should be excluded. Most of that knowledge is not written anywhere.

Problem

Files drift while the task stays the same.

Headers move, sheets are renamed, identifiers change type and lookup keys stop being unique. Repeating the task safely requires more than replaying clicks.

Target

Make the operating logic reusable.

The asset is a workspace contract plus source locators, extraction rules, cleaning, relations, transformations, validations and evidence.

Framework principles

Rules I would protect from the beginning.

Inbox is immutable

Raw input is evidence. Never repair the only copy of a source file in place.

Find meaning before coordinates

Prefer Excel tables, named ranges, anchor headers and region scoring before fixed A1-style ranges.

Raw, canonical, business

Separate source representation, comparison-friendly cleanup and true business transformations.

Exceptions are output

Rejected rows need reason codes, source coordinates and rule IDs. They are not just log messages.

Drift is normal

Known formatting drift may repair automatically. Semantic, key or cardinality changes require review.

Every run leaves evidence

Inputs, hashes, procedure version, structural diff, validation results and output statistics belong to the run history.

Catalog capabilities, not files

Index procedures by domain, task, source, trust, owner and dependencies so reuse does not depend on knowing a folder name.

Promote shared logic

Repeated locators, cleaners and validators become versioned blocks rather than copied fragments.

Govern by risk

Ad-hoc procedures stay lightweight. Business-critical procedures get stronger tests, review and policy controls.

Example / messy SAP export

The real problem starts before the join.

Inbox

A monthly workbook arrives with a cover sheet, an Orders sheet and a hidden helper sheet.

Locate

The Orders table begins at row 8 this month, not row 6. The procedure finds it from Sales Document + Item + Material anchors.

Clean

Material and customer IDs stay strings, whitespace is normalized, German decimal values are parsed explicitly and rejected dates remain exceptions.

Validate

Document + Item must stay unique, material lookup coverage must exceed the threshold and a control total is reconciled before publication.

Boundary

Build the operating model before the interface.

The useful work is to collect ugly real cases, improve locator and cleaning techniques, build a small standard block library, define what may auto-repair, and make every repeated manual decision either a rule, reference record or explicit exception. The catalog then turns those assets into something a team can actually find and trust.
