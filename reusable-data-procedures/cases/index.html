Casebook

Prove the framework on real-shaped problems.

A reference case is more than an example screenshot. It carries synthetic inputs, a procedure candidate, reference data, tests, expected run evidence, review work and the decision that changes the next run.

OverviewCasesTestingPacksReview

Case contract

Every case should test the whole chain.

Source reality

Show workbook layout, headers, rows, source roles and the awkward details that usually hide in manual work.

Reusable logic

Bind semantic concepts, reference data, blocks, transforms and validation gates into a procedure candidate.

Expected evidence

Describe what a correct run must record: selected region, resolved versions, drift, exceptions, controls and publication decision.

Learning loop

Introduce a controlled drift, create a review item, record the decision, then replay the same business period with the approved change.

Rule: a case passes only when it explains both the successful path and the safe failure path.

Reference case 02 / Procurement

Purchase Order Material Reconciliation

A SAP Procurement export checks each PO item against a controlled supplier-material cross-reference. The case proves composite keys, supplier-scoped mappings and the difference between strong evidence and automatic master-data changes.

What two cases tell us

Reuse the controls, not the assumptions.

Shared framework

Sales and Procurement both use source location, stable identifiers, controlled references, gates, review, versioning and replay.

Different keys

Sales uses a direct material alias. Procurement needs Supplier + Supplier Material as a composite business key.

Different evidence

A value on the same PO row can support a mapping proposal, but it still does not approve a controlled reference change.

Stronger confidence

When two domains exercise the same framework boundary in different ways, the shared pattern has better evidence than a single polished example.
