Execution model

Procedure ≠ Deployment ≠ Run.

These three objects answer different questions. Keeping them separate makes the framework portable: the same approved business logic can run manually on a laptop, on a schedule, or inside a governed service without changing the procedure itself.

OverviewProcedureDeployment & RunTestingGovernance

Three contracts

Keep business logic, operation and evidence apart.

01Procedure

What the data work means: sources, locators, cleaning, mappings, transforms, validations and output contracts.

02Deployment

Where and when it runs: environment, trigger, source binding, destination binding, credentials reference, retry, timeout and concurrency policy.

03Run

What actually happened: resolved inputs, hashes, versions, timing, drift, validation evidence, exceptions, outputs and publication decision.

Why this matters: changing a schedule should not create a new business procedure version. Changing a material-key normalization rule should.

Idempotency

Do not publish the same logical run twice by accident.

Schedules, folder watchers and retries create duplicate-trigger risk. The framework needs an explicit answer before automation becomes unattended.

Run key

Build an idempotency key from deployment, logical business period and input hashes or another declared source identity.

Duplicate policy

Skip, replace, create revision, or require review. The choice belongs to the deployment policy.

Atomic publication

Prepare outputs first. Publish only after blocking gates pass so consumers never see a half-written result set.

Retry boundary

Retry network or temporary storage failures. Do not keep retrying a broken key cardinality and hope mathematics changes its mind.

Run evidence

A run should be explainable without reopening the original session.

Identity

Run ID, deployment ID, procedure version, engine version, start/end time and actor or trigger.

Inputs

Resolved source roles, file names or resource IDs, hashes, workbook regions and source fingerprints.

Execution

Pinned block versions, resolved reference-data versions, step metrics and deterministic plan hash.

Quality

Drift classification, validation results, exception counts, control totals and publication decision.

Outputs

Output names, hashes, row counts, destinations and consumer-facing publication status.

Lineage

Which source and rule produced an output field or exception. Full cell lineage is optional; meaningful business lineage is not.
