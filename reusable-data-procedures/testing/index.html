Testing model

Test the ugly cases on purpose.

A procedure that only works on one clean example is a demonstration. A reusable procedure needs a small corpus that proves normal behavior, known exceptions, drift handling and failure boundaries.

OverviewFrameworkDeployment & RunTestingGovernance

Corpus layers

One happy file is not evidence.

01Golden case

Known input bundle with expected result, exceptions, validations and evidence summary.

02Boundary case

Empty files, one-row tables, maximum identifier length, zero amounts, duplicate keys and null-heavy columns.

03Drift case

Moved headers, renamed sheets, added optional columns, changed locale, duplicate target key or changed business meaning.

04Failure case

Unreadable workbook, missing required key, invalid dates, lost identifier precision or failed control total.

05Historical replay

Approved old run package used to compare a new procedure or engine version against known production behavior.

06Mutation case

Start from a valid fixture and deliberately alter one property to verify that the correct drift or validation rule reacts.

Fixture design

Small data, strong meaning.

Synthetic first

Prefer small synthetic files that reproduce the structural or business behavior without carrying uncontrolled corporate data.

One reason per case

A focused fixture should make the expected behavior obvious. Large mixed examples are useful later for end-to-end checks.

Expected evidence

Test not only the result rows. Assert drift class, validation state, exception reason codes and selected locator.

Stable identifiers

Give cases IDs such as excel.header-moved.001 or join.target-duplicate.001 so regressions can be discussed and cataloged.

Excel mutation library

Generate the boring failures before users do.

MutationExpected reaction
Move table down by five rowsSemantic locator still resolves the same logical region.
Rename a header to an approved aliasCompatible or resolvable drift, no silent procedure edit.
Remove a required key columnBreaking drift; publication blocked.
Add a subtotal rowFooter/total detection excludes or routes it according to extraction policy.
Convert material IDs to numeric cellsIdentifier classification protects leading-zero semantics or raises a controlled exception.
Change decimal localeParse-success gate detects the mismatch instead of silently changing values.
Duplicate lookup target keyCardinality validation blocks or routes ambiguity.
Insert a second similar tableLocator confidence drops or requires review instead of choosing randomly.

Promotion gates

Testing depth should follow risk.

CriticalityMinimum evidence
Ad-hocAt least one golden case and explicit manual review of outputs.
OperationalGolden + boundary + key drift cases, deterministic rerun and owner review.
Business-criticalRegression suite, historical replay where allowed, mutation tests for key assumptions, dependency impact and rollback evidence.

Engine compatibility

Test the runtime as well as the procedure.

Procedure compatibility

A newer engine must either execute an older supported spec consistently or reject it with a clear migration requirement.

Block compatibility

Shared block versions have their own fixtures. A change can be tested before every dependent procedure is rerun.

Plan hash

Compile a stable execution-plan signature where practical. Unexpected plan changes become review signals.

Golden diff

When expected output changes, review the semantic difference and change reason instead of blindly replacing fixture files.
