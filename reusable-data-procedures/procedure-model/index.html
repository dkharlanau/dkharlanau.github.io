Procedure model

The procedure owns logic, not infrastructure.

A procedure should describe what the data work means and how it behaves. Folder locations, credentials, schedules, retry and concurrency belong to a deployment. Actual hashes, timings and results belong to a run.

Core object

Ten concerns belong to the procedure.

01Identity

Stable ID, name, purpose, owner and procedure version.

02Catalog metadata

Domain, job family, data concepts, source families, sensitivity, criticality and tags.

03Lifecycle & trust

Maturity, trust evidence, review dates, deprecation and replacement chain.

04Dependencies

Pinned reusable blocks, reference datasets, other procedures and external systems.

05Source contracts

Logical source roles, formats, worksheet rules, required fields, types and structural fingerprints.

06Locators & extraction

How the logical table is found and extracted without binding the procedure to one physical folder.

07Mappings & transforms

Relations, cardinality, normalization, deterministic operations and reusable block references.

08Validations

Locator confidence, schema, parse success, uniqueness, mapping coverage, control totals and business assertions.

09Output contracts

Logical result names, roles, formats and expected fields. Physical destinations are deployment bindings.

10Behavior & provenance

Failure behavior, who changed the version, what changed and why.

Boundary

Three contracts keep change understandable.

ArtifactContainsDoes not contain
procedure.jsonReusable business/data logic, source semantics, tests and behavior rules.Schedules, physical paths, secrets, retry, run hashes.
deployment.jsonPinned procedure version, environment, trigger, bindings, policy profile, idempotency and operations.Business transformation semantics.
run.jsonResolved inputs, hashes, versions, drift, validations, exceptions, control totals and outputs.Editable configuration.
reference dataApproved dictionaries, code lists, aliases and mappings with ownership.Temporary one-run fixes unless deliberately promoted.
test corpusSynthetic or approved fixtures and expected behavior.Uncontrolled production extracts by default.

The procedure should stay portable.

Notice what is missing: no Inbox/C:\..., no SharePoint URL, no cron schedule and no secret. Those are deployment concerns. This makes the procedure portable rather than merely configurable.

Versioning

Version by semantic impact.

Patch

Description, labels or other non-behavioral metadata changes.

Minor

Compatible aliases, optional fields or non-breaking validations.

Major

Changed keys, locator semantics, mapping cardinality, required source contracts, dependency behavior or output meaning.

Not a procedure change

Changing a schedule, file location, credential reference, retry count or notification target normally changes the deployment instead.
