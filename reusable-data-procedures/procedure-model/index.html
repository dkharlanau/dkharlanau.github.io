Detail 02 / Procedure model

The procedure is the product.

The reusable unit should be portable, inspectable and independent from one user interface. A web app, CLI, scheduled job or agent should all be able to read the same definition.

OverviewApproachProcedure ModelArchitectureRoadmap

Core object

Seven parts, kept deliberately boring.

The definition should be readable enough that a consultant can review it without reverse engineering code.

01Identity

ID, name, purpose, owner, domain, version, status and timestamps. A procedure is managed content, not an anonymous script.

02Source contracts

Logical source roles, accepted file types, worksheet selection, required and optional columns, type expectations and fingerprints.

03Mappings

Relations between fields or source roles, cardinality, normalization, approval state and evidence behind the decision.

04Transforms

Named deterministic steps: normalize, filter, lookup, derive, aggregate, split, rename, convert and route exceptions.

05Validations

Schema checks, null rules, uniqueness, referential integrity, coverage thresholds, row-count conditions and business assertions.

06Output contract

Expected columns, ordering, formats, exception datasets and output destinations. Success means more than producing a file.

07Provenance

Who approved mappings and rules, what evidence supported them, which previous procedure version was used and why a change was made.

SeparateRun report

Input fingerprints, actual metrics, drift findings, validation results and output statistics belong to a run, not to the reusable definition.

Separation

Definition and execution evidence must not collapse into one file.

Draft shape

A procedure should read like a small data contract.

{
  "kind": "reusable-data-procedure",
  "version": "0.2",
  "id": "sales-material-reconciliation",
  "purpose": "Enrich a sales export and flag missing references",
  "sources": [
    {"role": "sales", "requiredColumns": ["SalesDocument", "Item", "Material"]},
    {"role": "material", "requiredColumns": ["Material", "MaterialGroup"]}
  ],
  "mappings": [
    {"from": "sales.Material", "to": "material.Material", "cardinality": "many-to-one"}
  ],
  "transforms": [
    {"op": "normalize_identifier", "field": "sales.Material", "rule": "sap-alpha-like"},
    {"op": "lookup", "mapping": "sales.Material -> material.Material"}
  ],
  "validations": [
    {"rule": "mapping_coverage", "minimum": 0.99},
    {"rule": "target_unique", "source": "material", "field": "Material"}
  ],
  "outputs": [{"name": "enriched_sales"}, {"name": "exceptions"}]
}
Design preference: keep the procedure declarative where possible. Escape hatches for custom code will be needed, but they should be explicit because every escape hatch is future maintenance wearing a fake moustache.

Versioning

Changes have different meanings.

Patch

Description, labels or non-behavioral metadata changes. Same execution behavior.

Minor

Compatible new optional source field, additional non-breaking validation or new output metadata.

Major

Changed key, mapping cardinality, transformation semantics, required source contract or output contract.

Run-time repair

A drift suggestion does not silently mutate the procedure. It creates a proposed revision with evidence and review.

Machine contract

Keep the spec useful to both tools and people.

The current draft schema is intentionally small. It should evolve from real cases rather than attempt to model every possible spreadsheet operation on day one.
