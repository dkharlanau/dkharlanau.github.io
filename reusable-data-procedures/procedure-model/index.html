Procedure model

The procedure is the reusable product.

A web app, CLI, scheduled job or agent should all be able to read the same definition. The interface may change. The operating logic should not disappear with it.

OverviewFrameworkTechniquesApproachProcedure ModelArchitectureRoadmap

Core object

Nine parts, all explicit.

The definition should be readable enough that a consultant can review it without reverse engineering code.

01Identity

ID, purpose, owner, domain, procedure version, status and timestamps.

02Workspace policy

Inbox, quarantine, reference, outbox and evidence responsibilities plus publication behavior.

03Source contracts

Logical source roles, formats, worksheet rules, required fields, types and structural fingerprints.

04Locators & extraction

How a real table is found inside a workbook: table name, anchor headers, scoring, fallbacks and region boundaries.

05Mappings

Relations between fields or source roles, cardinality, normalization and evidence.

06Transforms

Deterministic cleanup and business operations: parse, normalize, filter, lookup, derive, aggregate and route exceptions.

07Validations

Locator confidence, schema, parse success, uniqueness, coverage, control totals and business assertions.

08Output contract

Result, exceptions and evidence outputs with formats, fields and destinations.

09Provenance

Who approved rules, what evidence supported them, what changed and why.

RunRun report stays separate

Actual input hashes, source coordinates, drift, validation metrics, exceptions and output statistics belong to execution history.

Separation

Definition, reference data and run evidence are different artifacts.

ArtifactContainsDoes not contain
procedure.jsonWorkspace policy, contracts, locators, extraction, mappings, transforms, validations and outputs.Corporate rows from a particular run.
run-report.jsonResolved inputs, hashes, selected regions, drift, metrics, exceptions and output statistics.The authoritative procedure definition.
reference/Approved dictionaries, code lists, aliases and mappings with ownership.Temporary manual fixes from one run unless deliberately promoted.
fixtures/Small synthetic or approved regression datasets.Uncontrolled production extracts.

Draft shape

A procedure should read like a small data contract.

{
  "kind": "reusable-data-procedure",
  "specVersion": "0.3",
  "id": "sales-material-reconciliation",
  "workspacePolicy": {
    "inbox": "Inbox/",
    "quarantine": "Quarantine/",
    "outbox": "Outbox/",
    "evidence": "Evidence/"
  },
  "sources": [{
    "role": "sales",
    "filePattern": "sales_*.xlsx",
    "locators": [{
      "strategy": "header-anchor",
      "requiredHeaders": ["Sales Document", "Item", "Material"],
      "scanFirstRows": 40
    }],
    "requiredFields": [
      {"name": "Sales Document", "required": true, "role": "key"},
      {"name": "Item", "required": true, "role": "key"},
      {"name": "Material", "required": true, "role": "key"}
    ]
  }],
  "transforms": [
    {"id": "material-key", "op": "comparison-key", "input": "sales.Material"}
  ],
  "validations": [
    {"id": "sales-key", "rule": "unique", "target": "Sales Document + Item", "severity": "block"}
  ],
  "outputs": [
    {"name": "result", "role": "result", "format": "xlsx"},
    {"name": "exceptions", "role": "exceptions", "format": "xlsx"}
  ],
  "provenance": {"createdAt": "2026-08-16T00:00:00Z"}
}
Design preference: keep the procedure declarative where possible. Custom code will exist, but it should be a visible escape hatch rather than a secret basement where maintainability goes to disappear.

Versioning

Repair creates history.

Patch

Description, labels or non-behavioral metadata changes.

Minor

Compatible aliases, optional fields or non-breaking validations.

Major

Changed keys, locator semantics, mapping cardinality, required source contracts or output meaning.

Run-time repair

A confirmed drift repair creates a proposed revision with evidence. Approved behavior remains reproducible.
