Detail 01 / Approach

Capture the reasoning, not the clicks.

A reusable procedure should describe what the data means operationally: which sources are expected, how they are related, what transformations are allowed, what must be true, and what to do when a new file no longer fits.

OverviewApproachProcedure ModelArchitectureRoadmap

First run

Discovery creates hypotheses.

The system should not jump from uploaded files to a final join. It should build evidence in layers.

Identify the source

File name is weak identity. Use sheet names, expected columns, column types, value patterns, row shape and optional business labels to build a source fingerprint.

Profile the columns

Measure type candidates, null rate, distinct values, uniqueness, common formats, value length, ranges and representative samples. A likely key is an observation, not a fact.

Generate relation candidates

Compare field names, normalized values, overlap, uniqueness, cardinality and known enterprise vocabulary. A good relation has several independent signals.

Ask for business confirmation

The user confirms that MATNR and Material are the same concept, or rejects the suggestion. This decision becomes part of the procedure provenance.

Turn actions into explicit transforms

Leading-zero normalization, date parsing, filters, lookups, derived fields and exception handling become named steps with parameters.

Validate before save

Test coverage, uniqueness, null tolerance, row-count expectations and business rules. Save the procedure only with the evidence used to accept it.

Mapping evidence

One similarity score is not enough.

SignalWhat it tells usTypical weakness
Header similarityNames such as Material, Material_ID and MATNR may describe the same field.Different business concepts often use similar words.
Value overlapReal values can show whether two fields share the same identifier domain.Small samples and dirty values can mislead.
Type compatibilityText-to-text or date-to-date relations are more plausible than random type pairs.Enterprise IDs are often stored as numbers in one export and text in another.
CardinalityOne-to-one, many-to-one and many-to-many patterns help classify the relation.Duplicates may be valid business behavior rather than bad data.

Repeat run

Drift handling is the real product.

The interesting question is not whether the first run works. It is what happens next month when the export changes.

Compatible drift

A new optional column appears. The saved procedure still runs and records the difference.

Resolvable drift

A column is renamed but structure and values strongly match the previous source. The system proposes a repair and asks for confirmation.

Breaking drift

A required key disappears, type changes radically, or cardinality becomes unsafe. Execution stops before producing a misleading result.

Business drift

The file still looks technically valid, but business meaning changed. This is why critical rules need owner, description, provenance and review dates.

Important distinction: schema compatibility and business correctness are different checks. A technically compatible file can still be wrong.

Role of AI

Useful where uncertainty exists.

Good use

Explain unfamiliar columns, rank mapping candidates, compare metadata, suggest validation rules, summarize drift and retrieve similar approved procedures.

Bad use

Let a model silently decide joins, transformations or exception handling on every run. That removes repeatability exactly where the project is trying to create it.

Better pattern

AI produces a proposal with evidence. A deterministic compiler turns approved choices into an execution plan.

Enterprise boundary

Raw values may contain personal or confidential data. Semantic analysis needs masking, local models, approved endpoints or metadata-only modes depending on policy.
