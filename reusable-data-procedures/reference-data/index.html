Reference layer

Mappings are data assets, not hidden worksheet tabs.

Many procedures depend on small but important datasets: customer aliases, plant mappings, code conversions, accepted values or manual exception lists. If these datasets change output meaning, they need identity, ownership, versioning and tests of their own.

Asset model

Reference data deserves the same discipline as procedure logic.

IDStable dataset ID

Example: sales.customer-aliases or enterprise.plant-map.

VERVersion or effective period

Use semantic versions, dated releases or valid-from / valid-to periods depending on the business case.

OWNOwner and steward

The owner decides business meaning. A steward maintains records and quality.

KEYKey and cardinality

Declare which columns identify a record and whether one-to-one or one-to-many mapping is expected.

SEMConcept bindings

Columns can reference semantic concepts, making the value spaces and mapping purpose explicit.

USEConsumers

Procedures and blocks that depend on the dataset are visible through the dependency graph.

Reference families

Not every small table is the same kind of asset.

Lifecycle

Reference data changes should be reviewable and reproducible.

Propose

A new record or changed mapping has a reason, source and author.

Validate

Check key uniqueness, nulls, duplicate targets, concept compatibility, dates and allowed domains.

Approve

Risk-based review confirms the new mapping or code list is valid for its declared scope.

Release

Create an immutable version or effective-dated snapshot. Procedures pin the version they use.

Observe

Track unmatched values, coverage, stale records and downstream exceptions.

Deprecate

Retire a version or record with replacement and history rather than deleting the evidence.

Contract

Make data semantics visible in the dataset definition.

{
  "id": "sales.customer-aliases",
  "version": "2026.08",
  "family": "alias-dictionary",
  "owner": "sales-operations",
  "key": ["sourceSystem", "sourceCustomer"],
  "cardinality": "many-to-one",
  "columns": [
    {"name": "sourceCustomer", "concept": "customer.external-id"},
    {"name": "businessPartner", "concept": "sap.business-partner-id"},
    {"name": "validFrom", "concept": "time.valid-from"}
  ],
  "policy": {"unmatched": "exception", "ambiguous": "block"}
}

Quality rules

A lookup file needs stronger checks than “Excel opened successfully”.

Key uniqueness

A one-to-one or many-to-one lookup must not introduce duplicate source keys unless the contract explicitly allows them.

Target validity

Targets can be checked against known concepts, master-data extracts or another reference dataset.

Effective dates

Overlapping validity periods should be detected before a run chooses two answers for the same key.

Coverage trend

A sudden fall in mapping coverage is run evidence and may indicate source or business drift.

Orphan records

Reference rows not used for a long period should be reviewed, not silently trusted forever.

Change impact

Before release, query which procedures, blocks and consumers use the changed dataset.

Practical storage

Version definitions and controlled data together, but separate raw evidence.

registry/reference/
  sales.customer-aliases/
    reference.json
    releases/
      2026.07/data.parquet
      2026.08/data.parquet
    tests/
      duplicate-key.json
      unknown-target.json
    CHANGELOG.md

runs/
  .../run-report.json   # records exact reference version used
Rule: a procedure can depend on reference data, but it should not hide a mutable mapping table inside itself. Reproducibility requires the exact released reference version to appear in run evidence.
