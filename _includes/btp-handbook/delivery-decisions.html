Recipe A — Make one request explainable end to end

Objects: a ReviewCase entity containing only extension-owned state; a scoped read service; an explicit submitEvidence or approveReview action; selected security configuration; deployment descriptor; database binding; ERP destination/communication setup. The action names are application-owned examples, not standard SAP BP APIs.

Flow: user signs in → backend validates role and case assignment → service reads/writes the permitted case → required ERP action uses the approved API and identity → local state records confirmation or a recoverable unknown outcome. A browser request never carries a broad ERP administrator credential.

Reject the design if a reviewer can approve their own evidence when separation is required, if a case number reveals another supplier's data, or if a timeout silently triggers a duplicate non-idempotent posting. A successful happy-path demonstration is not enough.

Recipe C — Put the failure between the arrows

Write event ID → business key → attempted operation → receiver evidence → final status. Acknowledge only according to the chosen durable processing contract. Test a crash before commit, after commit, and before acknowledgement. A poison message needs bounded retries and an owner; a retry loop is not a recovery strategy.

13 / Delivery and recovery

A green deployment is the beginning of verification.

Tree 15 — What should happen after failure?

Did the operation reach a known business outcome?
├─ Confirmed success → record it; do not repeat the effect.
├─ Confirmed business rejection → correct/escalate; blind retry will not fix it.
├─ Confirmed transient failure before effect → bounded retry with backoff/jitter.
└─ Unknown: timeout or crash after dispatch → query/reconcile the receiver first.
   ├─ Receiver confirms success → close the pending operation.
   ├─ Receiver proves no effect and replay is safe → retry under policy.
   └─ Cannot establish outcome → controlled investigation/manual resolution.

Delivery: source control → lint/unit tests → API/contract and authorisation tests → build immutable artifact → deploy to test → integration/failure checks → approved production promotion. Cloud Transport Management can move supported content; a CI/CD system builds and tests. Neither is a substitute for database migration design, secrets configuration or deployment ownership.

Observability: correlate UI request, app log, iFlow/message and backend result using appropriate IDs. Use Cloud Logging or the selected logging stack for technical telemetry, Audit Log for relevant security events, Cloud ALM for supported end-to-end monitoring, and Alert Notification/Automation Pilot when routing or controlled remediation is needed. These are distinct jobs, not five mandatory products for every pilot.

Scaling: set resource limits, timeouts and downstream concurrency. Autoscaling the caller can overload ERP. Bound queue backlogs, retries and batch sizes. Treat 429 as a signal to respect the receiver's rate policy, not to create more parallel retries. Define worker overlap protection for scheduled jobs.

Free-to-paid is a migration question. Some services support a documented plan upgrade, but this is not universal. For Kyma, moving from a free plan to a paid plan requires a new cluster according to the free-plan guidance. Build the exit path before the pilot accumulates important state.

What belongs in the contract conversation

Scope: exact service and plan, feature/edition, permitted productive and non-productive use, internal/external users and developer/consumer categories. Confirm source-system and third-party/model rights separately. An API's technical availability is not a ruling on ERP commercial access rights.

Economics: the chargeable unit, minimums/rounding, region, quantities, term, included capacity, overage, unused commitment treatment and supporting services. Check whether model tokens, capacity units and AI Units are converted under the applicable offering; they are not universally equivalent.

Operations and exit: support, SLA, residency/subprocessors, retention, restore/export, termination and the fate of stored data. Record unresolved items and the person who must confirm them. This checklist identifies questions; the signed agreement determines the answer.

Simple sizing example: two 0.5 GB app instances running for 730 hours consume 730 GB-hours of application memory-time; a 0.5 GB test instance running for 220 hours adds 110 GB-hours. Total: 840 GB-hours before converting to the selected plan's billing unit and rules. This is a workload calculation, not an SAP price quote.

Cost multiplier: 5,000 reviews × 2 model calls = 10,000 calls before retries. Ten percent additional calls add 1,000. Model length, extraction, storage and logs also matter. Estimate low/expected/high demand and compare whole-life operating effort, not just the runtime line.

Budget alerts notify; they do not universally stop consumption. Put explicit limits where work multiplies: queue retries, batch size, model calls, token/output limits, job concurrency and retention. Keep a named cost owner and regularly remove unused resources.

15 / Pilots with a purpose

Eight projects that force the architecture to become concrete.

Start with synthetic or approved sandbox data and a bounded outcome. Each pilot needs a design, a small implementation, a failure test and a decision about whether to continue. Do not provision paid services or connect productive write APIs before the access and cost scope is approved.

1. BP change-request preflight

Problem: requests reach governance with missing or inconsistent information. MVP: a reviewer sees an allowed case, deterministic checks and missing-evidence prompts; no direct update of ERP tables.

Stack: Fiori elements + CAP on CF; case storage only if the pilot owns cases; selected identity; a mock API first, then a released BP/MDG interface appropriate to the landscape. Artifacts: CDS model, scoped service, validation rules, destination/communication record and negative access tests.

Prove: wrong reviewer is denied, stale data is detected, and a rejected business rule cannot be bypassed with a direct API call. Continue only if: users can correct a real class of avoidable defects without creating a second governance owner. Measure rejected submissions and correction effort; do not invent an ROI percentage.

2. Offline warehouse or field inspection

Problem: work stops when connectivity disappears. MVP: download assigned inspections, capture results/photos offline, reconnect and display accepted/rejected/conflicting outcomes.

Stack: MDK + Mobile Services + supported OData; add a facade only for a demonstrated API gap. Artifacts: service definition, defining requests, pages/actions/rules, client configuration, sync policy and device test matrix.

Prove: airplane mode, restart, partial upload, concurrent server edit, user switch and no duplicated final effects. Continue only if: the hardest offline operation and data-security requirement are feasible on real target devices.

3. Recoverable order-event consumer

Problem: a successful technical delivery can still leave an uncertain business result. MVP: consume a small event type, perform one controlled operation and reconcile unknown outcomes.

Stack: eligible event service/queue + CF worker initially; durable processing record or an equivalent receiver contract. Artifacts: event schema, queue/subscription policy, consumer, deduplication key, dead-letter runbook and correlation view.

Prove: duplicate delivery and a crash after receiver commit do not create a second effect. Continue only if: an operator can safely resolve a pending operation without guessing whether to replay it.

4. Exception approval without another workflow engine

Problem: exception approvals live in email with unclear ownership. MVP: one form, one decision table, two approval roles and a controlled backend action.

Stack: existing suitable workflow or Build Process Automation; approved API; Task Center only if inbox consolidation is a requirement. Artifacts: process model, form, action contract, escalation timer and role assignments.

Prove: approval expiry, reassignment, absent approver and failed backend completion. Continue only if: the workflow state and ERP state can be reconciled and one owner remains authoritative.

5. Supplier-document extraction with a human checkpoint

Problem: reviewers repeatedly retype document fields. MVP: extract supported fields, show evidence and allow correction before any business update.

Stack: Document AI, a small review UI/process and appropriate document storage; add CAP only for orchestration/validation the existing product cannot provide. Artifacts: extraction configuration, field mapping, validation policy, review screen and retention rules.

Prove: an unreadable document, incorrect field, unsupported layout and duplicate upload do not silently produce a trusted posting. Continue only if: measured correction effort is lower while critical-error handling remains acceptable.

6. Read-only integration support assistant

Problem: support engineers cannot quickly locate the relevant approved runbook. MVP: answer from a small permitted document set and cite the exact evidence; no production-changing tools.

Stack: authenticated app, permission-aware retrieval, selected AI Core/generative AI hub setup or another approved model path. Artifacts: ingestion/access mapping, retrieval configuration, prompt/output schema, evaluation cases and usage limits.

Prove: no evidence leads to a qualified non-answer, another team's restricted document is not exposed, and injected instructions cannot add tools. Continue only if: evaluated answer usefulness improves over ordinary search at an acceptable cost.

7. The same small application on CF and Kyma

Problem: runtime choice is being made by preference rather than requirements. MVP: deploy the same bounded API and comparable dependencies to two approved sandboxes.

Stack: identical CAP/service contract; CF deployment descriptor versus Kyma image/chart. Artifacts: deployment scripts, binding inventory, operations checklist and comparable workload definition.

Prove: deploy, update, scale, restart, rotate a credential and diagnose a broken backend. Decision: compare operating effort and total cost for the actual workload. Choose Kyma only if its extra control is useful enough to justify its responsibility. A benchmark with unequal database or replica settings is not a fair runtime comparison.

8. Architecture cost and entitlement ledger

Problem: a diagram reaches procurement without a complete dependency list. MVP: each component has a reason, plan, region, usage unit, environment quantity, owner and unresolved contract question.

Stack: a simple structured register; no BTP runtime is needed to start. Artifacts: bill of materials, low/expected/high usage model, assumption log and decommission checklist.

Prove: double traffic, add a test environment and add retries; all affected lines change. Unknown licences remain unknown, not zero. Continue only if: the register exposes missing dependencies and makes a smaller viable composition visible.

One local recovery exercise

Use the existing recovery drill to explore a lost response after a simulated receiver commits. Run node btp-recovery-drill.mjs in the supported local Node.js environment. It is a simulation, not an SAP API or a distributed database test. The point is to distinguish safe retry from unknown business outcome; a real receiver's contract must be established separately.

Defend the choice before adding more services

Change one constraint: the app must now work offline; the backend becomes private; the customer already has a Kubernetes operating team; external reviewers need strict tenant isolation; the expected usage triples. Explain which components change, which remain, and which test now becomes decisive.

One-minute structure: “The requirement is ___. I choose ___ because ___. The minimum components are ___. I add ___ only when ___. The request travels through ___. The main failure is ___, handled by ___. We will accept the design when ___.” Then name the exact artifact and owner when challenged.

16 / Architecture discipline

Use a method to expose a missing decision.

SAP Application Extension Methodology: identify the gap, assess extension options and choose the right boundary. ISA-M: assess integration styles/domains and select suitable technologies. Data and Analytics Advisory Methodology: connect decision-support requirements with data and analytical architecture. These are reasoning methods, not three extra services to purchase.

The architecture pack: one context/request-flow view; one decision record with a rejected alternative; a service/plan bill of materials; an identity/data-access matrix; an interface/error contract; a deployment/recovery plan; measurable acceptance tests; named owners. A pretty product map cannot replace any of these.
