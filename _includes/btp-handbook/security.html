08 / Trust and connectivity

A successful login is only the first permission check

Follow one request across the system. The person signs in. The application checks the role and the assigned case. A gateway checks permitted API use. The ERP checks its own business authorization. Every successful check has a different meaning.

In the lab, a reviewer can record an opinion only for an assigned request. An approver can authorize the next business step, but cannot approve their own review. This is an example of separation of duties. The exact organizational rule is a business decision, not a default promise from the platform.

User identity or technical identity?

Principal propagation preserves a supported user identity across a call chain. It requires compatible trust, authentication and backend configuration. Merely adding a destination does not activate it.

Technical client credentials authorize a service identity. The backend may then see the technical user, not the human who initiated the action. The application must enforce the permitted business scope and retain initiating/approving identity in appropriate audit evidence. Do not give an agent broad administrator credentials to simplify the demo.

Destination, Connectivity and Cloud Connector

A destination holds supported endpoint and authentication configuration. The Connectivity service and Cloud Connector can support controlled access to private-network systems. Cloud Connector initiates an outbound connection from the private network and exposes configured resources, not the whole network.

For an internet-accessible cloud API, a Cloud Connector may not be needed. For private access, confirm supported protocols and adapters, resource allowlists, certificates and connectivity components for the selected runtime. The connector is not a general-purpose promise that every legacy protocol will work unchanged.

Two separate checks: can the application reach the endpoint, and may this identity perform the requested business operation? A green connectivity test answers only part of the problem.

Four checks for the token and the tenant

Architecture review: validate a token with the supported security library, including signature, trusted issuer, intended audience and validity. Decoding a JWT is not validating it. Check that the authenticated tenant and object scope reach the destination, database query, cache, job and audit record; never select a tenant merely from an untrusted request field.

With a technical identity, application checks remain essential even if ERP sees a powerful integration user. With user propagation, verify that each hop supports the intended delegation. “Forward the same token everywhere” is not a general integration design. CORS controls browser cross-origin access and CSRF defenses protect applicable browser/session interactions; neither grants business authorization.

Negative test: sign in as a legitimate reviewer, alter the case ID, then try the direct service endpoint without the UI. The server must deny the same forbidden action on every route. Repeat with another tenant and with an expired identity.

Documentation and further reading: cap-security, cap-integration.

Keep the controls operational

Use managed secret/binding mechanisms, minimum privileges, rotation and a clear expiry owner. Never put client secrets in browser code, source control, model prompts or screenshots. Protect logs and retrieval indexes as data stores: they can contain sensitive business information too.

For offboarding, test account deactivation, provisioning completion, role removal and session/token behavior across the actual applications. For AI tools, check that a revoked tool or policy is enforced on every allowed execution path. A registry flag cannot govern a connection that bypasses its enforcement point.

Use SAP Trust Center for relevant provider assurance and BTP Security Recommendations for configuration guidance. Provider certification does not certify the custom application’s configuration or the complete customer process.

Reference: identity, cap-security, connectivity, trust.

A reviewer changes the request ID in the URL and sees another supplier’s data. Which control is missing?

Object-level authorization: the service must validate assignment and scope for every read and write. Authentication and a broad role are insufficient. Include this exact negative test in the acceptance criteria.
