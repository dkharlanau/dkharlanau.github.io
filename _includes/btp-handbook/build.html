06 / Extensions and development

Choose the smallest supported extension

Start with fit-to-standard. A supported ERP configuration change may solve the problem without custom development. When an extension is justified, decide where its business behavior belongs. Clean core is about sustainable change, not a ban on every custom ABAP object.

OptionGood fitConstraint or trade-off
Key-user extensibility — on-stackSupported fields, UI adaptation and limited business logic close to the standard process.Only the extension points and scope exposed by the target application are available.
Developer extensibility — on-stackABAP Cloud / RAP logic using released objects in a supported ERP stack.Tighter access to the ERP business context, but the applicable release contracts and edition rules remain binding.
Side-by-side — outside ERPCross-system workflow, external user experience, independent lifecycle or a different runtime need.Adds remote calls, identity and operations. It does not grant local ERP transaction semantics across the network.

For supplier review, the external user boundary can justify a side-by-side UI. It does not justify copying the entire supplier master. Store the case reference and review evidence you need; use a supported interface for authoritative business data.

Five clean-core dimensions, not only code

Processes: avoid unnecessary variants. Extensions: use supported contracts. Data: control quality and lifecycle. Integrations: keep stable, governed interfaces. Operations: release and recover the solution predictably. Moving unsupported logic to BTP does not automatically improve all five.

The A–D clean-core classification helps assess extension risk, especially in private-edition and on-premise modernization. Level A uses the preferred released-contract approach. Level B covers the relevant documented classic APIs/technologies under SAP’s classification. Level C has internal-object dependencies requiring stronger upgrade attention. Level D uses non-recommended techniques. An arbitrary BAPI is not automatically Level B or guaranteed upgrade-safe. Check the actual object and assessment guidance. Public-edition extensibility remains more restricted.

CAP and RAP can both support transactional applications and Fiori experiences. CAP commonly supports cloud extensions on Cloud Foundry or Kyma; RAP runs in an ABAP environment. Select from business coupling, skills, contracts and lifecycle requirements, not from which acronym sounds newer.

SAP Build: choose the artifact you need

Process Automation provides workflows, decisions, forms and task automation. Prefer APIs to UI automation where a suitable stable API exists. RPA may still fit an interface gap, but UI changes and desktop execution become operating risks.

Build Code supports pro-code development; ADT is the ABAP development tool. Work Zone provides application access and digital workspaces. Standard and advanced editions differ in scope; advanced collaboration is not needed just because several users launch an app. Task Center aggregates supported tasks; the source system still owns task semantics and authorization.

Lifecycle note: SAP’s March 2026 announcement deprecates SAP Build Apps as a standalone product while maintaining existing contractual commitments. Do not present it as an unchanged default for a new standalone purchase. Read the transition guidance for the actual customer setup.

Mobile is a separate requirement, not a smaller browser

Mobile Services supports capabilities such as secure onboarding, push and supported offline synchronization. MDK uses metadata to build mobile experiences; native SAP BTP SDKs for iOS and Android offer deeper platform-specific development. A mobile entry app such as Mobile Start / its evolving Joule Work mobile experience is not the same thing as Mobile Services. Confirm the current product name and scope.

A warehouse worker who must operate without connectivity needs conflict handling, local-data protection and a synchronization design. “The UI is responsive” does not answer those requirements. Mobile Cards is a separate content/application capability; do not assume every card or approval experience is automatically embedded in the chosen mobile entry app.

Decision to remember: start from the required change, select the extension boundary, then choose the programming model, tool and runtime. The development lab makes that separation concrete.

The team knows ABAP well. Must the extension therefore run inside S/4HANA?

No. RAP-based applications can also run in SAP BTP ABAP environment where supported. Skills influence the choice, but business coupling, released interfaces, lifecycle, cost and the external-user boundary still need a decision.
