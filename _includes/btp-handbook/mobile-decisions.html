10 / Mobile architecture

Mobile SDK, MDK and Mobile Services are not interchangeable.

Mobile Services is the cloud service supplying selected mobile capabilities. MDK — Mobile Development Kit is the metadata-driven application approach and client. SAP BTP SDK for iOS / Android supplies native development libraries. The business backend remains a separate API and transaction owner. You may need this combination without needing a new CAP app, a new HANA database or Kyma.

Tree 14 — Online, offline or hybrid?

Must users keep working without a reliable connection?
├─ No → Online operations; avoid unnecessary local sensitive data.
└─ Yes → Can the business accept a bounded local snapshot and delayed validation?
   ├─ No → Keep authoritative decisions online; allow only safe offline capture.
   └─ Yes → Does the API and operation fit supported Offline OData capabilities?
      ├─ Yes → Design defining requests, local store, upload/download and errors.
      └─ No → Add an appropriate API facade or design custom synchronisation;
              compare that cost with simplifying the offline requirement.

Online is about freshness and authoritative answers. A stock availability check, credit decision or final posting may require the server. Offline is about continuity with explicit uncertainty. A technician can record inspection evidence locally, but “saved on device” must not be displayed as “posted in ERP”. A hybrid design often lets users capture evidence offline and performs final validation online.

Offline OData supports documented OData 2.0, 4.0 and 4.01 scenarios with limitations. Do not assume every action, query option, draft flow, relationship change or attachment API works offline unchanged. An arbitrary REST or GraphQL endpoint does not become an Offline OData backend just because it is configured as a destination.

Defining requests select the working set; they are not an access-control boundary. For example, download assigned open inspections and required reference data rather than the entire plant history. The server must enforce assignment and user scope even when the caller changes a filter. Decide how reassignment, deletion and authorisation changes reach existing local stores.

The sync lifecycle

Initial online onboarding → authenticate → initialise/download authorised working set
                    ↓
Read/write local store → show Pending on device → retain queued changes durably
                    ↓ connection returns
Upload pending operations → inspect backend errors → download accepted/current data
                    ↓
Show server-confirmed state OR a recoverable rejection/conflict; keep evidence intact.

Uploading before downloading is the usual sequence to publish local work before refreshing it; use the documented semantics for the selected client and application. Interrupted sync must be restartable. Partial success is not full failure and not full success: preserve which operations succeeded, which failed and which have an unknown outcome.

A useful business state model: Draft → PendingUpload → Submitted → Accepted, with separate Rejected, Conflict and UnknownOutcome paths. These are application states to design, not a claim that the SDK creates this exact state machine for you. Do not clear the local store to “fix sync” while it contains unsubmitted work.

Conflicts are business decisions

Two users edit one inspection: compare the server version using the API's supported concurrency mechanism. Decide which fields can merge and which require review. A server rule changes while offline: explain the rejection and allow correction. The server commits but the response is lost: reconcile using an operation identity/status contract before replaying a non-idempotent action. “Last write wins” is not a safe universal policy for quantity, approval or bank details.

Files need their own strategy. Bound photo size, attachment count and total store size; handle upload separately where the API requires it; link attachments to the correct business operation. Add malware scanning, content controls and retention when needed. A metadata sync does not prove every attachment has arrived.

Acceptance tests that expose the real design

Connectivity: initialise online, switch to airplane mode, create several records, kill/restart the app, reconnect and verify each server result. Cut the connection during upload and during download. Retry without creating duplicate business effects.

Correctness: change the same record on the server, revoke an assignment, return a validation error and return a partial batch result. The app must show the right state and retain recoverable work. Test the largest realistic working set, not only three demo records.

Security: use supported encrypted storage/key handling, minimise downloaded data, test logout and user switching, token expiry and lost-device procedures. Remote revocation cannot instantly contact a device that remains offline; define the acceptable offline access window and compensating controls. Never reuse one user's store as another user's starting state.

Provisioning and commercial prerequisites

The CF-based Mobile Services setup also needs the relevant CF org/space and runtime, route and service-instance quotas. This platform prerequisite does not mean you must develop a separate CAP backend. Mobile Services can be consumed standalone or through the applicable SAP Build setup; follow the onboarding and metering rules of the selected offer.

In the current SAP Build setup, custom MDK/native-SDK applications fall under the premium-user scope; the standard-user scope does not cover custom application development/deployment. Do not transfer this rule to a different standalone plan without checking its terms.

Minimum stack for an offline inspection pilot

R: MDK client/project, Mobile Services configuration with the required mobile/offline scope, supported OData backend, identity/access, local working-set design, sync/error UX and a backend conflict policy. C: Cloud Connector/connectivity for a private backend; custom CAP or RAP facade for missing API semantics; document storage/scanning for attachments; enterprise device management/distribution according to policy. O: Work Zone, a new HANA database, Integration Suite or Kyma when the pilot has no requirement for them.
