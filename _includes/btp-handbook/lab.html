15 / Build a small application

A supplier-review service you can inspect, test and change

The increment: an assigned external reviewer records a decision. A different internal approver authorizes the next step. That authorization is stored in our extension. It does not activate a supplier in ERP. Keeping those two facts separate is part of the design.

Get the local CAP lab scaffold. This original script creates nine local files; it does not install packages, connect to SAP or provision chargeable services. Read it before execution. Use Node.js 22 or later, and the currently supported Node.js/CAP combination when adding CAP dependencies.

Step 1. Create the exercise and test the business rules

node btp-review-lab.mjs supplier-review
cd supplier-review
npm test

Executed check: the supplied dependency-free policy suite passed 17 tests in Node.js. It checks roles, assignment, valid decisions, evidence, duplicate transitions and separation of duties. The CAP adapter, database concurrency, HTTP authorization and BTP deployment have not been executed in this authoring environment. They are separate checks below, not implied by the unit-test result.

Step 2. Understand the model, not only the syntax

entity Requests : cuid, managed {
  businessPartner : String(40);
  assignedReviewer : String(80);
  status : String(20) default 'OPEN';
  evidence : String(500);
  reviewedBy : String(80);
  approvedBy : String(80);
  version : Integer default 1;
}

cuid adds a technical UUID key; managed adds lifecycle fields. The BP reference identifies the object being reviewed; it is not a second supplier master. The version supports a conditional update so two requests should not silently overwrite one another. Test that behavior with the chosen database adapter.

The state path is OPEN → ACCEPTED or REJECTED → AUTHORIZED only from ACCEPTED. An external reviewer can record their assigned review. An internal approver can authorize an accepted review, but not their own assessment—even if the same person has both roles.

@readonly
@restrict: [
  { grant: 'READ', to: 'Reviewer', where: 'assignedReviewer = $user' },
  { grant: 'READ', to: 'Approver' }
]
entity Requests as projection on db.Requests;

@requires: 'Reviewer'
action recordReview(requestID : UUID,
                    decision : String, evidence : String)
  returns Requests;

The projection controls reading; the action controls a specific change. The handler must still verify request ownership, current state and input. A role annotation alone cannot enforce the complete process. In a real deployment, the approver's organization, tenant and object scope also need explicit controls.

Step 3. Add the CAP runtime locally

npm add @sap/cds @cap-js/sqlite
npm add --save-dev @sap/cds-dk
npx cds compile srv --to edmx
npx cds env get requires.auth
npm run dev

These commands require package-registry access. Resolve compatible dependencies and commit the resulting lockfile; later builds should use npm ci. The lab uses public, development-only fake users with basic authentication. Do not expose this server to an untrusted network or reuse its example password in any real system.

The startup output shows the actual service endpoint. Inspect /odata/v4/reviews/$metadata to see the service contract. Query Requests to see the projection. OData metadata and CRUD behavior save implementation effort; they do not define the approval policy for you.

Step 4. Prove the positive and negative paths over HTTP

curl -i -u reviewer:local-lab \
  -H 'Content-Type: application/json' \
  -d '{"requestID":"11111111-1111-4111-8111-111111111111",
       "decision":"ACCEPT",
       "evidence":"Registration details checked against supplied evidence."}' \
  http://localhost:4004/odata/v4/reviews/recordReview

The README contains the complete commands. First verify ACCEPTED. Then call authorizeActivation as the independent approver and verify AUTHORIZED. No ERP change has happened.

Step 5. Turn it into a BTP design, one dependency at a time

Identity: choose the production identity and authorization model. IAS authentication does not automatically supply application roles; use the appropriate authorization integration. XSUAA remains an option for suitable landscapes. Check token claims, assigned roles and object-level access.

Persistence: replace the development database only when the production requirements justify the target. Review migrations, backup, retention and test isolation. SQLite passing a local test is not proof of HANA behavior.

Deployment: in an authorized sandbox, inspect the current CAP deployment guidance. A Cloud Foundry path can use cds add hana, cds add xsuaa where that security model is selected, and cds add mta. Review generated descriptors, install required dependencies, build the archive and validate service bindings before deployment. These steps can create costs. The lab does not execute them automatically.

ERP: discover the released BP API for the actual edition and release. Verify the intended operation and status semantics; there is no universal “activate supplier” field to assume. Add a remote service/destination, communication setup, authorization, an outbound request identity and reconciliation. An application authorization followed by an ERP update is not one distributed database transaction.

UI: a Fiori elements application can use service metadata and annotations for standard interaction patterns. It still needs task-oriented design, error messages, accessibility and authorization tests. A generated list page is not the whole review experience.

Step 6. Make one change and explain the impact

Raise the minimum evidence length from ten to thirty characters. Write a failing test, change the policy and rerun the suite. Then explain which UI validation, API documentation and existing clients might also need a change. Finally, design—but do not blindly implement—a retry-safe ERP completion step.

Your practical artifact: a test result, one changed policy, a diagram of the proposed BTP deployment, a service/plan inventory and a list of unproven assumptions. Those are concrete signs of understanding; “I read the code” is not.
