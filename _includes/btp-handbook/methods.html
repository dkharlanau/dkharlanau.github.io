13 / Three methods, one design

Use a methodology to produce a decision, not another slide deck

The supplied lessons introduce three complementary SAP methods. Keep their names, phase order and main artifacts clear. Then apply them to an actual question. The tables below preserve that structure; the supplier-review application is our own worked example.

QuestionMethodResult
How should we add missing application behavior?SAP Application Extension Methodology.Scenes, extension tasks, technology selection and an extension target solution.
How should systems exchange information consistently?SAP Integration Solution Advisory Methodology (ISA-M).Integration scope, policies, technology mapping, best practices and a governed integration practice.
How can data support a measurable business outcome?SAP Data & Analytics Advisory Methodology (DAAM).Outcomes, data journeys, capability/solution architecture, governance and roadmap.

Application Extension Methodology: three phases

1. Assess Extension Use Case. Agree system context, business requirements and scenes. The SAP scene template uses Actions, Application Logic, System and Required Data. For a portfolio extension strategy, the method may instead start from the technology-assessment phase.

SceneActions and application logicSystem and required data
Request verificationAn employee starts a case; the application records the pending request.ERP and review service; BP reference, requester, assignment and initial status.
Collect external reviewThe specialist accesses only an assigned case and records findings.Partner-facing UI/service; permitted BP fields and evidence reference.
Approve the next stepAn authorized internal owner accepts/rejects the review outcome.Approval service/workflow; decision, reviewer, approver and policy.
Update and confirmA permitted ERP process records the result; the case tracks confirmation or an exception.Released ERP interface and owning business object; correlation and completion evidence.

2. Assess Extension Technology. Identify extension styles across presentation, application and data. Define technology-neutral tasks: present an external review screen, restrict case access, capture evidence, call the approved interface and retain status. Map tasks to candidate building blocks. On-stack versus side-by-side describes the extension domain, not the business need itself.

3. Define Extension Target Solution. Select the feasible combination using requirements and decision guidance. Compare standard governance, a side-by-side CAP service, workflow services and existing portal capabilities. Produce the target architecture and rationale. A custom status in our review app is not automatically a standard ERP “activation” field; choose the actual approved business operation for the customer’s edition.

DAAM: four phases, with iteration

PhaseActionEvidence
I. Scoping and baseline analysisAgree the investigation scope, current architecture/capabilities and prioritized pain points.Statement of architecture work, baseline and opportunity assessment.
II. Business outcomes and solution requirementsDefine the outcome and trace the data journey back from value to sources.Approved outcome, use-case/data-product requirements, solution context and data integration flow.
III. Capability map and solution architectureIdentify technology-neutral capabilities, map solutions, compare options and validate assumptions.Capability/solution maps, options assessment and target architecture; PoC findings where needed.
IV. Data governance and roadmapsAssess relevant maturity, organization and ownership gaps; sequence the work.Governance actions, roles, data-product ownership and an implementation roadmap.

Phases II and III can repeat. For our case, start with “reduce the time to a valid supplier decision”, not “buy a dashboard”. Use the Data Journey Map’s Action, System, People and Experience lenses. Work backwards: what decision will the procurement lead make, what measure supports it, which case events define it and where do they originate?

Two related use cases—review-cycle monitoring and identifying repeated rework—help test whether the data product is reusable. Define the request-level grain, reopenings, timestamps and access scope. Compare live access and persisted history according to requirements, then map capabilities to products. Governance starts during discovery; Phase IV consolidates its actions, not postpones all data ownership until the end.

A weighted options matrix can help compare fit, cost and complexity. Reject options that violate mandatory constraints before scoring. A high average score cannot compensate for prohibited external ERP access or an unmet recovery requirement.

ISA-M: four phases and a practical interface assessment

PhaseOutput
1. Assess Your Integration StrategyIn-scope integration domains, styles and use-case patterns.
2. Design Your Hybrid Integration PlatformTechnology mapping, integration policies and interface assessment.
3. Define Integration Best PracticesDos and don’ts, architecture blueprints and development guidelines.
4. Enable a Practice of EmpowermentRoles, responsibilities, governance and integration quality assurance.

Domain describes the landscape relationship, such as cloud-to-on-premise. Style describes the integration category, such as process or data integration. Use-case pattern describes its purpose, such as application-to-application, B2B or B2G. An integration area combines a domain and style in the relevant taxonomy. Do not use “API” as a substitute for all of these classifications.

Integration Assessment uses configured questionnaires, characteristics and catalogs. An application profile names a product; an application instance identifies an actual deployment. Technology profiles and instances apply the same distinction to integration technology. A product in the catalog does not prove the customer has it installed or licensed.

Worked request: synchronize newly created/changed BP data from on-premise S/4HANA to Salesforce using an agreed ten-minute polling design. Record source and target instances, classification, required fields, keys, transformations, authentication and operating needs. Review available content and proposed technologies. Then assign real deployments and owners, approve the interface contract and test it.

Polling needs a reliable change-selection/watermark approach, overlap handling, deduplication, and a decision about deletions and missed runs. An event-based alternative may be better, but only after checking released events and the business requirement. Integration Assessment’s recommendation does not prove either design will work.

AIF may satisfy some business-monitoring requirements in a supported backend scenario. “Business users need monitoring” is not a universal rule that automatically mandates AIF. Document why the chosen combination fits this interface.

One coherent set of deliverables

The extension method owns the external reviewer’s experience and application behavior. ISA-M owns the exchange contract and integration standards. DAAM owns the decision-support data and its quality. The business process owner approves authority and success criteria. Connect these decisions through a common BP/request identity and the same target architecture.

Where to look: Discovery Center for services, plans, missions and estimation; Guidance Framework and Architecture Center for decision guidance and reference designs; Business Accelerator Hub for APIs, events and integration content; Trust Center for provider assurance. A reference architecture is a starting point, not a customer-specific contract.

Reference: methods-extension, methods-integration, methods-data, discovery, bp-api, trust.

Which method should lead a project whose only requirement is trustworthy supplier-review reporting?

DAAM should lead the data/analytics decision. Use the extension method only if required application behavior is missing, and ISA-M for necessary interface choices. Three methodologies do not mean three mandatory projects or three new products.
