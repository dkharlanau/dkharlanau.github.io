01 / Start with the decision

Do not start by buying a platform-shaped solution.

A good BTP design answers six questions: what must change, who owns the business data, where the code runs, how the systems communicate, who may act, and what happens when a dependency fails. Product names come after those answers.

Use three reading routes. Choose: follow the trees and challenge one alternative. Build: follow a recipe and identify its actual configuration objects. Broaden: scan the service map, then assemble one pilot without copying an entire reference architecture.

R / Required means required for the selected pattern, not for every BTP project. C / Conditional means add it only when the stated requirement exists. O / Optional means useful but replaceable. Security, ownership, recovery and cost control are required responsibilities; buying every SAP service carrying those names is not.

Keep the layers separate

LayerExamplesThe decision it answers
Business systemS/4HANA, MDG, SuccessFactorsWhere is the authoritative transaction or master record?
Programming model / libraryCAP, RAP, SAPUI5, SAP Cloud SDKHow do we implement the application? These are not four hosting subscriptions.
RuntimeCloud Foundry, Kyma, ABAP environmentWhere does our server-side code execute?
Managed serviceHANA Cloud, Destination, Mobile ServicesWhich platform responsibility do we consume instead of building?
Product / capabilitySAP Build; Cloud Integration within Integration SuiteWhich business or development capability and package fit?
Development toolBAS, ADT, local IDE, CLIWhere do developers work? An IDE is not the production runtime.
Commercial planA service plan, included use, committed capacityWhat may we use, how much, where, and on what terms?

Three useful negatives: CAP does not imply Kyma. A mobile application does not automatically need a custom CAP backend. An S/4HANA connection does not automatically need Integration Suite.

02 / Extension boundary

First decide whether anything belongs on BTP.

Tree 01 — Standard, in-app or side-by-side?

Does a standard process meet the requirement?
├─ Yes → Configure the standard application. Do not build a duplicate.
└─ No → Is the gap a supported field, UI adaptation, rule or extension point?
   ├─ Yes → Use the relevant in-app / key-user extension.
   └─ No → Must custom logic participate in an ERP-local transaction?
      ├─ Yes → Assess supported on-stack developer extensibility / RAP.
      └─ No → Independent UI, cross-system logic or release lifecycle?
         ├─ Yes → Design a side-by-side extension; choose its runtime next.
         └─ No → Recheck the gap. More platforms are not a requirement.

Example: adding an approved custom BP field differs from building an external supplier-evidence portal. The former may fit standard extensibility. The latter may justify BTP because users, document handling and releases are independent. Neither choice transfers master-data ownership away from MDG or S/4HANA.

Clean core is an interface discipline, not a location label. A side-by-side app that updates ERP tables directly still creates coupling. BTP ABAP environment is separate from ERP: using ABAP there does not grant local access to ERP tables or its database transaction. Check released APIs, events and extension points for the actual edition and release.

Decision record: name the business gap, selected option, rejected alternative, data owner, interface, operating owner and a revisit trigger. Reject an option that cannot meet access, residency or recovery constraints before comparing convenience.

03 / Runtime and code

Cloud Foundry, Kyma or ABAP: choose the operating model.

Tree 02 — Which runtime?

Is a managed product enough: workflow, integration or ready-made app?
├─ Yes → Configure that product. No separate custom-app runtime by default.
└─ No → Does the implementation require ABAP Cloud / RAP?
   ├─ Yes → On-stack if transaction-local; BTP ABAP environment if side-by-side.
   └─ No → Do you need Kubernetes APIs, operators, custom workload topology,
           or container/network control that the managed app model cannot meet?
      ├─ Yes → Kyma, provided a team owns Kubernetes application operations.
      └─ No → Start with Cloud Foundry for supported web/API/worker workloads.
              Move only when a concrete constraint defeats that choice.

A container is not, by itself, a reason to choose Kubernetes. Neither “microservices”, “events” nor “high volume” automatically means Kyma. Cloud Foundry can run multiple services and workers. Kyma is valuable when Kubernetes-specific control is part of the requirement, not just part of the diagram.

Counterexample: an order-event consumer with one queue and a simple API does not require Kyma. Choose CF unless a workload constraint says otherwise. Conversely, a required Kubernetes operator cannot be replaced by calling a CF application “cloud native”. Validate the operator, permissions and managed-cluster restrictions before committing.

Tree 03 — CAP, RAP, general code or a managed process?

What dominates the implementation?
├─ Domain entities, OData/REST services, business rules → CAP in Node.js or Java.
├─ ABAP transactional business objects → RAP on a supported ABAP target.
├─ Human tasks, forms, approvals, decision tables → Build Process Automation.
├─ Special protocol, algorithm or library outside these models → General code.
└─ A standard supported integration → Configure the integration, not a new app.

CAP is a model, not a language and not a runtime. Select Node.js or Java for team competence, required libraries and operational standards. CAP can target CF or Kyma. SAP Cloud SDK helps application code consume supported APIs and destinations; it does not perform every business mapping or replace Integration Suite.

From a CAP idea to deployable objects

Model: put owned entities in db/, expose a deliberately small service in srv/, and keep the UI in app/. Define actions, validations and authorisation annotations. Import the real remote API metadata and implement only the operations the business needs. A read-through facade need not persist a second copy of the master data.

Prepare: choose production identity and persistence explicitly. For a conventional HANA + XSUAA + CF pattern, the CAP facets are cds add hana, cds add xsuaa and cds add mta. Inspect the generated xs-security.json, mta.yaml, database deployment and service dependencies. These commands configure one selected pattern, not a universal mandatory stack.

Deploy: build an MTA archive and deploy it to the authorised CF org/space, or use the documented CAP deployment workflow. For Kyma, cds add kyma prepares the corresponding deployment; supply a reachable image registry, build/push images, review the generated chart, and bind the required BTP services. Do not commit credentials or put environment-specific secrets in the chart. A successful image pull is not an application acceptance test.

Prove: test a permitted operation, denied role, wrong tenant, expired token, unavailable backend and restart after a pending operation. Check both HTTP behaviour and persisted business state. A local mocked login is not production authentication.

04 / User experience

Choose the client separately from the backend.

Tree 04 — Which UI?

Where must the work happen?
├─ Browser, standard lists/forms/object pages → Fiori elements + OData annotations.
├─ Browser, specialised interaction → Freestyle SAPUI5 or another suitable web UI.
├─ One entry point for many business apps → Add Work Zone when needed.
├─ Unified supported approval inbox → Add Task Center when needed.
└─ Native mobile / unreliable connection → Follow the mobile decision tree.

Fiori elements reduces repetitive UI work when the floorplan fits. Freestyle UI5 gives more control at the cost of more implementation. HTML5 Application Repository stores static frontend content; it does not run CAP or store transactional business data. The selected entry pattern supplies routing and authentication: for example a managed app router through Work Zone, or an application-owned router.

Work Zone standard edition is an application-entry option; advanced edition adds a broader workspace experience. Neither is mandatory for every web application. Task Center aggregates supported tasks; the provider still owns the workflow and approval semantics. A task tile must not become a second, inconsistent workflow engine.

Tool/package trap: BAS is an IDE, SAP Build Code is a development offering, and SAP Build is a portfolio/package context. None is an alternative execution environment to CF, Kyma or ABAP. For new low-code procurement, check the current SAP Build offer: standalone SAP Build Apps was retired from sale on 23 March 2026; existing contracts have their own continuation terms.

05 / Integration

Direct call, iFlow, API gateway or event?

Tree 05 — What must the connection do?

Does the caller need an immediate answer?
├─ Yes → One supported API, little transformation, clear ownership?
│  ├─ Yes → Direct backend API consumption can be enough.
│  └─ No → Cloud Integration for mapping, adapters and mediated flow.
└─ No → Is this a fact that independent consumers must receive?
   ├─ Yes → Event-driven delivery; choose a broker/event service below.
   └─ No → Batch, scheduled command or human approval?
      ├─ Scheduled work → Job Scheduling + a safe worker, or integration scheduling.
      └─ Human process → Build Process Automation / existing business workflow.
Across these branches: add API Management when API publication, traffic policies,
consumer governance or external exposure justify it. Do not insert it by reflex.

Cloud Integration: the concrete artifact is an integration flow with sender/receiver adapters, connections, mappings, authentication material, exception handling and monitoring. API Management: the artifact is an API proxy/product and its policies. A gateway can protect and shape API access; business-object authorisation must still be enforced by the application.

Example: a CAP screen reading one released S/4 API can call it directly through the selected destination/authentication path. An EDI order from a trading partner, with document transformation and protocol handling, is a different problem: assess Cloud Integration, Integration Advisor and Trading Partner Management. Buying the suite does not activate every capability or include every edition.

Tree 06 — Which event option?

What event landscape are you building?
├─ Supported SAP cloud application event distribution / formation
│  → Evaluate SAP Cloud Application Event Hub and its supported participants.
├─ Application queues/topics and asynchronous extension integration
│  → Evaluate the Event Mesh capability in the selected Integration Suite edition.
├─ Enterprise-wide mesh across brokers, clouds and locations
│  → Evaluate Advanced Event Mesh; check separate commercial scope.
└─ Existing standalone Event Mesh instance
   → Check its contract and migration path; do not assume new-customer availability.

Queue versus topic: a topic describes an event stream; a durable consumer queue holds deliveries for its consumer group. Separate subscribers usually need independent queues. Design consumer acknowledgement, bounded retry, dead-letter handling, retention and ordering requirements. More consumers on one queue usually share work; they do not each receive a separate copy of every message.

Exactly-once business effect is a contract, not a checkbox. A consumer can crash after ERP commits but before the message is acknowledged. Redelivery is then expected. Use a stable operation identity, an atomic deduplication/outbox design where applicable, and receiver-specific status lookup or reconciliation. Do not invent an idempotency header for an API that does not support one.

Edge Integration Cell is a selected integration runtime deployed in a customer-managed environment. It is not a generic substitute for Kyma, nor a promise that cloud control-plane dependencies disappear. Validate supported adapters, connectivity, operating responsibility and edition.

Trace the actual hops

Public API:  Browser → authenticated app entry → CAP → destination/auth → S/4 API
Private API: CAP → Connectivity path → Cloud Connector → allowlisted ERP resource
Mobile:      MDK/native client → Mobile Services → configured backend destination → API
Mediated:    Sender → Cloud Integration iFlow → mapping/error handling → receiver
Event:       Business producer → event service/queue → consumer → durable result
AI:          App backend → authorised retrieval → AI Core endpoint → validated output

Not every identity token can cross every arrow unchanged. For each hop name the endpoint, protocol, caller identity, trust relationship, timeout and correlation ID. The mobile destination and the BTP Destination service configuration are related concepts, not automatically the same object.

One real API, not an imaginary “activate supplier” button

For relevant S/4HANA Cloud Public Edition BP integration, investigate API_BUSINESS_PARTNER and communication scenario SAP_COM_0008. Configure the required communication system, user/authentication and arrangement for that scenario. Check the specific entity and supported operation, required fields, custom-field exposure, CSRF/session requirements and authorisations. This is not a universal API for every MDG change-request operation or every supplier-status transition.

Version interfaces deliberately: required fields, error schema and event meaning are contracts. Support an agreed transition window and test old consumers. Treat ETag/If-Match as concurrency protection where supported, not as duplicate-request prevention.

06 / Connectivity and identity

A reachable endpoint is not an authorised operation.

Tree 07 — How do we reach the backend?

Is the approved API reachable over the public internet?
├─ Yes → HTTPS + supported authentication; destination configuration when useful.
│        Cloud Connector is not required merely because the target is SAP.
└─ No → Which private path is supported for this runtime and target?
   ├─ On-premise/private network → Cloud Connector + relevant Connectivity setup.
   ├─ Supported hyperscaler private endpoint → Evaluate Private Link Service.
   └─ Neither → Resolve network architecture; do not expose ERP broadly as a shortcut.

Destination holds endpoint and supported authentication configuration. Connectivity provides the relevant connectivity facility. Cloud Connector runs in the private network, establishes an outbound tunnel and exposes allowlisted resources. It is not a general VPN and not a licence to expose every path. Kyma may use the applicable Connectivity Proxy / Transparent Proxy and service-binding integration; CF-specific environment variables are not a universal Kubernetes configuration recipe.

Tree 08 — Which identity and authorisation components?

Who is calling?
├─ Human → Corporate identity federation / IAS as the selected login architecture.
│  ├─ Existing supported XSUAA application model → scopes, roles, role collections.
│  └─ Supported IAS + Authorization Management model → policies and app integration.
├─ System / job → supported workload identity or OAuth client; least privilege.
└─ User lifecycle synchronisation needed → add IPS; provisioning is not login.
At the backend: technical identity or supported principal propagation?
Choose and test the whole chain. Neither choice bypasses backend permissions.

IAS authenticates/federates. IPS provisions identities. XSUAA supports application authorisation/trust in the relevant model. Authorization Management supports policy-based authorisation in its supported integration model. Do not install both authorisation approaches without an actual architectural reason.

Four checks at the app boundary: validate issuer and audience, token validity, required permission, and tenant/object scope. A user with the reviewer role must still be prevented from reading another supplier's case. Hiding a UI button is not a control. Filter the database query or service result by authorised scope; do not retrieve everything and hope the UI filters it.

Secrets: use supported service bindings, credential handling and rotation. Do not embed privileged client secrets in browser JavaScript or native app bundles. Separate administrator and business-user access. Keep sensitive payloads out of routine logs and set retention deliberately. Credentials, destinations, trust settings and role mappings also need recoverable configuration.

07 / Data placement

Store the extension's state, not a second ERP.

Tree 09 — Do we need a database, and which kind?

Does the extension own durable state?
├─ No → Read through released APIs; no extension database by default.
└─ Yes → What kind of state?
   ├─ Cases, transactions, joins, rules → HANA Cloud or a supported SQL alternative.
   │  ├─ HANA-specific capabilities / SAP model fit → HANA Cloud.
   │  └─ Conventional relational needs → assess PostgreSQL and CAP support matrix.
   ├─ Files, photos, binaries → Object Store; or Document Management for document semantics.
   ├─ Disposable fast cache → Redis; never the only authoritative record.
   ├─ Governed analytical models → Datasphere / relevant Business Data Cloud architecture.
   └─ Dashboards and planning → SAP Analytics Cloud consumes suitable governed data.

HANA Cloud is not mandatory just because the app runs on BTP. CAP supports database choices with different feature and deployment constraints. Choose for transactions, querying, search/vector needs, extensibility/multitenancy requirements, operations and total cost. Local SQLite development does not prove the production database behaviour.

HANA HDI container is an application database-isolation/deployment construct; it is not another complete HANA Cloud database. Object Store stores objects; a document repository adds document-oriented services. Test backup, versioning and restore for the actual plan: a managed service does not imply every form of automatic recovery. A cache should be rebuildable.

MDG versus Master Data Integration: governance decides how master data is created, approved and controlled; distribution moves supported master data between applications. Neither a replicated copy nor an event bus becomes the approval authority. Start with ownership and the supported business-object model.

Datasphere versus Business Data Cloud: Datasphere supplies data integration/modelling and semantic capabilities. Business Data Cloud is a broader commercial and solution context with data products and optional components, not “HANA with another name”. SAC is an analytics/planning consumer, not the default transactional persistence layer for CAP. Source-data rights, refresh/freshness, row-level access and additional component entitlements remain separate decisions.

08 / AI and process logic

Use an agent only when rules are not enough.

Tree 10 — Which AI path?

Can a deterministic rule or query solve the problem?
├─ Yes → Use it. Do not pay an LLM to compare two known fields.
└─ No → What is the missing capability?
   ├─ Extract fields from supported documents → SAP Document AI + validation/review.
   ├─ Explain or draft from approved knowledge → grounded model access / RAG.
   ├─ Existing SAP copilot interaction fits → evaluate Joule in that product.
   ├─ Custom Joule skills / agents → evaluate Joule Studio and its prerequisites.
   └─ Custom ML workload lifecycle → assess AI Core and the required model pipeline.

AI Core is the runtime/service boundary for supported AI workloads and generative AI hub access. AI Launchpad is a management application, not an obligatory hop in every inference request. Generative AI hub is a capability; current access requires the documented AI Core extended plan. Check model, region, resource group and running deployment before application integration.

One concrete RAG path: authenticate the user → select documents the user may access → retrieve relevant passages → call the configured model/orchestration endpoint → return an answer linked to evidence → record necessary operational metadata. A vector database is conditional on the retrieval design; HANA vector capabilities are one option, not a mandatory companion to every model call.

What must not happen: an uploaded document must not redefine the agent's permissions; retrieved text is untrusted input. Enforce allowlisted tools, argument validation, action limits and approvals outside the prompt. A confidence-looking number is not proof of correctness. Test missing evidence, contradictory documents, malicious instructions, access revocation and excessive cost.

Tree 11 — Workflow, RPA or agent?

Is the action path stable and explicitly defined?
├─ Yes → Existing business workflow or Build Process Automation.
│  └─ No usable API, UI automation is unavoidable → bounded RPA with exception ownership.
└─ No → Does an evaluated agent add value in choosing among permitted steps?
   ├─ Yes → bounded agent + deterministic tools + approval before risky effects.
   └─ No → improve the process/data first; do not automate uncertainty.

Keep one owner for the approval state. An agent may draft a recommendation, but it must not silently grant itself authority to change bank details or release a blocked supplier. Define the owner, allowed data, allowed actions, escalation path, evaluation set, spend limit and a kill switch. Inventory/governance tooling can document these controls; the runtime and business systems must enforce them.

09 / Landscape and tenancy

A role, an entitlement and a tenant solve different problems.

Global account: commercial and administrative umbrella. Directory: optional grouping/delegation. Subaccount: a key regional, trust and entitlement boundary. CF org/space: application and development organisation within that environment. Kyma cluster/namespace: Kubernetes infrastructure and workload organisation. A namespace is not automatically sufficient isolation for unrelated customers.

Tree 12 — How much isolation?

Who shares the solution?
├─ One organisation → separate development/test/production and access responsibilities.
├─ Multiple organisations, strict dedicated isolation required
│  → dedicated deployment/subaccount or stronger boundary justified by the requirements.
└─ SaaS with shared application operations
   → tenant-aware application model + onboarding/offboarding + tenant-isolated data,
      destinations, credentials, authorisation, jobs and observability.

Subscription is overloaded. A commercial subscription is a purchasing model. Subscribing to a SaaS application in a subaccount is a technical onboarding action. A service instance is provisioned configuration/capacity; a binding supplies connection information to a consumer. An entitlement permits a service plan; a quota allocates a measured resource; a role permits a person or workload to perform an action. None substitutes for the others.

A standard CF org is associated with its subaccount; Kyma has its own cluster model and a subaccount can support multiple clusters. Verify the selected environment and regional setup rather than memorising “one subaccount equals one runtime”. For SaaS, assess SaaS Provisioning, Service Manager and the supported CAP multitenancy lifecycle. Test tenant deletion, key rotation and background jobs, not only login.

Ownership: platform owner handles subaccounts and entitlements; security owner handles trust and access design; development/integration teams own their artifacts; operations owns recovery; business owns the approval rules; procurement confirms usage rights. Write a small RACI rather than assigning every task to “the BTP team”.
