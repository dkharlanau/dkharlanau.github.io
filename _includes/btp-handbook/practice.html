16 / Explain, challenge and prove

Use the guide as a case workbook

Use three levels. First explain a worked example with the answer visible. Next hide the explanation and complete a missing decision. Finally change a constraint and defend a new design. The aim is transfer: choosing sensibly when the question no longer looks like the page.

An answer structure that works in a workshop

Outcome → owner → options → decision → controls → evidence. Start with what changes for the business. Name the application that owns the transaction. Compare two viable options. Choose under stated constraints. Explain security and recovery. Finish with how you will prove the outcome.

Example answer: “We need external supplier verification without giving the partner general ERP access. I would first check the standard onboarding process. If an extension is needed, I would separate the external review from internal authorization, keep S/4HANA as the master-data owner, and use a released interface for the approved change. CAP on an appropriate runtime is one option, not the requirement itself. I would check roles, data exposure, duplicate handling, service plans and support ownership. The design is accepted only when the review, approval and final ERP state can be traced end to end.”

Answer before opening the review notes

1. The business asks for BTP, but standard ERP covers the workflow. What do you propose?

Compare the standard process plus configuration with a custom extension. Check usability, external access, lifecycle, cost and remaining gaps. Prefer standard when it meets the need. Evidence: fit-gap record and a demonstrated workflow, not a service list.

2. The API call timed out after sending a purchase request. Should the agent retry?

First determine whether the receiver created the business document. Use a correlation key, request status or reconciliation query. Retry only under the agreed idempotency contract. Evidence: one intended business effect, including a timeout-and-redelivery test.

3. A reviewer can log in, but must see only assigned BPs. Where is the control?

Authentication establishes identity. Application roles and instance-level filtering limit access; the backend enforces its own business authorization. Test unauthorized IDs and direct API access, not only hidden UI buttons. The lab demonstrates why ownership checks are needed inside actions too.

4. An event broker is available. Does that make events the right design?

Not automatically. Check latency, consumer independence, event availability, delivery/ordering requirements, recoverability and consistency. Synchronous request-response may be clearer when a user needs a confirmed outcome. Event delivery still needs monitoring and duplicate-safe consumers.

5. Procurement and Finance disagree on “supplier delay.” Which tool fixes it?

First agree the business definition, grain, source timestamp, partial deliveries, calendars and organization filters. Then model and serve the agreed measure. A dashboard cannot resolve an ownership dispute. Use DAAM and a data-product contract before choosing more technology.

6. The cheapest supplier exists only in a spreadsheet. What may an agent do?

Treat it as a lead, not approved master data. Check source authority, qualification, contract and capacity. Route a vetting request under policy instead of creating an unauthorized PO. More model confidence does not change the supplier’s approval status.

7. A customer wants Kyma because it “scales.” What do you ask?

Ask about workload, container requirements, integration, deployment control, skills, support and cost. Cloud Foundry can also scale applications. Choose Kubernetes flexibility only when it solves a real requirement and the operating model is supportable.

8. The proof of concept was free. Why is the production estimate much larger?

Account for the selected paid plans, minimum sizes, multiple stages/replicas, runtime hours, storage, data transfer, integration messages, AI usage, logging retention, support and operations. Free plans and trial limits are not the production bill. Validate quantities with observed usage and contract terms.

9. The agent is registered in AI Agent Hub. Can it access any verified MCP server?

Registry state is not blanket access. Check configured enforcement paths, specific tool permission, identity, scopes, tenant/object access and current policy. A verified server can still expose an action that this agent must not call.

10. A deployment rollback succeeded, but a wrong PO remains. Why?

Software rollback reverses a code/configuration deployment, not completed ERP business transactions. Use the business process’s authorized correction or compensating action. Evidence must include both the software version and the corrected document state.

11. Which of the three SAP methodologies should lead the supplier-review design?

Use the extension method for missing application behavior, ISA-M for integration strategy and interface assessment, and DAAM for decision-support data and analytics. Their outputs join in one architecture; they are not three required purchases.

12. You need to explain the design in ninety seconds. What do you leave out?

Keep the business outcome, ownership boundary, chosen option, one important alternative, access/recovery controls and proof. Leave detailed service catalogs and implementation syntax for follow-up questions. Then be ready to trace one concrete request without hiding behind product names.

Two original oral rehearsals: defend the design under a new constraint

Give an initial answer in about 90 seconds, then answer each challenge in your own words. These are original practice scenarios, not real exam questions. Use the review notes only after your attempt.

Rehearsal A: design supplier onboarding, then remove half the proposed services. What survives?

Start with the standard process and the external-user boundary. Retain accountable approval, permitted ERP access, case-level authorization, durable evidence and recovery. A small CAP service with suitable identity and persistence is one candidate. Remove a separate broker, middleware, agent or analytical platform unless its requirement remains. Check each retained service/plan, user scope, stage and operating owner. The smallest supported design is a defensible outcome.

Challenge A1: ERP is private-network only, and the reviewer must never get an ERP identity. Trace the request.

Authenticate the reviewer at the application boundary and authorize their assigned case. An internal approval initiates a backend call using the specifically permitted integration identity. In the selected Cloud Foundry pattern, resolve a destination and use Connectivity/Cloud Connector to the allowlisted endpoint. The ERP validates its technical caller and business operation. The app retains initiating and approving identity; it does not pass unrestricted ERP access to the browser.

Challenge A2: the user waits 20 seconds, sees a timeout and presses Submit twice. What state is safe?

Record an unknown result after a possibly committed remote write, not an automatic business rejection. Reconcile by the supported request/business reference. A retry is safe only under the receiver contract. Disable duplicate effects using an appropriate durable key and concurrency control; two app replicas must share that protection. A local UI button alone is insufficient.

Rehearsal B: a sponsor asks for “AI everywhere”, near-zero downtime and a fixed low bill. How do you respond?

Convert each wish into an outcome and measurable constraints. Keep deterministic approval rules. Evaluate an assistant only for the unstructured evidence problem; control permitted retrieval and tools. Agree latency, traffic, RTO/RPO, data residency and cost assumptions. Explain that redundancy, model usage and integration can add cost. Compare a simpler option and mark conflicts the sponsor must resolve rather than promising all three wishes without a trade-off.

Challenge B1: the model is accurate on examples, but the plan and region are unknown. Can you commit to delivery?

No. Confirm the exact AI capability, eligible plan, runtime/deployment, supported model/region, permitted data path and metering. Test authorized and forbidden inputs, missing evidence and changed model behavior. Treat the plan and region as blocking design assumptions, not procurement details to discover after implementation.

Challenge B2: procurement asks why you need all three architecture methodologies.

We do not run three separate projects. The extension method shapes missing application behavior, ISA-M governs the interface choices, and DAAM defines reusable decision-support data when needed. Their outputs share the same business scope, identifiers and ownership. Use only the relevant depth, and name the artifact each method changes.

Self-check, without a fake readiness score: could you explain the first design, trace its actual calls, defend an alternative, identify a license unknown and describe a recovery test? If one answer depends on “the platform handles it”, return to that boundary. Fluency is useful; specific, consistent reasoning is the evidence.

Practical familiarity helps, but this text does not establish formal eligibility, substitute for your enrollment requirements, or guarantee a passing result. Readiness means you can explain the platform without mixing products and runtimes, defend a scoped design, estimate its consumption, trace a failed call, run and change the lab, and name what remains untested. Revisit the weak decision rather than rereading everything mechanically.

Suggested repeat: explain the case today, reconstruct it without notes in a few days, then solve it again with one constraint changed. Pair retrieval with diagrams and a small implementation. There is no claim that one technique is universally best or that a fixed schedule works for every learner.
