Applied architecture / Decisions and acceptance evidence

Make the smallest design that survives a review

The product chapters explain capabilities. This workbench tests the missing step: selecting a coherent set, proving its boundaries and removing components that do not earn their place. The choices and numerical targets below are original teaching examples; product-specific constraints are linked to SAP documentation.

A required capability is not a required SAP product

Our supplier-review case requires restricted external access, a review record, independent internal authority, a supported ERP change and recovery evidence. It does not automatically require every service shown in a reference architecture. Compare three options first: existing ERP/MDG governance; an existing workflow plus secure partner access; a custom side-by-side service only for the remaining gap.

Decision rule: apply hard gates before weighted scores. A hard gate is a condition that cannot be traded away: a missing released write operation, unacceptable data processing location, prohibited external access or unavailable required service plan. Reject an infeasible option before comparing convenience, skills or cost. This is a design-review rule, not an additional SAP methodology phase.

One concrete SAP reference: public-edition BP integration is documented under communication scenario SAP_COM_0008. A scenario describes the supported integration scope; a communication system represents the partner system; the arrangement configures the scenario for the connection and its identities. It is not a BTP role collection. Verify the exact release, API restrictions and authentication before implementation. BP integration · BP A2X restrictions.

Two different API safeguards: a CSRF token protects applicable request contexts against cross-site request forgery; it is not a business role. An ETag identifies a resource version; an If-Match condition can prevent overwriting someone else's change. A version conflict requires rereading and reconsidering the change, not deleting the check. Neither mechanism replaces request idempotency. Use the actual API's documented token and concurrency behavior. CAP concurrency · Remote services.

License gates: make uncertainty specific

For every selected component record: product and SKU/plan; global account and commercial model; provider/region; permitted purpose and users; included quantity; billable metric; dependent services; production/non-production scope; expiry or lifecycle condition; contract owner. A service entitlement enables technical consumption; it does not establish all rights for the connected ERP or a third-party product.

Cost drill, synthetic volumes: polling every ten minutes produces 144 calls per day per endpoint before retries, even without a new supplier. At 3,000 cases per month, two model calls per case, 4,000 input tokens and 500 output tokens per call imply 24 million input and 3 million output tokens. These are engineering quantities, not SAP billing units. Apply the selected service's conversion, inclusions and contract rates; count evaluation, failed work, storage and logging too. AI metering.

Write quality requirements that can be tested

SLI is the measured service indicator; SLO is the target; SLA is the relevant contractual commitment. A p95 latency of two seconds means 95% of the measured requests finish within that time, under the stated workload. It is not a promise that every request completes in two seconds.

ConcernExample requirement—not an SAP commitmentAcceptance evidence
Performance and loadReview-list p95 below two seconds at the agreed peak of 50 concurrent users.Representative data volume, query and identity path; slow backend and rate-limit tests.
ConsistencyNo lost review decision; no duplicate intended ERP change for one accepted request key.Competing updates, duplicate delivery and commit-then-timeout tests.
RecoveryProposed RTO four hours and RPO fifteen minutes, subject to business acceptance.Restore data and configuration, recover identities/connections, replay safely and reconcile ERP state.
Tenant and data isolationNo other supplier's restricted evidence in reads, logs, caches, jobs or model context.Negative object/tenant tests, including export and retrieval paths.
Degraded operationA model outage must not prevent an authorized manual review.Disable the optional model path and perform the supported fallback.
Operational ownershipEvery stuck approved request has an accountable owner and a documented escalation.Alert delivery, acknowledgment, runbook and confirmed business recovery—not just a sent email.

A failure domain is a set of components that can fail together. Two app instances do not prove recovery from a region outage or a failed shared identity dependency. Map the critical path, including database, identity, ERP, integrations and any mandatory model call. SAP's multi-region CAP reference uses specific prerequisites and entitlements; do not copy its topology without a recovery requirement. Customer-managed service configurations also need an explicit backup/restoration plan. SAP multi-region example · Configuration backups.

Use a RACI discussion to separate who does the work (Responsible), who owns the outcome (Accountable), who advises (Consulted), and who is informed. In this case the internal process owner retains approval authority; platform operations owns its agreed recovery work; the external reviewer supplies evidence. Name a person/team and an escalation, not just “SAP” or “IT”.

Optional practical drill: the receiver committed, but the reply was lost

Recovery-contract example and its tests form a dependency-free Node.js exercise. Save both in one folder and run node --test btp-recovery-contract.test.mjs. It uses only an in-memory fake receiver: no credentials, network calls, BTP resources or ERP postings.

Inspect the difference between AUTHORIZED, UNKNOWN, CONFIRMED and RECONCILIATION_REQUIRED. The exercise checks tenant-qualified request keys, payload reuse conflicts, expired approvals and a lost response. Tests of a fake receiver do not establish that a real SAP API supports idempotency or status lookup; that remains a contract-discovery task.

Architecture defense: procurement wants the cheapest design and says the business is small. What do you remove?

Consider removing optional AI, a new analytical data platform, an extra gateway or a custom portal where existing supported capabilities meet the requirement. Do not remove object authorization, internal approval, data ownership, error handling or recovery evidence. Simplify products, not necessary controls. Confirm costs against actual plans rather than assuming every removed diagram box was separately billed.

The business now needs a shared service for twenty subsidiaries. Which decisions must be revisited?

Tenant/organization boundaries, identity and delegated administration, per-tenant destinations and data isolation, configuration and schema upgrades, quotas and noisy-neighbor risk, support ownership, service availability, data processing locations and charge allocation. A new subaccount, directory or namespace alone does not settle all those questions.
