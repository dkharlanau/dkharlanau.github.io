Operating model for a governed Daybreak workflow

An operating model is the practical working pattern that defines who can do the work, what they can do, which assets and environments are approved, which tools and data may be used, which approvals are required, what evidence is produced, who reviews the output, how long evidence is retained, and where final decisions are recorded.

A bounded evaluation needs this operating model before the workflow starts. Tool capability does not answer questions about authorization, accountability, evidence handling, or customer-owned decisions.

Operating model question What it helps clarify
Are we allowed to do this work? Authorization, defensive purpose, customer permission, and scope.
Is the asset customer-owned and the environment approved? Whether the target and environment are appropriate for the workflow.
What can the workflow access and do? People, systems, tool permissions, data access, and allowed actions.
What evidence will be produced, reviewed, retained, and recorded? Auditability, evidence quality, review process, retention, and systems of record.
Which decisions remain customer-owned? Human accountability for risk, severity, remediation, release, retention, and closure.
Should we proceed, pause, escalate, or expand? The responsible next step based on operating-model readiness and the agreed evaluation charter.

Use three enterprise operating-model layers

For a governed Daybreak workflow, separate the operating model into context, agentic runtime, and observability. The layers answer different governance questions and should not be collapsed into one generic “platform” discussion.

Layer What it governs Key questions
Context What the workflow is allowed to know and use. Which repositories, tickets, architecture documents, scanner results, logs, identities, policies, and customer data are in scope? Which sources are authoritative? What must stay out of model context?
Agentic runtime What the workflow is allowed to do. Which tools can be called? Which actions are read-only, preparatory, or write-capable? Which environment is approved? What permissions, approvals, budgets, stop conditions, and human checkpoints apply?
Observability How the workflow can be reviewed and governed after and during execution. What traces, findings, evidence references, tool calls, approvals, decisions, and revalidation results are recorded? Who reviews them? How long are they retained? Which system is the final record?

Context

Context should be explicit and bounded. Define approved sources, data classes, access paths, freshness expectations, and the authority of each source. A repository may be in scope while production secrets, unrelated customer data, or unapproved logs remain out of scope.

The context layer should also define the evidence ceiling. If the workflow can inspect source code and tickets but cannot run approved tests, it may support source facts and supported inferences, but not runtime proof.

Agentic runtime

The runtime layer converts the charter into enforceable behavior. It should define tool allowlists, credentials, environment boundaries, allowed actions, approval points, and stop conditions.

read evidence
-> analyze finding
-> prepare recommendation
-> human review when required
-> bounded action if approved
-> revalidation

Do not treat an agent instruction as the only control for a high-impact action. Authorization, permission limits, approvals, and environment restrictions should be enforced outside the model wherever possible.

Observability

Observability is not only technical telemetry. For a security workflow it is also the evidence trail that allows the customer to understand what happened and defend the final decision.

Record enough information to reconstruct the evaluation path: target, source evidence, evidence level, tool activity, reviewer actions, approvals, finding disposition, bounded fix when used, revalidation result, and final decision owner.

Retention should be deliberate. Security evidence may contain sensitive code, logs, identities, or vulnerability details. The operating model should define what is retained, for how long, who can access it, and which system is authoritative.

Customer-owned decisions stay customer-owned

Daybreak or another advanced security workflow can gather evidence, correlate signals, prepare findings, suggest remediation, and support revalidation. The customer should still own decisions such as accepting risk, changing severity, approving remediation, expanding scope, releasing a change, retaining sensitive evidence, or closing a finding.

context defines what the workflow may know
-> agentic runtime defines what it may do
-> observability proves what happened
-> named customer owners make the final governed decisions

If one of these layers is unclear, the next action may be to pause, narrow the evaluation, or escalate the governance question before expanding capability.
