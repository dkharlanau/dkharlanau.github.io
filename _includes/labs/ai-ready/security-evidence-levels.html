Start with a bounded evaluation

A customer may be excited about Daybreak, Codex Security, or advanced cyber capability. That interest is useful, but it is not yet an evaluation plan.

Bounded evaluation means a deliberately limited evaluation focused on one approved workflow, target, review path, and success metric set. The purpose is to learn whether the workflow produces evidence that security and engineering teams can trust without expanding the exercise into an open-ended security program.

customer interest
-> evaluation question and hypothesis
-> approved workflow and target
-> bounded evaluation
-> evidence and review
-> decision
-> bounded fix when justified
-> revalidation

A bounded evaluation should define the target, timing, allowed evidence sources, review path, permissions, success metrics, and stop conditions before work begins. This keeps the evaluation useful, reviewable, and safe while still giving the customer enough evidence to decide whether broader adoption is justified.

Evaluation question and hypothesis

Every bounded evaluation should start with a clear question.

A good evaluation question connects the customer’s workflow bottleneck to a measurable improvement. It should make clear what the team wants to learn, where the improvement should happen, and what evidence would support the conclusion.

Evaluation question pattern: Can this workflow improve [specific bottleneck] for [bounded target] while preserving [required quality or safety condition]?

Hypothesis turns that question into a testable expectation. It should name the expected change, the metric used to observe it, the comparison point, and any guardrail that must not get worse.

If we use [approved workflow] on [bounded target],
then [measurable outcome] should improve compared with [baseline],
without reducing [evidence, safety, or review-quality guardrail].

This prevents an evaluation from becoming a product demonstration with no decision rule. The team should know before the work starts what result would support the hypothesis, what would weaken it, and what would remain unresolved.

Choose a strong first evaluation target

A strong first evaluation target meets these criteria:

Criterion What it means
Owned The customer controls the repository, application, backlog, or environment.
Authorized Security and engineering stakeholders approve the review.
Bounded The scope can be clearly described and enforced.
Relevant The target connects to a real security bottleneck or business-relevant risk.
Reviewable A named reviewer can assess findings, evidence, and proposed actions.
Measurable The team can define success metrics before the evaluation starts.
Context-rich The workflow includes enough code, system, test, scanner, ticket, or architecture context to support useful analysis.
Safe The activity avoids unapproved production testing, exploit-heavy behavior, unclear data handling, or unclear ownership.

If several of these criteria are weak, narrow the scope or choose a different first target. A difficult target may be valuable later, but the first evaluation should make evidence quality easy to judge.

Decision quality

Decision quality means the customer has better evidence to decide what should happen to a finding. The goal is not to maximize the number of findings. The goal is to make each disposition more defensible.

  • Confirm when the available evidence is strong enough to support the finding.
  • Suppress when the signal is a false positive, duplicate, accepted pattern, or otherwise not actionable under the agreed review rules.
  • Defer when the finding is credible but remediation is intentionally postponed.
  • Remediate when the issue is sufficiently supported and a bounded fix is justified.
  • Escalate when the impact, uncertainty, ownership, or required authority exceeds the current review boundary.
  • Leave unresolved when more proof is needed and the available evidence does not justify a stronger conclusion.
candidate finding
-> collect and classify evidence
-> assess decision quality
-> confirm / suppress / defer / remediate / escalate / unresolved

Good decision quality does not require every candidate finding to become a confirmed issue. A review is useful when it helps the customer distinguish what is proven, what is plausible, what can be safely dismissed, what needs action now, and what still has a proof gap.

Ask five review questions

Do not begin with a scanner, a model, or a fix. First define what the customer needs to know and what evidence would be strong enough to support a decision.

  1. What is the target? Is the customer asking about a whole repository or service, a backlog slice, a specific pull request, or an already validated finding?
  2. What is the timing? First assessment, high-risk review, pre-merge review, backlog triage, or post-validation remediation?
  3. What evidence is needed? Candidate findings, validated findings, attack-path evidence, source-supported review, remediation guidance, or revalidation?
  4. Is remediation ready? Is there enough evidence to prepare a bounded fix, or does the team need more validation first?
  5. How will we search for and analyze errors? Which signals should be checked first: changed code, tests, logs, configuration, scanner output, data flows, authorization paths, integration boundaries, or approved runtime behavior? Define how a suspicious signal becomes a reproducible defect or a documented proof gap.

Error search and analysis loop

Finding an error is not the same as understanding it. A useful review traces a signal to the smallest supported explanation before anyone starts writing a fix.

symptom or risk signal
-> locate evidence
-> reproduce or trace the behavior
-> isolate the smallest failure surface
-> test alternative explanations
-> classify the evidence
-> decide: validate, remediate, or stop

Good search starts from observable signals. Review the diff for changed assumptions, follow failing tests to the responsible branch, connect log errors to the request or job that produced them, inspect authorization and data-flow boundaries, and compare scanner findings with the actual code path.

During analysis, ask: What input triggers the problem? Where is the first incorrect state or decision? Is the issue local or caused upstream? Can another control still block the path? Is the behavior reproducible? What evidence would disprove the current theory? This prevents a suspicious pattern from being promoted into a confident claim just because it looks dramatic.

For AI-assisted review, use agents to widen the search surface, correlate evidence, and test hypotheses. Keep the final claim tied to code, configuration, logs, tests, scanner output, or explicitly approved runtime evidence. The goal is not to produce more findings. The goal is to reduce uncertainty without inventing certainty.

Remediation terminology

Bounded fix means a targeted change that addresses the specific finding without broad refactoring, unrelated changes, or unapproved expansion of scope.

A bounded fix should have a clear relationship to the evidence that justified the finding. If the proposed change requires a wider architectural rewrite, new product behavior, unrelated cleanup, or a larger permission boundary, treat that work as a separate scope decision rather than quietly attaching it to the remediation.

Revalidation means checking the original finding again after a proposed fix. The team should verify that the original failure path, unsafe behavior, or evidence condition is no longer present and that the fix did not merely move or hide the symptom.

validated finding
-> bounded fix
-> targeted verification
-> revalidate original finding
-> close, revise, or reopen

Do not close a finding only because code changed or a patch was proposed. Closure should follow revalidation against the original evidence and acceptance criteria.

Evidence levels for AI security review

Not every security statement carries the same evidentiary weight. For Codex Security and similar AI-assisted reviews, label findings by how strong the evidence is.

Source fact

Something directly visible in code, configuration, logs, test output, scanner output, or provided materials.

Example: “The pull request removes a role-checking helper from the account export route.”

Supported inference

A reasonable conclusion drawn from available source facts.

Example: “Because the route previously called the role-checking helper and now does not, authorization behavior may have changed for this action.”

Runtime proof

Evidence observed from approved runtime testing.

Example: “In the approved staging environment, a user without the export role successfully triggered the export endpoint.”

Use this label only when runtime activity was explicitly authorized and observed.

Unsupported claim

A statement that goes beyond available evidence.

Example: “This issue allows any attacker to export all customer accounts” when no runtime test, access path, or data exposure proof has been established.

Proof gap

Something that remains unproven and needs more evidence or human review.

Example: “The review does not confirm whether upstream middleware still blocks this route at runtime.”

This distinction protects credibility. It also helps customers understand what they can decide now and what still needs validation. A source fact or runtime proof can support a decision. A supported inference can justify more investigation. A proof gap should stay visible until it is resolved. An unsupported claim should not be presented as a finding.
